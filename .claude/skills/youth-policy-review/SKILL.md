# 변경 검토

검토 대상: $ARGUMENTS

인자가 없으면 커밋하지 않은 변경 전체(`git diff HEAD`와 추적하지 않는 새 파일)를 검토한다. 커밋 범위·브랜치·경로가 있으면 그 범위만 검토한다. 파일을 수정하거나 테스트·서버·외부 명령을 실행하지 않는다.

## 변경 개요

!`git status --short`

!`git diff --stat HEAD`

## 절차

1. 변경 파일을 분야로 나누고, 해당 분야의 공통 기준 `skills/youth-policy-<분야>/SKILL.md`와 Claude 보충 `.claude/skills/youth-policy-<분야>/SKILL.md`의 "Claude Code 보충" 절을 읽는다. 분야: `backend`, `api-contract`, `frontend`, `ingestion`, `eligibility`, `reminders`, `docs`, 공고별 규칙 JSON은 `rule-data`.
2. diff를 파일별로 읽고, 필요한 만큼 주변 코드·호출부·테스트를 확인한다. 추측만으로 문제를 보고하지 않는다.
3. 아래 점검표와 분야 기준으로 실제 실패 시나리오가 있는 문제만 남긴다. 각 항목을 다시 코드로 확인해 오탐을 제거한다.

## 점검표

이 저장소의 커밋 이력에서 반복해서 수정된 유형이다. 변경과 관계있는 항목만 확인한다.

### 화면

- 입력 수정·계정 전환·화면 이동·재시도 뒤 이전 요청의 늦은 응답이 상태를 덮어쓰는가. `AbortController`·요청 순번·현재 위치 확인이 있는가.
- 변경 요청(저장·비교·재처리·적용)이 진행 중에 다시 전송될 수 있는가. 자동 입력 중 제출이 가능한가.
- 재조회·재시도·질문 시작·개정 변경 뒤 키보드 초점이 사라지거나, 사용자가 옮긴 초점을 빼앗는가.
- 로그아웃·계정 전환·뒤로 가기 복원(`pageshow` `persisted`) 뒤 이전 계정의 화면·생년월일이 남는가. 개인 조건이 URL·브라우저 저장소·공개 캐시·메타데이터에 들어가는가.
- 조회 실패·로딩이 불충족·결과 없음·저장 안 됨으로 표시되는가. 날짜만 있는 마감을 브라우저 시간대·자정으로 바꾸는가.

### 서버·데이터

- 조건 결과 `UNKNOWN`·전체 `NEEDS_REVIEW`가 `NOT_MET`·`INELIGIBLE`로 바뀌는 경로가 있는가. 미확인 예외가 있는데 불충족으로 확정하는가.
- `LocalDate.now()`·`Instant.now()`를 직접 쓰거나 서울 날짜 변환 없이 UTC 날짜를 쓰는가. 주입한 `Clock`을 쓰는가.
- 외부 API·AI·이메일 호출이 DB 트랜잭션·잠금 안에서 실행되는가. 업무 변경과 Outbox 요청이 같은 트랜잭션에 저장되는가.
- 오래된 수집 응답·이전 AI 요청 결과·같은 요청의 재전송이 최신 상태를 덮어쓰거나 중복 개정·알림을 만드는가.
- 회원 데이터 접근에 서버 소유권 검사가 있는가. 관리자 쓰기에 CSRF·요청 ID·사유 기록이 있는가.
- 기준 스키마·규칙 시드(`V1__baseline_schema.sql`·`V2__seed_reviewed_policy_rules.sql`)를 비롯해 적용된 Flyway 파일을 수정했는가. 스키마·시드 변경을 다음 번호의 새 SQL 파일로 추가했고 그 번호가 기존 파일과 중복되지 않는가.
- 오류 응답·로그에 개인정보·DB 오류·비밀값이 나가는가.

### 계약·생성물·문서

- `api/openapi.*.json`·`frontend/src/generated/**`를 직접 수정했는가. 서버 DTO 변경 뒤 재생성하지 않았는가.
- 웹에 서버 DTO를 별도 타입으로 복제했는가.
- 정책별 Java 클래스로 공고 값을 추가했는가(ADR-0003 위반).
- 문서가 코드와 다른 동작·명령을 설명하거나, 계획을 구현 완료로 기록했는가. 테스트 총개수를 여러 문서에 복사했는가.
- 변경한 동작의 충족·불충족·미확인·실패 경로에 테스트가 없는가. 같은 사례를 여러 계층에 반복했는가.

## 보고 형식

한글로, 심각한 순서대로 보고한다. 문제가 없으면 "확인한 범위에서 문제 없음"과 확인한 분야를 적는다.

```
1. [높음|중간|낮음] <파일>:<줄> — <문제 한 문장>
   - 실패 시나리오: <입력·상태 → 잘못된 결과>
   - 근거: <확인한 코드·호출부>
   - 제안: <최소 수정 방향>
```

마지막에 "보완할 테스트"(변경 동작 기준, 최대 5개)와 "확인하지 못한 부분"을 짧게 적는다. 스타일·취향 지적과 변경 범위 밖의 기존 문제는 넣지 않는다. 기존 문제가 변경과 직접 얽혀 있으면 별도로 표시한다.
