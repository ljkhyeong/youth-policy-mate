# AI 요청 예산 예약·정산 상태

## 1. 범위

[PRD 6.2·8절](../PRD/0001_product-baseline/spec.md)과 [AI 요청 전 판단](ai-request-admission.md)을 따른다. 사전 판단에서 잔액이 충분한 요청을 요청별로 예약하고, 외부 호출 이후 결과·청구가 확인되지 않은 금액을 보존하며, 확인된 비용 또는 무과금 근거로 종료하는 내부 상태를 정의한다.

이번 모델은 메모리의 순수 Java 상태 전이다. 실제 PostgreSQL 저장·행 잠금·유일 제약, AI 호출, 공급자 사용량·청구 확인은 없다. 월 운영비 3만 원 중 AI 배분액과 공급자 가격도 정하지 않는다.

## 2. 상태와 금액

| 상태 | 의미 | 예약액 처리 |
|---|---|---|
| `HELD` | 사전 판단에 사용한 최대 비용을 요청에 확보함 | 유지 |
| `DISPATCHED` | 예약 후 외부 호출 식별자를 기록함 | 유지 |
| `OUTCOME_UNKNOWN` | 타임아웃·연결 끊김 등으로 결과를 확정하지 못함 | 유지 |
| `SETTLED` | 공급자 청구 금액을 확인해 확정액으로 반영함 | 최대 비용 예약을 해제하고 실제 비용을 확정액에 추가 |
| `CANCELLED` | 외부 호출 전에 취소함 | 해제 |
| `RELEASED_NO_CHARGE` | 외부 호출 후 무과금을 별도 근거로 확인함 | 해제 |

타임아웃과 요청 실패만으로 무과금을 추정하지 않는다. `OUTCOME_UNKNOWN`은 재시작이나 예산 기간 변경 뒤에도 예약액으로 남아야 한다. 후보 생성 성공 여부와 청구 확인도 별개다. 후보를 받았더라도 실제 비용을 모르면 정산 완료로 처리하지 않는다.

실제 비용이 최대 예약액보다 크면 그 사실을 버리지 않고 확정액에 반영한 뒤 초과 정산으로 구분한다. 이 상태에서는 후속 예약을 보류하고 공급자 가격 산정·청구를 대사해야 한다.

## 3. 중복과 충돌

- 예약 식별자는 한 예산 안에서 한 요청과 최대 비용에만 연결한다.
- 같은 정책 개정·작업 종류·생성 방식·요청 순번은 다른 예약 식별자로 다시 예약하지 않는다. 재시도는 새 요청 순번을 사용한다.
- 성공한 예약 명령을 같은 식별자와 내용으로 다시 전달하면 재생으로 처리한다. 다른 요청이나 금액이면 충돌이다.
- 외부 호출과 종료 확인도 같은 예약 안에서 같은 식별 정보의 재전달만 재생으로 처리한다.
- 정산·호출 전 취소·무과금 확인 중 하나가 끝나면 다른 종료 결과로 바꾸지 않는다. 늦은 결과는 자동으로 확정 상태를 덮지 않는다.
- 사전 판단의 잔액과 실제 예약 직전 잔액이 다르면 오래된 판단을 거절한다. 다만 메모리 객체의 비교만으로 동시 작업자의 중복 예약을 막았다고 보지 않는다.

## 4. 실제 저장 연결 조건

1. 예산 ID·기간·한도·확정액·예약액과 요청별 예약·외부 호출·결과 확인 정보를 Flyway 스키마로 확정한다.
2. 짧은 PostgreSQL 트랜잭션에서 최신 정책·후보·요청·잔액을 다시 읽고, 잔액 확인과 예약 저장을 함께 처리한다.
3. 예산 버전 비교나 행 잠금으로 동시 예약을 직렬화하고, 예약 ID와 요청 ID에 필요한 유일 제약을 둔다.
4. 예약 커밋 후 외부 호출하며 대기 중에는 DB 잠금을 유지하지 않는다. 호출 식별자를 저장해 재시작 후 결과를 조회할 수 있게 한다.
5. 정산·호출 전 취소·무과금 확인도 멱등 식별자와 함께 저장한다. 결과 미확인 예약은 운영자가 확인할 수 있게 하고 자동 만료시키지 않는다.
6. 내부 최대 비용과 실제 공급자 청구를 대사하고, 초과 청구·가격 변경·환율·세금을 포함한 운영 상한을 공개 전에 검증한다.

현재 구현과 검사 범위는 [개발 기록](../development/ai-budget-reservation-lifecycle.md)을 따른다. 이 내부 상태만으로 PRD AC-06·AC-11이나 실제 과금 차단을 완료했다고 보고하지 않는다.
