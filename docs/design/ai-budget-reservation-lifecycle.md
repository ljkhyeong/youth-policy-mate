# AI 요청 예산 예약·정산 상태

## 1. 범위

[PRD 6.2·8절](../PRD/0001_product-baseline/spec.md)과 [AI 요청 전 판단](ai-request-admission.md)을 따른다. 사전 판단에서 잔액이 충분한 요청을 요청별로 예약하고, 외부 호출 이후 결과·청구가 확인되지 않은 금액을 보존하며, 확인된 비용 또는 무과금 근거로 종료하는 내부 상태를 정의한다.

PostgreSQL 저장소를 예약·호출 이후 상태 전이의 기준 구현으로 사용한다. 별도의 메모리 상태 엔진은 유지하지 않고, Java에는 호출부와 저장소가 공유하는 상태·이벤트 값 타입을 둔다. 상태 전이와 시간 경계는 실제 저장소 테스트에서 확인한다. DB에는 예산, 요청별 예약, 호출 식별 정보, 결과 미확인과 종료 확인을 저장한다. 외부 AI 호출과 공급자 사용량·청구 조회는 없으며, 저장하는 정산·무과금 정보는 호출 측이 확인해 전달한 사실만 반영한다. 월 운영비 3만 원 중 AI 배분액과 공급자 가격도 정하지 않는다.

## 2. 상태와 금액

| 상태 | 의미 | 예약액 처리 |
|---|---|---|
| `HELD` | 사전 판단에 사용한 최대 비용을 요청에 확보함 | 유지 |
| `DISPATCHED` | 예약 후 외부 호출 식별자를 기록함 | 유지 |
| `OUTCOME_UNKNOWN` | 타임아웃·연결 끊김 등으로 결과를 확정하지 못함 | 유지 |
| `SETTLED` | 공급자 청구 금액을 확인해 확정액으로 반영함 | 최대 비용 예약을 해제하고 실제 비용을 확정액에 추가 |
| `CANCELLED` | 외부 호출 전에 취소함 | 해제 |
| `RELEASED_NO_CHARGE` | 외부 호출 후 무과금을 별도 근거로 확인함 | 해제 |

타임아웃과 요청 실패만으로 무과금을 추정하지 않는다. `OUTCOME_UNKNOWN`은 재시작이나 예산 기간 변경 뒤에도 예약액으로 남아야 한다. 후보 생성 성공 여부와 청구 확인도 별개다. 후보를 받았더라도 실제 비용을 모르면 정산 완료로 처리하지 않는다.

실제 비용이 최대 예약액보다 크면 그 사실을 버리지 않고 확정액에 반영한 뒤 초과 정산으로 구분한다. 이 상태에서는 후속 예약을 보류하고 공급자 가격 산정·청구를 대사해야 한다.

## 3. 중복과 충돌

- 예약 식별자는 한 예산 안에서 한 요청과 최대 비용에만 연결한다.
- 같은 정책 개정·작업 종류·생성 방식·요청 순번은 다른 예약 식별자로 다시 예약하지 않는다. 재시도는 새 요청 순번을 사용한다.
- 성공한 예약 명령을 같은 식별자와 내용으로 다시 전달하면 재생으로 처리한다. 다른 요청이나 금액이면 충돌이다.
- 외부 호출과 종료 확인도 같은 예약 안에서 같은 식별 정보의 재전달만 재생으로 처리한다.
- 정산·호출 전 취소·무과금 확인 중 하나가 끝나면 다른 종료 결과로 바꾸지 않는다. 늦은 결과는 자동으로 확정 상태를 덮지 않는다.
- 사전 판단의 잔액과 실제 예약 직전 잔액이 다르면 오래된 판단을 거절한다. PostgreSQL 예약 경계에서 잠금과 유일성 제약으로 동시 작업자의 중복 예약을 막는다.

## 4. PostgreSQL 저장 경계

- Flyway V1은 `ai_budgets`와 `ai_request_reservations`를 만든다. 예산은 기간·한도·확정액·예약액을 저장하고, 예약은 정책 적용 개정·원본 해시·AI 작업 종류·생성 방식·요청 순번·가격 버전·최대 비용을 보존한다.
- Flyway V2는 호출 식별자·결과 미확인·완료 식별자·실제 비용 열을 추가한다. 단계마다 필요한 열의 조합과 시간 순서를 DB 제약으로 확인한다.
- 예약 트랜잭션은 예산 행을 `FOR UPDATE`로 잠그고 DB의 최신 잔액과 사전 판단 값을 다시 비교한다. 예약 INSERT와 예약액 증가는 같은 트랜잭션에서 처리한다.
- 정산·호출 전 취소·확인된 무과금 해제는 예산 행과 예약 행을 같은 순서로 잠근다. 예약 상태 변경과 확정액·예약액 변경은 한 트랜잭션에서 처리해 같은 예약액을 두 번 해제하지 않는다.
- 예약 ID는 기본 키다. 정책 ID·AI 작업 종류·요청 순번에도 유일 제약을 둬 같은 요청의 다른 예약을 막는다.
- 같은 내용의 재전달은 기존 예약을 반환하고 금액을 더하지 않는다. 다른 내용의 예약 ID와 이미 예약된 요청은 별도 충돌로 반환한다.
- PostgreSQL `timestamptz` 정밀도에 맞춰 저장·비교 시각을 마이크로초로 맞춘다. 나노초 차이 때문에 정상 재전달을 충돌로 오인하지 않는다.
- `HELD`·`DISPATCHED`·`OUTCOME_UNKNOWN`은 갱신 시각 순으로 조회할 수 있다. 이 조회는 재시작 후 확인 대상을 찾는 기능이며 작업자 소유권 획득이나 자동 재호출을 뜻하지 않는다.
- 예산 행은 자동 생성하거나 기본 금액으로 채우지 않는다. 운영비 배분이 정해진 뒤 별도 설정 경계에서 만들어야 한다.

## 5. 남은 외부 연결

1. [AI 실행 경계](policy-ai-execution.md)는 호출 식별자를 기록한 뒤 DB 잠금 없이 내부 포트를 실행하고 응답·결과 미확인을 상태 전이에 연결한다. 실제 공급자 계약에 맞는 호출 식별자와 결과 조회 방식은 공급자 선정 후 확인한다.
2. 재시작 후 미완료 조회에 작업자 소유권·재확인 시도 이력·운영 표시를 연결한다. `OUTCOME_UNKNOWN`을 시간 경과만으로 자동 해제하지 않는다.
3. 정책·후보·예정 요청 저장이 생기면 예약 트랜잭션에서 최신 개정과 기존 후보도 함께 다시 확인한다.
4. 내부 최대 비용과 실제 공급자 청구를 대사하고, 초과 청구·가격 변경·환율·세금을 포함한 운영 상한을 공개 전에 검증한다.

현재 구현과 검사 범위는 [개발 기록](../development/ai-budget-reservation-lifecycle.md)을 따른다. 원자적 예약과 내부 상태 전이는 실제 PostgreSQL에서 검증했지만, 이 경계만으로 PRD AC-06·AC-11이나 외부 과금 차단을 완료했다고 보고하지 않는다.
