# AI 요청 전 재사용·비용 확인

## 1. 범위

[PRD 6.2·8절](../PRD/0001_product-baseline/spec.md)과 [AI 후보 설계](policy-ai-candidates.md)를 따른다. 기존 후보 재사용, 신규·변경 정책 또는 명시적 재시도 여부, 주어진 AI 예산·요청별 최대 비용으로 사전 판단만 수행한다.

월 3만 원은 모든 운영비의 합계다. AI 배분액·공급자·요금·환율·과금 주기는 미정이므로 기본 예산이나 예상 단가를 넣지 않는다. 실제 원천·AI 호출, DB 예산 예약·정산, 공급자 과금 차단은 이번 범위가 아니다. 제품 정책과 PRD 상한은 변경하지 않는다.

## 2. 입력과 판단 순서

- 정책 입력은 기존 `PolicyRevisionState.Transition`이다. 정책의 현재 적용 개정과 이번 수집이 새 개정을 만들었는지를 함께 받는다.
- AI 후보 상태·예정 요청은 같은 정책·작업 종류여야 한다. 예정 요청은 현재 개정과 원본 근거가 같아야 하며, 정책 ID나 요청 순번을 AI 응답에서 가져오지 않는다.
- 현재 개정·생성 방식의 후보가 있으면 비용 설정이 없거나 소진되어도 재사용한다. 새 AI 요청은 만들지 않는다.
- 후보가 없으면 이미 처리한 AI 요청 순번을 다시 사용하지 않는다. 자동 처리에서는 새 개정을 만든 경우에만 다음 검사를 진행한다. 단순 재수집·생성 방식 변경·수집 실패만으로 새 호출을 허용하지 않는다.
- 같은 개정에 처리 결과가 이미 있으면 자동 반복하지 않는다. 명시적 재시도는 현재 개정·생성 방식에 실패·잘못된 출력·한도 보류 결과가 있고 새 요청 순번일 때만 비용을 다시 확인한다. 재시도도 한도를 우회하지 않는다.
- AI 예산 없음, 현재 시각이 예산 기간 밖, 잔액 소진, 최대 비용 미확인, 다른 요청의 비용 정보, 유효기간이 지난 비용 정보를 각각 보류한다.
- 남은 금액 안에 요청별 최대 비용이 들어오면 **예산 예약 필요**를 반환한다. 이는 아직 외부 호출 허용이나 예약 완료가 아니다.

원본·후보·자격 판정 상태는 이 검사에서 변경하지 않는다. 보류 결과를 기존 AI 후보 모델의 미생성 결과로 기록하는 연결과 재시도 일정은 아직 없다.

## 3. 예산과 최대 비용

예산 입력은 내부 예산 ID, 명시적인 시작·종료 시각, 한도·확정 사용액·예약액이다. 모든 금액은 원화 `BigDecimal`이며 음수를 받지 않는다. 확정 사용액과 예약액이 이미 한도를 넘은 상태도 받아 새 요청을 보류할 수 있어야 한다.

예약액에는 진행 중 요청과 호출·비용 결과가 아직 확인되지 않은 요청의 확보 금액을 포함해야 한다. 공급자 오류나 타임아웃을 무료로 간주해 예약을 해제하면 안 된다. 잔액은 `한도 - 확정 사용액 - 예약액`으로 계산하며, 0 이하이면 보류한다. 0원 한도는 호출 중지로 취급한다.

요청별 비용은 평균 예상액이 아니라 **해당 예정 요청에 연결된 최대 비용**이어야 한다. 비용 정보에는 생성 요청 전체, 가격 산정 버전, 유효 종료 시각과 최대 금액을 연결한다. 같은 정책이라도 개정·생성 방식·시도 순번 등이 달라지면 다른 요청의 비용으로 사용하지 않는다.

최대 금액에는 최대 입력·출력, 부가 기능, 세금·환율·반올림 등 실제 청구에 필요한 항목을 반영해야 한다. 이를 계산하는 공급자 어댑터는 아직 없다. 비용을 모르면 0원으로 보충하지 않는다. 요청별 최대 금액이 잔액과 정확히 같으면 예약 대상으로 판단하며 소수 금액을 버리지 않는다.

예산 기간은 시작 포함·종료 제외다. 비용 유효 종료 시각과 같으면 만료다. 이 시각들은 호출 측이 확정해서 제공하며 이번 코드가 서울 월 경계·공급자 청구월·갱신 주기를 정하지 않는다.

## 4. 실제 호출 연결 전 필요한 조건

1. 서버·DB·원본 보관·이메일 비용을 고려해 AI 배분액을 정하고, 원화 최대 비용 산정·갱신 기준을 공급자 계약으로 확인한다.
2. 짧은 트랜잭션에서 최신 정책·AI 예정 요청·후보·예산을 다시 읽는다. 동일 정책·작업의 진행 중 요청도 확인한다.
3. 예산 버전 비교·행 잠금 등으로 잔액 확인과 요청별 예약을 함께 저장한다. 요청 식별자의 유일 제약으로 중복 예약을 막는다. 사전 판단 결과만으로 외부 호출하지 않는다.
4. 예약 저장에 성공한 뒤 외부 호출한다. 호출 중에는 DB 잠금을 유지하지 않는다. 재시작·중복 작업자·늦은 요청 결과의 처리 소유권도 확인한다.
5. 내부 예약은 원래 예산에 정산하고 실제 청구월과의 차이는 별도로 대사한다. 결과 미확인은 예약을 유지하고, 미호출·무과금이 확인된 경우에만 해제한다. 기간 변경으로 미확인 금액을 지우지 않는다.
6. 공급자 청구가 보수적인 최대 금액을 넘는 경우의 차단·대사와 실제 청구 검증까지 구현한다. 예산 알림이나 이 순수 모델만으로 외부 청구 상한을 보장하지 않는다.

현재 구현·검사는 [개발 기록](../development/ai-request-admission.md)을 따른다. PRD AC-06·AC-11의 실제 연동·운영비 검증은 아직 완료하지 않았다.
