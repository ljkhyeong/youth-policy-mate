# AI 미완료 예약 복구 소유권과 확인 이력

## 1. 범위

[AI 예약·정산 상태](ai-budget-reservation-lifecycle.md)와 [AI 실행 경계](policy-ai-execution.md)를 따른다. 서버 재시작 뒤 `HELD`·`DISPATCHED`·`OUTCOME_UNKNOWN` 예약을 여러 작업자가 중복 확인하지 않도록, 제한된 시간의 확인 소유권과 시도 이력을 정의한다.

이번 소유권은 확인할 예약을 한 작업자에게 배정하는 내부 임대다. 인공 복구 조정자는 임대와 예약 상태를 다시 확인한 뒤 정산·무과금·호출 전 취소를 적용한다. 실제 공급자 상태 조회와 AI 재호출은 수행하지 않는다.

## 2. 임대와 시도 상태

호출 측은 시도 ID·작업자 ID·획득 시각·만료 시각을 모두 제공한다. 운영 주기와 공급자 응답 시간이 정해지지 않았으므로 기본 임대 시간을 넣지 않는다.

| 시도 상태 | 의미 |
|---|---|
| `ACTIVE` | 한 작업자가 미완료 예약의 확인 소유권을 가진 상태 |
| `COMPLETED` | 작업자가 임대 시간 안에 확인 시도를 마친 상태 |
| `EXPIRED` | 임대가 끝나 새 작업자가 소유권을 얻거나 늦은 완료가 도착한 상태 |

`COMPLETED`는 AI 결과·청구·예약 상태가 해결됐다는 뜻이 아니다. 확인 시도 결과는 `CHECK_COMPLETED`·`CHECK_FAILED`·`MANUAL_REVIEW_REQUIRED`로 남기고, 소유권 획득 당시 단계와 완료 당시 단계를 따로 저장한다.

오래 걸리는 외부 확인에서는 같은 작업자가 끝나기 전의 현재 임대를 더 늦은 시각까지 갱신할 수 있다. 갱신은 새 시도를 만들거나 시도 횟수를 늘리지 않으며 최초 획득 시각과 작업자를 바꾸지 않는다.

## 3. 소유권 획득

- 특정 예약을 직접 선택하거나 가장 오래된 미완료 예약을 선택할 수 있다.
- 다음 예약 선택은 `FOR UPDATE SKIP LOCKED`를 사용한다. 한 작업자가 잠근 예약 때문에 다른 예약의 선택이 기다리지 않는다.
- 같은 예약에는 `ACTIVE` 시도를 하나만 허용한다. 만료 전 다른 작업자는 현재 소유자를 확인하고 획득하지 않는다.
- 만료된 `ACTIVE` 시도는 새 소유권 획득 시 `EXPIRED`로 바꾸고 시도 순번을 증가시킨다.
- 같은 시도 ID와 내용의 재전달은 재생한다. 같은 시도 ID를 다른 작업자·시각·예약에 사용하면 충돌이다.
- 시도 ID 검사는 PostgreSQL 트랜잭션 자문 잠금으로 직렬화한다. 다른 예약의 같은 시도 ID가 동시에 들어와도 한 내용만 저장한다.
- 종료 상태인 예약은 새로 소유하지 않는다.

## 4. 확인 완료

- 소유한 작업자만 시도를 완료할 수 있다.
- 완료 시각은 소유권 획득과 현재 예약 상태보다 빠를 수 없고 임대 만료보다 빨라야 한다.
- 임대 만료 시각과 같거나 늦게 도착한 완료는 적용하지 않고 시도를 `EXPIRED`로 기록한다.
- 같은 완료 정보의 재전달은 재생하고 다른 결과·시각은 충돌로 남긴다.
- 단순 완료는 예약 상태를 바꾸지 않는다. 확인된 청구·무과금·호출 전 중단은 복구 조정자가 펜싱을 통과한 경우에만 기존 `AiBudgetReservationLifecycleStore`로 적용한다.

## 5. 복구 결과 적용과 펜싱

1. 작업자는 임대를 얻은 뒤 현재 예약 단계와 갱신 시각을 읽는다.
2. 외부 확인 포트는 DB 트랜잭션 밖에서 호출한다.
3. 적용 시점에 활성 시도 ID·시도 순번·작업자·만료 시각을 잠가 다시 확인한다.
4. 확인 전후의 예약 단계나 갱신 시각이 다르면 결과를 적용하지 않고 수동 검토 필요로 남긴다.
5. 적용 시각이 임대 만료와 같거나 늦거나 새 시도가 활성화됐으면 오래된 결과를 거절한다.
6. 예약 상태 변경과 복구 시도 완료는 하나의 짧은 트랜잭션으로 처리한다.

시도 순번은 예약마다 증가하는 펜싱 토큰이다. 공급자가 기록한 청구·무과금 시각과 서버가 결과를 적용하는 시각을 구분하고, 임대 유효성은 실제 적용 시각으로 판단한다.

### 5.1 활성 임대 갱신

- 호출 측은 갱신 ID, 예약 ID, 시도 ID·순번·작업자, 확인한 현재 만료 시각, 갱신 시각과 새 만료 시각을 제공한다.
- 갱신 ID를 직렬화한 뒤 예약 행과 시도 행 순서로 잠근다. 시도 ID·순번·작업자와 확인한 만료 시각이 모두 현재 값과 같아야 한다.
- 시도는 `ACTIVE`, 예약은 미완료여야 한다. 갱신 시각은 현재 예약·시도의 마지막 갱신보다 빠를 수 없고 현재 임대 만료보다 빨라야 하며, 새 만료는 현재 만료보다 늦어야 한다.
- 이미 만료되거나 완료·교체된 시도, 종료 예약, 다른 작업자와 오래된 만료 시각을 사용한 요청은 현재 임대를 바꾸지 않는다. 끝난 임대를 과거 시각으로 소급해 되살리지 않는다.
- 같은 갱신 ID와 내용은 재전달하고, 같은 ID의 다른 내용은 충돌로 거절한다. 서로 다른 ID가 같은 만료 시각을 동시에 갱신하면 잠금을 먼저 얻은 요청만 반영한다.
- 갱신 성공은 현재 시도의 `lease_until`과 `updated_at`을 바꾸고 별도 감사 기록을 같은 트랜잭션에 저장한다. heartbeat 주기와 갱신 뒤 유지할 임대 길이는 공급자와 운영 조건을 정한 뒤 호출 측에서 제공한다.

### 5.2 외부 확인 중 자동 heartbeat

- 복구 조정자는 종료 예약이 아닌 활성 시도를 외부에서 확인하기 전에 heartbeat를 예약하고, 외부 확인이 끝나면 더 실행되지 않게 취소한다. 실제 예약 방식은 호출 측이 제공한 스케줄러에 맡긴다.
- heartbeat 주기와 갱신 뒤 유지할 임대 길이는 모두 양수여야 하고, 임대 길이는 주기보다 길어야 한다. 공급자가 정해지기 전에는 기본값이나 최대 연장 횟수를 코드에 넣지 않는다.
- 각 heartbeat는 신뢰할 수 있는 서버 시각에 임대 길이를 더해 새 만료 시각을 계산한다. 이미 현재 만료보다 충분히 긴 경우에는 갱신을 생략해 임대가 필요 이상으로 누적되지 않게 한다.
- 실제 갱신은 `AiReservationRecoveryLeaseRenewalStore`의 짧은 트랜잭션에서 실행한다. 외부 확인 호출과 복구 조정자는 DB 트랜잭션을 유지하지 않는다.
- `RENEWED`와 같은 명령의 `REPLAYED`만 다음 heartbeat를 허용한다. 현재 임대·소유자·예약 상태가 달라 갱신이 거절되면 외부 확인이 반환한 결과를 적용하지 않고 갱신 거절 결과를 조정자 호출자에게 돌려준다.
- 갱신 저장 중 예외가 발생해 성공 여부를 확인할 수 없으면 외부 확인이 끝난 뒤 해당 예외를 전달하고 결과를 적용하지 않는다. 공급자 호출 자체를 중간 취소할 수 있는지는 실제 공급자 어댑터가 정해진 뒤 별도로 결정한다.
- 외부 확인 완료와 heartbeat가 겹치면 진행 중인 갱신이 끝난 뒤 완료 여부를 결정한다. 완료 처리 뒤 시작된 heartbeat는 상태를 바꾸지 않는다.

## 6. PostgreSQL 경계

Flyway V3는 `ai_reservation_recovery_attempts`를 만든다. 예약별 시도 순번, 작업자, 임대 기간, 시작·완료 단계와 확인 결과를 보존한다. 부분 유일 인덱스로 예약별 `ACTIVE` 행을 하나만 허용하고, 상태별 필수 열·임대 기간·완료 시각을 제약으로 확인한다.

Flyway V8의 `ai_reservation_recovery_lease_renewals`는 갱신 ID, 대상 시도·순번·작업자, 이전 만료·갱신·새 만료 시각을 보존한다. 한 시도의 같은 만료 스냅샷은 한 번만 갱신할 수 있고, 성공 기록은 갱신 시각이 이전 만료보다 빠르며 새 만료가 이전 만료보다 늦어야 한다.

복구 소유권 저장소는 예약 행만 잠그며 예산 행을 잠그지 않는다. 확인 이력만 기록할 때는 예산 합계를 바꾸지 않기 때문이다. 정산·해제·취소를 적용할 때는 예산→예약→복구 시도 순서로 잠그고, 상태 변경과 시도 완료를 함께 커밋한다. 외부 조회 중에는 DB 트랜잭션을 유지하지 않는다.

## 7. 재확인 주기와 자동 중단 정책

공급자와 운영 주기가 정해지지 않았으므로 코드에 기본 재확인 간격이나 최대 횟수를 넣지 않는다. 호출 측은 다음 값을 한 묶음으로 제공한다.

- 1 이상의 최대 시도 횟수
- 각 완료·만료 시도 뒤에 적용할 양수 간격. 간격 개수는 최대 시도 횟수보다 하나 적다.

첫 시도는 미완료 예약의 현재 상태 시각부터 가능하다. 이후 시도 가능 시각은 예약의 최근 갱신 시각과 직전 시도의 완료 경계 중 늦은 시각에 해당 간격을 더해 계산한다. 활성 임대는 만료 전까지 보류한다. 임대가 끝난 뒤에도 설정한 간격을 적용하므로 작업자 장애 직후 같은 예약을 즉시 반복 선택하지 않는다.

완료·만료·시각상 만료된 활성 시도는 모두 최대 횟수에 포함한다. 재개되지 않은 `MANUAL_REVIEW_REQUIRED`와 종료 예약은 남은 횟수와 관계없이 자동 확인을 중단한다. `CHECK_COMPLETED`라도 예약이 `DISPATCHED`처럼 미완료이면 청구가 대기 중일 수 있으므로 다음 확인 시각을 계산한다.

수동 검토 재개는 기존 시도의 결과를 수정하지 않고 별도 감사 기록으로 남긴다. Flyway V7의 `ai_reservation_recovery_review_resumes`는 재개 ID, 대상 수동 검토 시도, 운영자, 정해진 재개 사유, 확인한 예약 단계·갱신 시각과 재개 시각을 보존한다. 사유는 공급자 상태 확인, 내부 상태 확인, 복구 장애 해소로 제한하며 자유 형식 공급자 응답이나 오류 메시지는 저장하지 않는다. 한 수동 검토 시도에는 재개 기록을 하나만 허용한다.

재개 저장소는 재개 ID를 직렬화한 뒤 예약 행과 대상 시도를 잠근다. 예약이 여전히 미완료이고 운영자가 확인한 단계·갱신 시각과 같으며, 대상이 해당 예약의 가장 최근 `COMPLETED`·`MANUAL_REVIEW_REQUIRED` 시도일 때만 기록한다. 같은 재개 명령은 재전달하고 같은 ID의 다른 내용, 바뀐 예약, 종료 예약, 과거·다른 결과의 시도와 이미 재개된 시도는 거절한다. 운영자 식별자의 인증·권한 확인은 후속 관리자 경계의 책임이다.

재개 기록은 사용한 시도 횟수를 초기화하지 않는다. 재확인 가능 시각은 예약 갱신·수동 검토 완료·재개 시각 중 늦은 시각에 기존 순번의 간격을 더해 계산한다. 따라서 재개 직후 즉시 반복 확인하지 않으며, 이미 최대 시도 횟수에 도달했다면 수동 검토가 재개돼도 자동 확인은 계속 중단한다.

순수 정책은 다음 세 결과만 반환한다.

- `Ready`: 다음 시도 순번과 확인 가능 시각
- `Deferred`: 활성 임대 또는 재확인 간격 때문에 보류하며 다시 판단할 시각
- `Stopped`: 예약 종료, 수동 검토, 최대 횟수 도달로 자동 확인 중단

이 판단은 작업자를 실행하거나 DB 상태를 바꾸지 않는다. 기존 `claimNext`도 이 정책을 직접 사용하지 않는다. 운영 조회의 후보를 배정할 때는 `Ready`였던 항목만 받고, 예약 행을 잠근 뒤 현재 예약과 전체 이력으로 다시 판단한 경우에만 소유권을 만든다.

## 8. 내부 운영 조회 경계

오래된 미완료 예약을 운영 대상으로 찾을 때는 호출 측이 기준 시각과 최대 조회 수, 재확인 일정을 명시한다. 조회는 `updated_at`이 기준 시각 이하인 `HELD`·`DISPATCHED`·`OUTCOME_UNKNOWN` 예약만 오래된 순서로 제한해 선택한다. 같은 갱신 시각에서는 예약 ID로 순서를 고정한다.

한 조회 결과에는 다음 정보를 같은 PostgreSQL 스냅샷으로 묶는다.

- 정책 ID·AI 작업 종류·생성 방식 버전·요청 순번
- 예약 단계·예약액·호출·결과 미확인·완료 정보와 마지막 갱신 시각
- 예약별 전체 복구 시도 이력
- 수동 검토 재개 감사 이력
- 주어진 일정과 조회 시각으로 계산한 `Ready`·`Deferred`·`Stopped` 판단

이 경계는 운영 판단을 위한 읽기 전용 모델이다. 예약·예산·복구 시도를 변경하거나 소유권을 획득하지 않는다. 원본 본문·AI 프롬프트·사용자 개인정보도 반환하지 않는다.

후속 배정 경계는 조회 결과에 실제로 포함된 `Ready` 후보만 받는다. 배정 시각은 조회 판단 시각보다 빠를 수 없으며, 다음 순서로 다시 확인한다.

1. 시도 ID의 기존 사용 여부를 직렬화하고 같은 요청이면 기존 배정을 재전달한다.
2. 예약 행을 잠그고 현재 예약 스냅샷과 전체 복구 이력을 다시 읽는다.
3. 같은 일정과 실제 배정 시각으로 재확인 정책을 다시 계산한다.
4. 여전히 `Ready`일 때만 다음 시도 순번의 활성 임대를 저장한다.

수동 검토·최대 횟수 도달·재확인 대기·활성 임대가 조회 뒤 새로 생기면 배정하지 않는다. 서로 다른 작업자가 같은 조회 결과를 동시에 사용해도 예약 행 잠금과 활성 임대 제약으로 한 작업자만 소유권을 얻는다.

현재 내부 저장소 조회, 명시적으로 선택한 후보의 안전한 배정과 배정된 활성 시도의 인공 확인 실행까지 구현한다. 실행 전에는 DB의 현재 시도를 다시 읽어 완료·교체된 배정을 거절한다. 실행 중에는 DB 트랜잭션을 열지 않고, 결과 적용 시 기존 펜싱으로 예약·임대 변경을 다시 확인한다. 배정 후 예약이 종료됐다면 공급자를 조회하지 않고 시도를 수동 검토로 마친다.

제한 목록 실행 경계는 한 운영 조회가 반환한 순서를 유지하며 `Deferred`·`Stopped`를 DB 변경 없이 건너뛴다. `Ready`만 호출 측 임대로 배정하고, 잠금 후 다시 준비된 경우에만 복구 조정자를 호출한다. 후보 하나의 외부 확인 예외는 해당 결과에 남기고 다음 후보를 계속 처리한다. 한 번에 읽고 처리할 최대 수는 운영 조회의 `limit`가 제한한다.

실행 기록 경계는 호출 측이 제공한 실행 ID·작업자 ID와 운영 조회 조건을 `RUNNING`으로 먼저 저장한다. 같은 실행 ID와 모든 값이 같으면 실행 중 또는 완료 결과를 재전달하고, 값이 다르면 충돌로 거절한다. 후보 처리가 끝나면 조회 수와 보류·미배정·완료·조정자 미시작·후보 실패·heartbeat 중단 수를 `COMPLETED`로 저장한다. 조회나 임대 생성처럼 실행 전체를 계속할 수 없는 오류는 집계 없이 `FAILED`로 남긴다.

`HeartbeatStopped`는 외부 확인을 시작했지만 임대 갱신이 거절되어 결과를 버린 경우다. 조정자 미시작·후보 예외와 별도로 집계하며, 한 후보는 여섯 결과 중 하나에만 포함한다. heartbeat 저장 예외는 기존 후보 실패 집계를 유지한다. 이 구분은 완료 집계에만 적용하며 예약 상태나 재확인 규칙을 바꾸지 않는다.

Flyway V9는 완료 집계에 nullable `heartbeat_stopped_count`를 추가한다. 기존 완료 기록의 NULL은 별도 집계 없음이며 기존 조정자 미시작 수에 heartbeat 중단이 섞여 있을 수 있다. 이를 0건으로 보정하거나 추정해서 나누지 않는다. 새 Java 완료 저장은 0을 포함한 명시적 개수를 요구한다. DB는 기존 방식의 쓰기도 NULL로 보존하며 합계는 기존 다섯 결과를 기준으로 검사한다. 새 개수가 있으면 여섯 결과 합계를 검사하고, 완료 외 상태에서는 새 열도 NULL이어야 한다. 구버전 조회 코드는 새 합계를 해석하지 못하므로 실제 적용 시 작업자를 중지하고 스키마·코드를 함께 교체해야 한다.

Flyway V4는 `ai_reservation_recovery_work_runs`를 만든다. 실행 시작·완료·실패는 각각 짧은 트랜잭션으로 처리하고 외부 확인 중에는 실행 기록 행을 잠그지 않는다. 같은 실행 ID의 중복만 막으며 서로 다른 실행 ID의 후보 경쟁은 기존 예약 잠금과 활성 임대 제약이 처리한다.

강제 종료로 남은 실행 중 기록은 호출 측이 시작 시각 기준·조회 시각·최대 개수를 제공해 오래된 순서로 읽는다. 조회만으로 상태를 바꾸지 않으며 코드에 자동 만료 기준을 넣지 않는다. 운영자는 한 조회 결과에 포함된 실행을 명시적으로 선택하고, 종료 확인 사유·운영자 식별자·중단 시각을 제공한다. 저장소는 실행 행을 잠근 뒤 여전히 `RUNNING`일 때만 별도 `ABORTED` 상태로 바꾼다. 완료·실패·중단 중 먼저 확정된 종료 결과를 나중 요청이 덮어쓰지 않는다.

Flyway V5는 운영 중단 사유와 운영자 식별자를 추가한다. 실행기 예외로 기록하는 `FAILED`와 운영자 확인으로 기록하는 `ABORTED`를 구분한다. 중단 사유는 프로세스 종료 확인·작업자 응답 없음·운영 판단으로 제한하며 자유 형식 공급자 응답이나 오류 메시지를 저장하지 않는다. 같은 감사 정보의 재전달만 허용하고 다른 중단 정보는 충돌로 남긴다.

완료 집계만으로는 한 실행이 실제로 소유한 예약별 복구 시도를 역추적할 수 없으므로 작업 실행과 새 복구 시도를 직접 연결한다. Flyway V6의 연결 테이블은 시도 ID를 기본 키로 사용해 한 시도를 최대 한 실행에만 연결하고 양쪽 외래 키로 존재하는 기록만 허용한다. 기존 직접 소유권 획득과 호환 경로에서 만든 시도는 실행 ID 없이 유지한다.

실행 조정자를 거친 `Ready` 후보의 시도를 만들 때는 작업 실행 행을 공유 잠금으로 읽어 상태가 `RUNNING`이고 실행 작업자와 임대 소유자가 같은지 확인한다. 시도 생성과 연결 INSERT는 한 트랜잭션에서 커밋한다. 같은 시도 요청을 실행 중인 같은 실행에 재전달하면 기존 연결을 반환하고, 같은 시도 ID를 다른 실행에 붙이거나 연결되지 않은 과거 시도에 소급 연결하지 않는다. 실행이 먼저 종료되면 새 시도를 만들지 않고, 연결 트랜잭션이 먼저 끝나면 해당 시도까지 실행 이력에서 조회할 수 있다.

`ABORTED`는 작업 실행 기록의 운영상 종료이며 이미 생성한 복구 임대·외부 확인·예약 상태를 취소하는 명령이 아니다. 연결된 시도의 상태와 예약의 청구 결과는 기존 임대·펜싱 계약으로 계속 판단한다. 운영 중단을 과금 취소나 공급자 요청 취소로 확대하지 않는다.

수동 검토 재개 저장과 운영 조회 연결, 외부 확인 중 heartbeat 조정 경계는 내부 Java로 구현한다. 관리자 HTTP API·화면·인증·권한, 작업 실행 자체를 시작할 주기 스케줄러, 오래된 실행의 자동 중단·인계는 포함하지 않는다. 기존 `recoverNext`는 호환을 위해 남아 있지만 재확인 정책을 거친 자동 작업 경로로 사용하지 않는다.

## 9. 남은 연결

1. 실제 공급자 상태 조회 어댑터와 작업 실행 스케줄러를 연결하고 확인 근거를 보존한다.
2. 공급자를 선정한 뒤 실제 재확인 간격·최대 시도·임대 길이·heartbeat 주기와 작업 실행 주기를 정한다.
3. 인증·권한을 정한 뒤 내부 조회·운영 중단을 관리자 API·화면과 수동 검토 재개 흐름에 연결한다.
4. 실제 운영 기준을 정한 뒤 오래된 실행 조회 기준과 자동 점검 주기를 정한다.
5. 후보 상태와 정책 개정의 PostgreSQL 저장을 연결한다.

현재 구현은 인공 결과에 대해 복구 경로의 오래된 상태 변경을 막고 만료 이력을 보존하며, 주어진 일정으로 오래된 운영 대상을 제한 조회해 보류·중단 항목을 건너뛰고 `Ready` 후보를 배정·실행한다. 실행 ID의 중복 기동과 후보 결과 집계, 오래된 실행 중 기록의 읽기 전용 조회와 운영 중단 감사 정보, 실행이 만든 예약별 복구 시도 연결, 수동 검토 재개 감사, 활성 임대 갱신 감사와 잠금 후 펜싱도 PostgreSQL에 남긴다. 외부 확인 중 호출 측 스케줄러로 heartbeat를 실행하고 갱신이 거절되면 확인 결과를 폐기한다. 실제 공급자 복구, 운영 주기와 공급자별 heartbeat 값, 자동 실행 중단, 관리자 권한, 서로 다른 실행 ID 사이의 정확히 한 번 실행이나 외부 과금 상한을 보장하지 않는다.
