# 수집 실행·실패·재처리 위치

2026-09-05 후속 구현: [한 페이지 수집과 저장 원본 재처리](../development/limited-policy-collection.md)에 실제 API·PostgreSQL·Spring Batch를 연결했다. 아래는 기존 순수 진행 모델의 설계이며 현재 수집 명령의 전체 구현 범위를 뜻하지 않는다.

## 1. 범위

- 제품 기준은 [PRD 6절](../PRD/0001_product-baseline/spec.md), 실행 책임은 [ADR-0001](../ADR/0001_기술스택과_책임_분리.md)을 따른다.
- 인증키 승인 전에는 호출자가 확인한 페이지 결과를 받는 내부 진행 모델만 만든다. 외부 페이지 번호·커서·정책 식별자 계약을 추정하지 않는다.
- 운영 수집기, 원천 DTO·파서, 실제 원본 저장, Flyway DDL, Spring Batch 실행 연결은 이번 범위가 아니다. 메모리의 반환 상태를 이어 쓰는 것과 프로세스 재시작 후 복구는 다르다.

## 2. 작업 위치와 처리 이력

- 실행은 실행 ID·시작 시각·첫 페이지 내부 참조로 시작한다. 내부 참조에는 URL·인증키·응답 본문을 넣지 않는다.
- 페이지 위치는 페이지 참조, 항목 위치는 페이지 참조와 항목 참조의 조합이다. 항목 참조는 해당 원본 안의 위치이며 정책 ID가 아니다.
- 각 위치는 시작 전 또는 시도 이력을 가진다. 시도는 실행 ID·작업 위치·위치별 시도 번호, 시작 시각과 종료 결과를 보존한다.
- 시도 번호는 [정책 개정 적용](policy-revision-application.md)의 정책별 수집 순번을 대신하지 않는다. 서로 다른 실행에서 같은 정책이 발견될 때의 멱등 처리도 별도로 필요하다.

## 3. 페이지 확정과 부분 실패

- 페이지 성공 결과는 원본 참조, 중복 없는 항목 참조 목록, 다음 페이지 또는 요청 범위의 명시적 종료를 함께 받는다. 빈 항목 목록만으로 종료를 판단하지 않는다.
- 페이지 성공 기록과 항목·다음 페이지 등록은 하나의 상태 변경이다. 같은 실행에서는 성공 페이지의 원본·항목 목록을 교체하지 않는다. 원천을 새로 읽어 전체 목록을 갱신하려면 별도 실행으로 처리한다.
- 다음 페이지가 현재 페이지나 이미 등록된 페이지를 가리키는 순환은 거절한다. 실제 외부 커서의 해석은 향후 원천 어댑터가 담당한다.
- 항목 성공과 검토 필요는 자동 재시도에서 제외한다. 검토 필요는 사람이 확인해야 할 작업이지 기술적 실패의 무한 재시도 대상이 아니다. 사용자 자격의 정보 부족과도 별개다.
- 실패한 페이지·항목은 실패 코드와 확보한 원본 참조를 남긴다. 다른 항목이나 이미 등록된 다음 페이지는 계속 처리할 수 있다. 실패·부분 응답·목록 부재로 정책을 삭제하거나 비공개로 바꾸지 않는다.

## 4. 중단과 재개

- 일시 중단은 진행 중인 시도를 중단 결과로 닫고 새 시도 시작을 막는다. 완료한 결과와 시작하지 않은 위치는 보존한다. 실제 네트워크 요청 취소 기능은 아니다.
- 재개는 새 시도를 허용한다. 재처리 위치 조회는 시작 전·실패·중단 위치만 반환하고 진행 중·성공·검토 필요는 제외한다. 자동 실행·재시도 횟수·대기 시간은 정하지 않는다.
- 이전 시도 또는 중단된 시도의 늦은 결과는 무시한다. 같은 시도의 같은 종료 결과 재전달은 재처리로, 다른 종료 결과는 충돌로 구분하고 기존 기록을 유지한다.
- 실행 상태는 일시 중단 → 재처리 필요 → 진행 중 → 검토 남음/완료 순서로 판별한다. 재처리 필요는 실패가 남았다는 표시이며 다른 위치의 처리 금지가 아니다.
- 명시적 종료를 확인하고 모든 등록 작업이 끝나야 완료 또는 검토 남음이다. 이 완료는 해당 요청 범위의 처리 완료이며 원천 전체의 일관된 스냅샷·정책 삭제의 증거가 아니다.

## 5. 실제 저장·실행 연결 전 조건

1. 원천 성공 응답으로 페이지·종료·식별자·부분 실패 계약을 확인한다. 큰 실행의 조회·처리 크기는 제한하고 API 호출 한도를 준수한다.
2. Spring Batch 실행 저장소와 업무 처리 기록의 역할을 정한다. 이 모델을 별도 스케줄러로 확장하지 않는다. 전체 이력을 매번 메모리에 싣는 방식도 운영 저장 설계가 아니다.
3. 시도 시작은 실행 소유권·임대 또는 버전 비교로 저장한 뒤 외부 작업을 수행한다. 외부 호출 중에는 DB 트랜잭션·행 잠금을 유지하지 않는다.
4. 페이지 결과 저장과 항목·다음 페이지 등록을 원자적으로 처리한다. 항목의 정책 반영과 처리 완료 기록도 같은 트랜잭션 또는 명시적인 멱등 복구 절차가 필요하다.
5. 정책 적용은 현재 개정만이 아닌 최근 처리 순번까지 비교한다. 실행 시도 식별값만으로 정책 개정·알림 중복을 막았다고 판단하지 않는다.
6. 프로세스 종료 후 진행 중 시도 회수, 새 작업자의 이전 결과 차단, DB 재조회, 재처리·최종 성공 실행 조회와 실제 동시성 테스트를 구현한다.

현재 코드와 검증 범위는 [구현 기록](../development/collection-run-progress.md)에 정리한다.
