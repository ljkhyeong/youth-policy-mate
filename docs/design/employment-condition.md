# 취업 조건 비교 범위와 추가 확인 설계

- 정리일: 2026-08-30
- 상태: 단일 취업 사실·답변 비교 구현. 추가 질문 화면·원천 코드 매핑은 아직 없음
- 구현 범위: [단일 취업 조건 비교](../development/employment-condition.md)
- 제품 기준: [PRD 4~5절](../PRD/0001_product-baseline/spec.md#4-조건-입력과-로그인)
- 기존 구현: [비회원 조건 입력](../development/guest-conditions.md), [판정 결과 집계](../development/eligibility-decision.md)
- 조사 근거: 저장소의 [온통청년 조사 기록 5~7절](../research/ontong-api-contract.md#5-공식-코드-정의서에서-확인한-값). 이번 작업에서 외부 자료를 다시 조회하거나 인증된 성공 응답을 확보한 것은 아님

## 1. 현재 입력만으로 가능한 일

`frontend/src/features/conditions/condition-draft.ts`의 `ConditionDraft.employmentStatus`는 문자열 하나다. 화면은 ‘현재 상황에 가장 가까운 항목’을 하나 선택하게 하고 선택값이 목록에 있는지만 검사한다. 겸업·재학·사업자등록·근로시간 등의 사실이나 취업 정보의 별도 기준일은 받지 않는다.

현재 가능한 것은 **사용자가 선택한 주된 상태를 확인 화면에 표시하는 것**이다. 정책별 정의와 기준일을 맞춘 적이 없으므로 선택값만으로 실제 취업 요건의 충족·불충족을 확정할 수 없다. 화면을 연 날짜나 서버에 요청한 날짜도 과거 정책 기준일의 취업 상태를 확인한 증거가 아니다.

## 2. 선택값에서 추정하면 안 되는 것

아래는 현재 화면 값의 해석 한계다. 직업별 법적 정의나 특정 정책의 자격 기준을 정한 표가 아니다. 추가 확인 항목도 모든 사용자에게 수집할 목록이 아니라, 실제 정책 원문이 요구할 때 확인할 후보다.

| 현재 값 | 선택지 | 선택만으로 확인되지 않는 것 |
|---|---|---|
| `EMPLOYED` | 재직자 | 정책이 정한 고용 형태·근로시간·보험 기준, 다른 일의 병행 여부 |
| `SELF_EMPLOYED` | 자영업자 | 사업자등록·휴폐업 여부, 임금근로 병행 여부 |
| `NOT_EMPLOYED` | 미취업자 | 정책별 미취업 정의 충족, 소득·보험·사업자등록 상태, 재학 여부 |
| `FREELANCER` | 프리랜서 | 별도 직장 재직 여부, 사업자등록·소득·근로시간 |
| `DAY_WORKER` | 일용근로자 | 정책이 정한 근무 기간·시간·고용 기준, 다른 일의 병행 여부 |
| `ENTREPRENEUR` | (예비)창업자 | 예비 단계인지 이미 창업했는지, 사업 개시·등록 여부 |
| `SHORT_TERM_WORKER` | 단기근로자 | 계약 기간·근로시간·정책별 취업 인정 기준 |
| `FARMER` | 영농종사자 | 정책에서 요구하는 영농·등록 요건, 다른 일의 병행 여부 |
| `OTHER` | 기타 | 나머지 모든 취업 형태에 비해당한다는 사실, 정책의 ‘기타’ 코드와 같은 의미인지 여부 |

예를 들어 주된 상태로 프리랜서를 골랐다는 이유로 재직 여부를 ‘아니오’로 만들지 않는다. ‘미취업자’를 골랐다는 이유로 대학에 다니지 않는다고 판단하지 않는다. 체크박스 여러 개로 바꾸더라도 **선택하지 않음과 명시적 비해당 답변은 다르다**.

## 3. 자동 비교를 허용할 전제

다음 비교 규칙 중 단일 사실·명시적 답변, 제한 없음과 미해석 처리를 구현했다. 원천 정책을 해석하거나 현재 화면의 주된 상태를 답변으로 바꾸는 코드는 없다. 실제 동작과 검증 범위는 구현 문서를 따른다.

| 확인한 내용 | 해당 항목의 처리 |
|---|---|
| 관련 본문·예외까지 확인한 결과, 취업 상태에 제한이 없음 | 취업 항목만 `MET`. 불필요한 취업 추가 입력을 요구하지 않음 |
| 단일 취업 사실의 정의·요구 방향·기준일이 확인되고, 같은 의미·날짜의 명시적 답변이 요구와 일치함 | `MET` |
| 위 전제를 충족하지만 명시적 답변이 요구와 반대임 | 해당 필수 항목은 `NOT_MET`. 전체 결과에는 남은 예외 검토를 별도로 적용 |
| 정책 해석은 끝났지만 주된 상태만 있거나, 필요한 답변이 누락·모름·다른 기준일임 | `UNKNOWN / MISSING_USER_INPUT` |
| 원천 코드·복수 값 관계·정의·기준일·예외를 해석하지 못함 | `UNKNOWN / UNRESOLVED_POLICY`. 사용자에게 답을 받아도 정책 해석을 대신하지 않음 |

‘요구 방향’은 같은 사실을 정책이 요구하는지 금지하는지다. 예를 들어 확인한 사실에 사용자가 ‘아니오’라고 답해도 정책이 바로 그 비해당을 요구한다면 충족일 수 있다. 답변의 예·아니오를 그대로 충족·불충족으로 복사하지 않는다. 또한 ‘재직하지 않음’을 정책의 복합적인 ‘미취업’ 정의 전체와 같다고 가정하지 않는다.

현재 원천 `jobCd`의 복수 값 표현·결합 방식과 본문 예외의 성공 응답은 확인하지 못했다. 알 수 없는 값·빈 값·파싱 실패를 ‘제한없음’으로 바꾸지 않는다. 코드와 UI의 이름이 같아도 자동 매핑의 근거가 되지 않는다.

여러 상태의 OR/AND나 예외를 아직 해석·지원하지 못했다면 보류한다. OR의 한 항목이 불충족이라는 이유로 전체 불충족을 만들거나, 각 대안을 독립적인 필수 항목으로 집계하지 않는다. 첫 구현 때문에 범용 규칙 엔진을 추가하지 않는다.

## 4. 추가 질문과 답변의 최소 범위

기본 입력은 현재의 주된 상태 하나를 유지한다. 추가 확인이 필요할 때만 실제 정책에서 해석한 사실을 묻는 흐름을 구현 후보로 삼는다. 이 문서에서 질문 목록·UI 선택 방식·REST 필드를 확정하거나 입력 화면을 변경하지 않았다.

질문에는 다음 내용을 함께 보여줘야 한다.

- 어떤 사실을 묻는지와 원문에서 확인한 정의. ‘신청 자격이 되나요?’처럼 자격 판단 자체를 사용자에게 맡기는 질문은 사용하지 않는다.
- 정책에서 정한 기준일. 기준일이 미해석이면 오늘 날짜를 채워 질문하지 않는다.
- 질문이 필요한 이유와 원문 근거. 정책이 특정 기간·시간·등록 여부를 요구할 때만 해당 사실을 추가 확인한다.
- ‘해당함·해당하지 않음·모름’에 해당하는 답변 경로. 미응답을 자동으로 ‘아니오’로 선택하지 않는다.

예시 형식은 ‘[정책 기준일] 기준으로 [원문에서 정의한 사실]에 해당하나요?’다. 대괄호는 실제 원문으로 채워야 할 자리이며 운영 질문이나 가상 정책으로 사용하지 않는다. 필요한 수치·기간을 예·아니오 한 문장으로 정확히 설명할 수 없다면 별도 입력 설계 전까지 보류한다.

질문과 답변이 어떤 조건 정의·정책 개정·기준일에 대한 것인지 구분해야 한다. 서버 내부 `EmploymentFact`·`EmploymentAnswer`가 이 연결을 보존하고 비교하며 DB·REST 계약은 아직 없다. 정의나 날짜가 달라진 질문에 과거 답변을 조용히 재사용하지 않는다. 복수 입력이 충돌할 때 사용자에게 확인하는 흐름은 아직 구현하지 않았으며 임의로 최신값이나 유리한 값을 고르지 않는다.

증빙서류·사업자등록번호·보험 식별번호·주소 이력을 미리 수집하지 않는다. 사용자 답변은 입력 조건 기준 안내에 사용하며 공적 사실 확인으로 표시하지 않는다. 저장과 API 전송은 별도 구현 범위다.

## 5. 기존 결과 모델에 연결할 때

`ConditionAssessment`에는 적용 조건, 비교한 답변과 기준일, 결과·미확인 원인, 이유와 근거를 보존한다. 아직 답변을 받지 않았다면 비교값을 만들어 채우지 않는다. 정책 미해석과 사용자 정보 부족이 함께 있으면 정책 미해석을 먼저 남긴다.

취업 항목이 충족돼도 `PolicyReview`를 자동으로 완료하지 않는다. [조사 사례 A](../research/ontong-api-contract.md#사례-a-학력-코드만-비교하면-놓치는-추가-조건)처럼 대학생 참여 제한이 있으면 재학 조건을 따로 확인해야 한다. 원문의 제한을 해석하지 못한 경우와, 제한은 확인했지만 사용자의 재학 정보를 모르는 경우를 구분한다.

## 6. 구현 시 필요한 대표 검증

다음은 전체 연결 시 필요한 시나리오다. 단일 사실 비교와 기존 집계 연결의 검증은 구현 문서를 따른다. 원천 코드·현재 입력 화면의 변환까지 검증한 목록으로 읽지 않는다.

| 입력·정책 상황 | 확인할 결과 |
|---|---|
| 주된 상태와 정책 코드의 표시 이름만 같음 | 자동 충족하지 않음. 정책 해석 완료 여부에 맞춰 미확인 원인 구분 |
| 프리랜서를 선택했고 정책은 재직 여부를 요구함 | 재직하지 않는다고 단정하지 않고 필요한 정보를 확인 |
| 정책 정의·날짜·요구 방향과 명시적 답변이 일치 / 불일치 | 각각 `MET` / `NOT_MET`와 근거 보존 |
| 해당·비해당 답변 대신 모름·누락 또는 다른 날짜의 답변 | `UNKNOWN / MISSING_USER_INPUT` |
| 알 수 없는 코드·기준일 또는 해석되지 않은 OR·예외 | `UNKNOWN / UNRESOLVED_POLICY`. 다른 항목의 불충족으로 덮지 않음 |
| 취업 제한 없음은 확인했지만 재학 조건의 사용자 정보가 없음 | 취업 항목만 충족, 재학은 정보 부족으로 전체 `NEEDS_REVIEW` |
| 같은 문구라도 정책 개정으로 정의·기준일이 바뀜 | 기존 답변을 확인 없이 재사용하지 않음 |

첫 구현은 **정의·요구 방향·기준일이 확인된 단일 사실과 3가지 답변 상태**의 비교 및 확인한 제한 없음으로 한정했다. 원천 코드 연결과 추가 질문 화면은 분리한다. 실제 자료 없이 취업 분류 전체의 변환표나 수치 기준을 고정하지 않는다.

## 7. 설계와 구현 기록

설계 작업에서는 화면 모델·입력 검사·안내 문구, 기존 집계 모델과 PRD·조사 기록을 대조했다. 당시에는 문서만 바꾸고 앱 테스트를 재실행하지 않았으며, 앞선 49건의 테스트에 취업 비교는 포함되지 않았다.

이후 단일 취업 비교 코드를 추가했다. 구현 모델·명령·실제 검증 결과는 [구현 문서](../development/employment-condition.md#코드와-검증)를 따른다. 추가 질문 화면·원천 코드 매핑·API·DB는 여전히 없다.
