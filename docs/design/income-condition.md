# 소득 조건 비교 범위와 입력 설계

- 정리일: 2026-08-30
- 상태: 구현 전 설계. 소득 입력 화면·비교기·원천 매핑·기준표 저장은 아직 없음
- 제품 기준: [PRD 4~5절](../PRD/0001_product-baseline/spec.md#4-조건-입력과-로그인)
- 기존 구조: [판정 결과 집계](../development/eligibility-decision.md), [정책 데이터 구조](policy-data-model.md)
- 원천 확인 수준: [온통청년 조사 4~5절](../research/ontong-api-contract.md#4-사용할-응답-필드). 인증된 성공 응답은 아직 없음

## 1. 현재 입력과 원천 자료의 한계

`frontend/src/features/conditions/condition-draft.ts`는 생년월일·서울 자치구·주된 취업상태만 받는다. 취업 질문 미리보기도 소득을 받지 않는다. 서버의 `ConditionAssessment`·`EligibilityDecision`은 소득 비교 결과를 담을 수 있지만, 현재 테스트의 소득 항목은 집계를 확인하기 위한 수동 입력이다. 소득을 실제로 계산·비교하는 코드는 없다.

기존 조사에서 소득 필드는 `earnCndSeCd`·`earnMinAmt`·`earnMaxAmt`·`earnEtcCn`이며, 구분 코드는 무관·연소득·기타로 확인했다. 이 필드명과 코드만으로 개인·가구, 소득 정의·연도·경계·빈 값 의미를 확정하지 않는다. 코드 정의서를 이번 작업에서 다시 내려받지는 않았다.

2026-08-30에 [온통청년 검색 화면](https://www.youthcenter.go.kr/youthPolicy/ythPlcyTotalSearch)의 연소득 입력이 만원 단위의 이상·이하 범위로 표시되는 것을 확인했다. 이는 검색 UI 관찰이다. Open API 응답의 금액 단위와 모든 정책의 포함 경계를 확인한 증거는 아니다.

## 2. 비교 전에 일치시킬 의미

아래는 구분해야 할 정보이며, 모든 사용자에게 입력받을 항목 목록이나 확정 DTO가 아니다. 원문에서 정할 정보와 사용자가 답할 정보를 분리한다.

| 구분 | 정책·입력에서 맞출 내용 | 추정하면 안 되는 것 |
|---|---|---|
| 소득 대상 | 본인 또는 정책이 정한 가구의 소득 | 본인 소득을 가구 소득으로 사용하거나, 주소가 분리됐다고 무조건 1인 가구로 판단 |
| 금액의 정의 | 원문이 정한 소득 항목·포함/공제 방식·세전/세후 등 | 월급·매출·소득인정액·건강보험료를 같은 금액으로 비교 |
| 금액 단위 | 원·만원 등 명시된 단위와 필요한 소수 처리 | 숫자 크기만으로 단위를 추측하거나 반올림으로 경계를 변경 |
| 대상 기간 | 특정 월·연간·평균을 구하는 기간과 산정 방식 | 현재 월 소득 × 12를 전년도 연소득으로 사용 |
| 적용 기준 | 기준표 종류·연도·개정과 원문에서 정한 기준일 | 판정한 날의 연도나 최신 표를 모든 정책에 적용 |
| 가구 조건 | 정책의 가구원 범위·산정 시점, 필요한 가구원 수·유형 | 주민등록 가구와 다른 기준의 가구를 자동으로 동일시 |
| 허용 범위 | 하한·상한, 각각의 이상/초과·이하/미만, 명시적인 한쪽 제한 없음 | 빈 상한을 무제한으로, 빈 하한을 0원으로 처리 |
| 사용자 값 | 위 의미를 확인한 금액 또는 구간, 미응답·모름 여부 | 선택 구간의 중간값·하한·상한 중 임의의 값으로 판정 |

가구 관련 정보는 정책이 요구할 때만 필요하다. 본인 소득 조건에 불필요한 가구원 수를 요구하지 않는다. 반대로 가구 정의나 표 적용에 필요한 가구원 수가 없는데 본인 금액만으로 가구 조건을 비교하지 않는다.

원·만원은 양쪽 단위가 확인됐을 때 정확히 변환할 수 있지만, 월·연 환산은 대상 기간과 계산 방식까지 같다는 뜻이 아니다. 첫 비교기에서는 월·연 환산, 세전·세후 변환, 소득 산정·공제 계산을 하지 않는다.

## 3. 공식 공고에서 확인한 보류 사례

[서울시 공고 제2026-1109호, 청년 부동산 중개보수 및 이사비 지원사업 모집 공고](https://soco.seoul.go.kr/bos/cmmn/file/fileDown.do?atchFileId=12817e11dea24565ae8f7a84b98175db&bbsId=&fileSn=1&menuNo=400018) 2쪽을 확인했다. 2026-04-01 공고의 상반기 모집 자료이며, 하반기 개정이나 현재 신청 가능 여부까지 확인한 것은 아니다.

- 이 공고는 특정 월인 2026년 3월의 건강보험료 고지금액과 해당 연도의 기준표를 사용한다.
- 피부양자는 주민등록이 분리돼 있어도 부양자 고지금액을 기준으로 삼는 설명이 있다.
- 기준표는 가구원 수와 직장·지역 가입 구분에 따른 보험료를 나누며 장기요양보험료 제외 조건을 명시한다.

설계 결론: 일반 소득 구간이나 현재 본인 월급을 이 보험료로 바꿔 비교하지 않는다. 별도 방식이 구현되지 않은 동안에는 `UNRESOLVED_POLICY`로 보류하고 미지원 계산 방식과 근거를 남긴다. 필요한 값을 받을 준비가 되지 않았는데 가족별 금액·보험 정보를 먼저 수집하지 않는다.

이 공고는 판정 방식의 차이를 확인하는 참고 자료다. 온통청년 정책번호·API 응답과 연결하지 않았고, 금액표를 코드나 DB에 복사하지 않았다. 온통청년 외 사이트를 제품 수집원으로 추가한 것도 아니다. 이 사례 하나로 전체 소득 정책을 대표하거나 자동 판정 가능 비율을 계산하지 않는다.

## 4. 첫 비교기의 구현 범위

첫 구현은 **같은 정의·대상·기간으로 확인한 금액 구간과 정책의 명시적인 허용 구간 비교**로 제한한다. 내부 비교 모델이며 화면에서 모든 사용자에게 정확한 소득을 새로 요구한다는 뜻은 아니다.

1. 원문과 예외에서 확인한 소득 정의, 개인·가구 범위, 대상 기간·적용 기준, 필요한 가구 조건을 하나의 비교 기준으로 묶는다. 이 정보를 모르면 비교 가능한 조건을 만들지 않는다.
2. 정책 ID·개정·조건 ID와 그 비교 기준에 사용자 값을 연결한다. 정책·정의·기간·적용 기준·필요한 가구 조건이 달라진 값을 현재 입력으로 재사용하지 않는다.
3. 정책과 사용자 범위는 각 끝값의 포함 여부를 보존한다. 정확한 금액은 양 끝이 같은 포함 구간으로 표현할 수 있다. 한쪽 제한 없음은 명시적으로 확인한 경우에만 사용한다.
4. 비교에는 단위가 확인된 원화 금액을 사용하고 원문의 단위·경계와 변환 근거를 남긴다. 소수·반올림 규칙이 해결되지 않았으면 임의의 오차 허용값을 두지 않는다.
5. 사용자 구간 전체가 정책 범위에 들어가면 `MET`, 두 범위가 겹치지 않으면 `NOT_MET`, 일부만 겹치면 `UNKNOWN / MISSING_USER_INPUT`으로 처리한다. 0원은 같은 정의·기간에 명시적으로 답한 값일 때만 금액으로 사용한다.
6. 관련 본문·예외까지 확인한 소득 제한 없음은 소득 항목만 `MET`으로 처리한다. 비교할 필요 없는 금액 입력을 요구하거나 결과에 복사하지 않는다.

잘못된 구간도 구분한다. 원천의 역전된 상·하한이나 모순된 경계는 정책 미해석이다. 사용자가 잘못 입력한 구간은 입력 오류로 안내하며 자격 불충족으로 바꾸지 않는다. 무응답·모름·빈 문자열은 금액 0 또는 한쪽 무제한을 뜻하지 않는다.

중위소득 비율·건강보험료·소득인정액 산정, 기준표 조회, 월·연 환산, 여러 조건의 OR/AND와 원문 예외 해석은 첫 구현에서 제외한다. 이런 자료를 숫자 하나로 축소해서 일반 구간 비교기에 넣지 않는다. 지원하지 않는 방식을 표현하려고 범용 수식 엔진이나 임의 코드 실행을 추가하지 않는다.

## 5. 기존 결과 모델에 연결하는 순서

| 조건 | 소득 항목 결과 |
|---|---|
| 정의·단위·기간·표·예외를 확정하지 못했거나 계산 방식을 지원하지 않음 | `UNKNOWN / UNRESOLVED_POLICY` |
| 정책은 비교 가능하지만 사용자 값 누락·모름·다른 기준의 값만 있음 | `UNKNOWN / MISSING_USER_INPUT` |
| 같은 기준의 사용자 구간이 정책 범위에 일부만 겹침 | `UNKNOWN / MISSING_USER_INPUT`. 더 좁은 구간 확인이 필요하다고 안내 |
| 같은 기준의 사용자 구간 전체가 범위 안 / 범위와 겹치지 않음 | 각각 `MET` / `NOT_MET` |
| 관련 본문·예외까지 소득 제한 없음이 확인됨 | 소득 항목만 `MET` |

정책 미해석을 먼저 처리한다. 사용자에게 금액을 받아도 원문 해석을 대신할 수 없다. 소득 항목이 충족돼도 `PolicyReview`를 자동 완료하지 않으며 재산·중복수혜 등 다른 조건은 별도로 확인한다. 기존 집계 순서대로 정책 미해석이 있으면 전체 `NEEDS_REVIEW`, 정책 검토가 끝났고 명확한 불충족이 있으면 다른 사용자 정보 누락보다 불충족이 우선한다.

결과에는 정책 개정·규칙 버전, 적용 범위·정의·단위·대상 기간·필요한 가구 조건, 비교한 구간과 미확인 이유·근거를 보존한다. `ConditionAssessment.referenceDate`는 날짜 하나이므로 소득 연도·평균 대상 기간·기준표 연도를 대신 담지 않는다. 실제 기준일이 없으면 빈 값으로 두고 기간·표 정보는 조건 설명에 보존한다. 기계가 재사용할 기간 입력 모델은 비교기 구현 때 정하며, 설명 문자열을 다시 파싱하지 않는다.

## 6. 추가 입력과 개인정보

- 정책 원문에서 정한 비교 대상·기간·단위와 입력이 필요한 이유를 먼저 안내한다. 계산 방법을 모르는 상태에서 ‘소득이 기준에 맞나요?’라는 질문으로 판정을 사용자에게 떠넘기지 않는다.
- 구간이 경계에 걸치면 필요한 범위만 더 좁혀 확인한다. 정확한 금액 입력을 기본 조건으로 승격하거나 공개 탐색을 막지 않는다. 모름·미응답은 그대로 남긴다.
- 가구 조건이 필요하다고 가족 이름·주민등록번호·보험 식별번호·가족별 소득·증빙서류를 일괄 수집하지 않는다. 현 단계에서 소득 입력·API·저장 기능을 추가하지 않는다.
- 정책 개정·질문 기준이 달라지면 기존 답변을 새 기준으로 다시 감싸지 않는다. 새 질문에 대한 확인이 필요하다. 입력 간 충돌이 있으면 유리한 값이나 최신값을 임의로 고르지 않는다.
- 향후 소득 비교값을 공개 캐시·공유 미리보기·로그·분석 이벤트·AI 요청에 넣지 않는다. 소셜 로그인이나 사용자 진술을 공식 소득 확인으로 표시하지 않는다.

## 7. 구현 때 필요한 대표 검증

다음은 향후 테스트 시나리오이며 통과한 테스트 목록이 아니다. 금액 예시는 실제 기준표 대신 명시적으로 구분한 인공 값으로 구성한다.

| 시나리오 | 확인할 결과 |
|---|---|
| 정확한 금액이 상한과 같음: 이하 / 미만 조건 | 각각 충족 / 불충족, 하한도 이상·초과 방향을 확인 |
| 사용자 구간이 정책 범위에 모두 포함 / 전부 밖 / 일부 겹침 | 각각 충족 / 불충족 / 사용자 정보 부족 |
| 두 구간의 끝값만 같고 포함·제외 조합이 다름 | 실제 겹침 여부를 구분하며 반올림하지 않음 |
| 개인·가구, 소득 정의·금액 단위·대상 기간·개정 중 하나가 다름 | 맞는 사용자 값이 없으면 정보 부족, 정책 기준 자체가 모호하면 정책 미해석 |
| 명시적 0원 / 미입력·모름 / 잘못된 사용자 구간 | 금액 비교 / 정보 부족 / 입력 오류를 구분 |
| 명시적인 한쪽 제한 없음 / 원천 끝값 누락 | 비교 가능 / 정책 미해석을 구분 |
| 필요한 가구 조건 또는 기준표 연도 미확인 | 입력 부족과 정책 미해석을 원인에 따라 구분 |
| 보험료 기준 공고에 현재 월급만 전달하거나 비율을 금액으로 사용 | 미지원 방식은 정책 미해석, 일반 구간 비교에 넣지 않음 |
| 소득 무관 코드와 본문 제한 충돌, 소득 충족과 다른 예외 미해석 | 전체 신청 가능으로 만들지 않음 |
| 같은 기준·입력으로 재평가, 조건 정의·기간·개정 변경 | 같은 결과·근거 보존 / 이전 입력의 조용한 재사용 차단 |

## 8. 이번 작업과 다음 구현

이번에는 PRD의 기존 미확인·최소 입력 원칙을 구체화하고 설계 문서만 변경했다. 현재 입력·집계 코드와 공식 공개 자료를 대조했으며, 소득 비교기·화면·API·DB·금액표는 만들지 않았다. 단위 테스트·빌드는 다시 실행하지 않았고 기존 서버 70건·웹 12건의 통과 기록을 소득 비교 검증으로 확대하지 않는다.

다음 작업은 정의·대상·기간과 양 끝의 포함 여부가 확인된 단일 소득 구간 비교기를 순수 Java로 구현하는 것이다. 제한 없음·정책 미해석·사용자 정보 부족을 기존 집계에 연결하고, 이 문서의 대표 경계만 검증한다. 원천 매핑·기준표 산정·실제 입력 UI는 분리한다.
