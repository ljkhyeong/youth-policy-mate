# 정책 개정에 연결한 AI 후보의 수용·재사용

## 1. 범위와 기준

[PRD 5.2·6.2·8절](../PRD/0001_product-baseline/spec.md)의 AI 보조 책임과 실패 시 원문 유지 기준을 따른다. [정책 개정 모델](policy-revision-application.md)이 제공하는 현재 적용 개정을 읽고, AI 결과 참조를 현재 후보로 보존할 수 있는지만 계산한다.

이 단계에는 AI 공급자·모델 선택, 프롬프트·응답 파싱, 실제 원문 전송, 후보 본문 저장, 자동 공개·자격 규칙 승격, 과금·호출 제어가 없다. 원천 DTO·Flyway DDL도 만들지 않는다. 테스트는 인공 참조 값만 사용한다.

## 2. 서로 다른 버전과 식별값

| 값 | 의미 |
|---|---|
| 정책 적용 개정 | 내부 정책 ID·개정 번호와 개정을 만든 원본·비교 내용·수집 순번·확인 시각. 기존 `AppliedRevision`을 사용 |
| 작업 종류 | 요약과 조건 후보 추출. 서로 다른 후보로 관리 |
| 생성 방식 버전 | 호출 측이 지정한 프롬프트·모델 설정·출력 형식·후처리 계약의 버전. 문자열의 같음만 비교 |
| AI 요청 순번 | 한 정책·작업 종류 안에서 재시도·개정·생성 방식 변경을 거쳐 계속 증가. 응답 도착 전에 발급 |
| 결과 참조 | 후보 결과의 내부 식별자와 본문 해시. 실제 본문·원문 근거 구간이나 저장 완료 증명은 아님 |

정책 수집 순번, 수집 작업의 시도 번호와 AI 요청 순번을 혼용하지 않는다. 같은 내용 재수집은 현재 적용 개정과 그 원본을 유지하므로 기존 AI 후보를 재사용할 수 있다. 최신 정상 수집 원본으로 요청 근거를 바꿔 끼우지 않는다. A→B→A로 돌아온 내용은 새 개정이며 처음 A의 후보를 자동 재사용하지 않는다.

내부 참조에는 요청 URL·토큰·사용자 개인정보를 넣지 않는다. 이 모델은 마지막 처리 결과와 마지막 정상 후보만 보존하며 전체 요청·거절·실패 이력 저장소가 아니다.

## 3. 결과 수용 순서

호출 측은 저장소에서 읽은 현재 정책과 해당 종류의 최신 예정 요청을 함께 제공해야 한다. AI 응답 안의 자기 설명을 최신 요청으로 믿지 않는다. 예정 요청에는 실제 외부 호출을 했다는 의미가 없다.

1. 정책 ID·작업 종류가 다른 결과는 입력 오류로 거절한다.
2. 현재 적용 개정이 없으면 후보를 수용하지 않는다.
3. 예정 요청과 결과 요청 각각의 개정 번호·원본 근거가 현재 적용 개정과 같은지 확인한다. 다르면 기존 상태를 유지한다.
4. 결과의 생성 방식 버전이 예정 요청과 다른지, 요청 순번이 낮거나 아직 발급하지 않은 순번인지 구분한다. 같은 순번에 다른 요청 시각 등 요청 정보가 붙어도 충돌이다.
5. 이미 처리한 순번보다 낮은 결과는 무시한다. 같은 순번·동일 결과(확인 시각 포함)는 재전달이며, 다른 결과는 충돌로 남기고 교체하지 않는다.
6. 더 높은 정상 결과는 마지막 처리 결과와 후보를 함께 갱신한다. 실패·잘못된 출력·한도 보류 결과는 마지막 처리만 갱신하고 기존 후보와 정책은 변경하지 않는다.

기록한 실패를 같은 순번의 성공으로 바꾸지 않는다. 실제 재시도는 새 요청 순번을 사용하며, 실패·한도 소진의 자동 재시도는 이번 모델이 결정하지 않는다. 거절 결과의 전체 감사 이력도 별도 저장 책임이다.

## 4. 현재 후보 조회와 실패 대체

- 현재 후보 조회는 매번 현재 정책 개정과 사용할 생성 방식 버전을 받는다. 마지막 성공 후보가 이 기준과 일치할 때만 반환한다.
- 같은 개정·생성 방식의 새 요청이 실패하면 이전 성공 후보를 재사용할 수 있다. 마지막 실패 결과도 별도로 남아 성공한 것처럼 덮지 않는다.
- 개정·생성 방식이 바뀌면 이전 후보 참조는 기록에 남아도 현재 후보 조회에는 나오지 않는다. 변경 전 요약을 최신 요약으로 표시하지 않는다.
- 원천 수집 실패로 기존 정책 개정을 유지한 경우 그 개정의 후보도 유지할 수 있다. 원천 최신 확인 실패 안내는 수집 상태의 별도 책임이다.
- 후보 없음·실패·한도 보류가 정책 원문이나 기존 규칙 판정을 지우지 않는다. `Generated`는 후보 참조를 받았다는 뜻일 뿐, 요약 정확성·조건 해석·자격을 검증했다는 뜻이 아니다.

## 5. 실행·복구 결과를 후보 검사로 넘기는 경계

AI 실행과 미완료 예약 복구는 비용 상태와 AI 응답 상태를 함께 다루지만, 후보 검사는 응답 본문 참조가 확인된 결과만 받는다.

- 정상 실행의 `Responded`는 청구 확정 여부와 관계없이 후보 검사에 전달할 수 있다. 청구 대기는 예약액을 유지하는 비용 상태이며 AI 응답의 존재를 부정하지 않는다.
- 결과 미확인 실행과 실행 전 중단은 후보 검사에 전달하지 않는다.
- 복구에서는 `ResponseFound`만 후보 검사 대상이다. 확인된 청구·무과금·호출 전 중단처럼 비용 사실만 복구한 결과는 AI 응답을 찾았다는 증거가 아니다.
- `ResponseFound`도 활성 복구 시도에서 `CHECK_COMPLETED`로 적용된 뒤에만 후보 검사에 전달한다. 만료된 임대, 변경된 예약, 수동 검토 결과를 후보로 사용하지 않는다.
- 전달받은 결과는 다시 현재 정책·최신 예정 요청과 비교한다. 복구 성공 시각이 늦더라도 이전 개정이나 다른 요청의 결과를 현재 후보로 바꾸지 않는다.

후보 검사 결과는 아직 메모리의 다음 상태일 뿐 DB 반영이 아니다. 실제 저장에서는 정책 개정·최신 예정 요청·마지막 처리 순번을 같은 트랜잭션에서 다시 확인해야 한다.

## 6. 실제 연결 전 조건

정책과 최신 요청을 다시 조회한 뒤 짧은 트랜잭션에서 결과를 반영한다. 저장 시 정책 개정·예정 요청·마지막 처리 순번을 비교해야 한다. 순수 모델은 동시 작업자의 DB 갱신이나 오래된 조회 상태로 저장하는 문제를 막지 못한다.

공급자 연결 전에는 생성 방식 버전 관리, 정책 원문과 출력의 근거 구간, 출력 검증, 원문 내 지시문 처리, 개인정보 제외, 비용 사전 한도와 결과 미확인 처리를 정한다. 생성 방식 변경을 이유로 변경 없는 모든 정책에 AI를 자동 재실행하지 않는다. 재사용 불가 판정과 유료 요청 승인은 별개다.

후속 [AI 요청 전 판단](ai-request-admission.md)에서 후보 재사용·명시적 재시도·주어진 예산과 최대 비용을 검사한다. 예약 필요 결과를 반환하는 내부 모델이며 실제 요청 예약·정산·과금 차단은 아직 없다.

실제 외부 호출·후보 표시·가능한 규칙 판정 유지까지 검증하기 전에는 PRD AC-06·AC-11 완료로 보고하지 않는다. [후보 모델 구현 기록](../development/policy-ai-candidates.md)과 [실행·복구 결과 연결 기록](../development/policy-ai-candidate-projection.md)에서 현재 범위를 구분한다.
