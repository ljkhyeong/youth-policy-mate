# 정책 수집·판정 데이터 구조 초안

- 상태: 원천 데이터·저장 구조 설계 초안. 2026-09-05에 목록·상세 성공 응답을 확인하고 V10의 소량 정책 저장·조회 테이블을 추가했다. 현재 구현은 [정책 조회 안내](../development/policy-catalog.md)를 따른다. 아래 내용은 자동 수집·판정까지 포함한 설계 초안이다. AI 예산·요청 예약 테이블은 이 초안과 별도로 구현했다. 독립적인 [판정 결과 집계](../development/eligibility-decision.md), [연령](../development/age-condition.md)·[거주](../development/residence-condition.md)·[단일 취업](../development/employment-condition.md)·[소득 구간](../development/income-condition.md) 비교기와 [개정 적용 판단](../development/policy-revision-application.md)은 순수 모델로 구현
- 제품 기준: [PRD-0001](../PRD/0001_product-baseline/spec.md)
- 기술 기준: [ADR-0001](../ADR/0001_기술스택과_책임_분리.md)
- 조사 근거: [온통청년 API 계약 조사](../research/ontong-api-contract.md)

## 1. 먼저 분리할 데이터

원본, 사용자에게 보여주는 정책 개정, 개인별 판정은 같은 데이터가 아니다. 조회수만 바뀐 원본은 보관 근거가 될 수 있지만 새로운 자격 판정이나 정책 변경 알림을 만들 필요는 없다.

| 데이터 | 필요한 값의 후보 | 책임 |
|---|---|---|
| 정책 식별 | 내부 ID, 원천명, 원천 정책번호, 현재 적용 개정 ID, 마지막 정상 확인 시각 | 제목이 바뀌어도 같은 원천 정책을 식별. `(원천명, 원천 정책번호)` 중복 방지 |
| 수집 실행·항목 결과 | 실행 ID, 요청한 페이지·필터, 시작·완료 시각, 항목별 결과·오류 분류, 완전 수집 여부 | 부분 실패·재실행·누락을 추적. 인증키나 키가 포함된 URL은 저장하지 않음 |
| 원본 스냅샷 | 원천 정책번호, 수집 실행 ID, 원문 보관 위치, 응답 내용 해시, 수집 시각, 원천 수정시각 원문 | 정규화 오류와 변경 근거를 다시 확인. 원문 저장 방식·보관 기간은 운영 설계에서 확정 |
| 적용 정책 개정 | 내부 개정 번호, 원본 참조, 정규화 버전, 표시 내용, 조건 원문과 해석 결과, 신청기간, 사업기간 | 판정·일정·변경 알림이 참조하는 정책 내용의 버전 |
| AI 파생 결과 | 적용 정책 개정, 요약·추출 버전, 결과·근거, 처리 상태 | 원본 또는 확정 규칙을 대신하지 않는 보조 결과. 오래된 결과의 적용 방지 |
| 개인별 판정 결과 | 정책 개정, 규칙 버전, 평가 시점·기준일, 결과, 항목별 이유·근거 | 입력 조건 기준 안내. 영구 저장 여부·기간은 개인정보 정책 결정 후 확정 |

위 표의 각 행을 무조건 별도 테이블·서비스로 만들지는 않는다. 첫 구현에서는 실제 조회·변경 책임에 필요한 구조만 만든다. 회원, 관심 정책, 알림 Outbox의 상세 DDL은 이번 초안의 범위 밖이다.

페이지·항목의 시도, 부분 실패와 재처리 위치는 [한 페이지 수집](../development/limited-policy-collection.md)과 [범위 수집](../development/policy-range-collection.md)을 따른다. 실제 API·DB 원본·항목 이력·Spring Batch를 연결했으며, 저장 원본 재처리·지정 범위 순회·설정 기반 정기 실행을 제공한다.

AI 파생 결과의 개정·원본·생성 방식·요청 순번은 [AI 후보 설계](policy-ai-candidates.md)와 [내부 모델 구현](../development/policy-ai-candidates.md)을 따른다. 후보 참조의 수용·재사용만 확인하며 실제 AI 호출·본문 검증·자격 규칙 승격·저장은 아직 없다.

## 2. 정규화한 정책의 묶음

| 묶음 | 내용 | 원천의 주요 근거 |
|---|---|---|
| 표시 정보 | 제목·지원 내용·분류·기관·공식 링크 | `plcyNm`, `plcySprtCn`, 기관 필드, URL 필드 |
| 지역 조건 | 코드 목록과 원문, 해석 가능 여부 | `zipCd`와 자격 관련 본문 |
| 연령 조건 | 제한 여부·최소·최대·나이 정의·기준일·예외 | 연령 필드와 자격 관련 본문 |
| 취업·학력·소득 조건 | 비교 가능한 값, 단위·관계·예외, 미해석 이유 | 코드·금액 필드와 추가사항·참여제한·신청절차 |
| 신청기간 | 원문, 특정기간/상시/마감/미확인, 확인된 기간 목록 | `aplyPrdSeCd`, `aplyYmd`와 관련 본문 |
| 사업기간 | 원문, 시작·종료 날짜 또는 기타 내용 | `bizPrd*` 필드 |
| 안내·근거 | 신청절차, 서류 안내, 확인해야 할 본문, 출처와 확인 시각 | 관련 설명 필드와 원본 스냅샷 |

현재는 복수 기간이 실제 API에서 어떤 형식으로 오는지 확인하지 못했다. 날짜 문자열을 바로 `LocalDateTime` 하나로 고정하지 않는다. 값이 없는 것, 해석하지 못한 것, 제한이 없다고 명시된 것을 구분한다.

## 3. 조건과 결과의 표현

개별 조건에는 원천 필드명·관련 본문, 파싱한 값, 해석 상태와 근거를 연결한다. 판정기는 해당 근거를 적용해 충족·불충족·미확인 결과를 낸다. HTTP 오류·AI 처리 실패·자료 누락은 곧바로 사용자 자격 불충족이 되지 않는다.

- 신청 가능: 필요한 조건과 예외를 모두 확인했고 충족한 경우다.
- 조건 불충족: 명확하게 적용되는 조건을 충족하지 못하고, 그 판단을 바꿀 미해석 예외가 없는 경우다.
- 추가 확인 필요: 필요한 사용자 정보·기준일·신청 주체·예외를 판단할 수 없는 경우다.

개별 조건의 해석 가능 여부와 최종 자격 상태를 같은 Boolean 하나로 저장하지 않는다. 서버 내부의 항목·전체 결과 enum과 집계는 [자격 판정 결과 구현](../development/eligibility-decision.md)을 따른다. 이 내부 모델은 원천 DTO·DB 구조·확정 REST 계약이 아니며, 전송 필드는 API를 구현할 때 정한다.

[결과·근거 표시 컴포넌트](../development/eligibility-result-preview.md)는 별도로 구현했다. 개발 전용 인공 자료로 전체 상태·항목·정책 검토 이슈·모집 안내를 표시하며 화면에서 자격 상태를 다시 계산하지 않는다. 서버 API·실제 정책·저장 구조와 연결한 것은 아니다.

취업 조건은 [입력 의미와 추가 확인 설계](employment-condition.md)를 따른다. 화면의 주된 상태, 정책이 정의한 취업 사실, 해당 사실에 대한 사용자 답변을 구분하며 코드 이름의 일치나 미선택을 충족·불충족 근거로 사용하지 않는다. 단일 취업 비교와 [개발 전용 질문 미리보기](../development/employment-question-preview.md)는 각각 구현했지만 실제 정책 연결·원천 코드 매핑·답변 저장 구조는 아직 없다.

소득 조건은 [입력 의미와 구간 비교 설계](income-condition.md)를 따른다. 개인·가구, 금액 정의·단위·기간·필요한 가구 조건이 맞아야 비교하며 금액 구간의 포함 경계를 보존한다. [명시적 원화 구간 비교](../development/income-condition.md)와 [개발 전용 질문 미리보기](../development/income-question-preview.md)는 각각 구현했다. 정책 범위와 일부만 겹치는 입력을 대표 금액으로 확정하지 않는다. 실제 정책·화면 판정 연결, 기준표 조회·보험료 산정·원천 매핑과 저장 구조는 아직 없다.

공개 사례 A처럼 코드와 추가사항이 다르면, 근거 없이 어느 쪽을 지우지 않는다. 충돌 또는 추가 제약이 해결될 때까지 추가 확인으로 남긴다. 사례 B의 동아리 요건을 확인하기 위해 단체 회원이나 별도 개인정보 입력 기능을 이번 단계에서 추가하지 않는다.

## 4. 원본 변경과 적용 개정

1. 원천 정책번호로 정책을 찾고 수집 실행·원본을 연결한다.
2. 표시 가능한 필수 정보가 깨졌으면 기존 정상 개정을 유지하고 해당 수집 항목을 예외로 기록한다.
3. 정규화 결과의 의미 있는 내용을 비교한다. 조회수·수집 시각만 다른 경우 적용 개정을 늘리거나 변경 알림을 만들지 않는다.
4. 자격·신청기간·신청 링크·지원 내용처럼 사용자 행동에 영향을 주는 내용이 바뀌면 새 개정을 적용한다. 변경 필드 목록도 남긴다.
5. 판정과 일정·미발송 알림을 최신 개정으로 갱신한다. 늦게 도착한 이전 개정의 AI 결과·알림 작업은 현재 개정에 적용하지 않는다.

원본 해시와 정규화한 내용의 해시는 용도가 다르다. 둘 모두 개정의 선후관계를 나타내지는 않는다. `lastMdfcnDt`의 정확도·시간대·보장을 검증하기 전에는 그것 하나로 동시 실행 결과의 순서를 정하지 않는다. 초기에는 중첩 수집을 제한하고 정책 적용 시 기대한 현재 개정이 맞는지 확인하는 방식을 검토한다.

재수집으로 같은 변경이 반복 반영되지 않아야 한다. 반대로 실제 내용이 A→B→A로 돌아온 경우 마지막 A는 새로운 변경일 수 있으므로 정책 전체 이력에 내용 해시를 전역 유일키로 두지 않는다.

인증키 없이 진행할 내부 적용 규칙과 실제 저장의 원자성 조건은 [원본 확인과 정책 개정 적용 경계](policy-revision-application.md)에 구분했다. 원본 참조·비교 내용·내부 수집 순번으로 한 항목의 다음 상태를 계산하는 범위이며, 원천 DTO·저장 DDL·수집기 확정은 아니다.

## 5. 시간·모집 상태·알림

- 날짜만 확인되면 날짜로 보관한다. 시각까지 있는 경우 원천 시각·시간대를 확인해 별도 표현한다.
- 신청기간과 사업기간은 별개다. 사업 종료일을 신청 마감일로 보충하지 않는다.
- 모집 상태는 개인 자격과 별도로 계산한다. 마감한 정책도 자격 조건 비교 근거는 유지할 수 있지만 현재 신청 가능한 것처럼 안내하지 않는다.
- 날짜 충돌·미확인·상시 정책에는 가짜 마감일을 만들지 않는다. 확인된 신청 마감에만 PRD의 D-7·D-3·D-1 규칙을 적용한다.
- 실제 발송 시각과 재시도 만료 기준은 아직 확정하지 않았다.

[모집 기간 설계](recruitment-period.md)에 따라 확인된 단일 날짜·시각 범위와 상시·소진 시 종료·명시적 마감·미확인을 구분하는 [서버 모델](../development/recruitment-period.md)을 구현했다. 날짜형은 서울 달력 날짜만 비교하며 정확한 접수 시각을 보장하지 않는다. 복수 차수·혼합 정밀도·충돌 원문은 아직 해석하지 않으며 실제 수집·화면·알림과 연결하지 않았다.

정책 모듈의 마감 날짜를 사용하는 [D-7·D-3·D-1 후보 계산](../development/deadline-reminder-candidates.md)도 구현했다. 지난 후보 날짜를 제외하고 오늘 후보는 발송 시각 확인 필요로 남긴다. 원본 마감·정책 개정·근거는 보존하며 실제 저장·예약·발송이나 기존 예약 취소를 구현한 것은 아니다.

## 6. 구현을 시작하기 전에 닫을 항목

- 실제 성공 JSON의 목록 경로와 목록·상세 간 필드 차이
- 정책번호의 범위, 복수 코드·널·날짜 형식, 필드명 대소문자 차이
- 지역 필터의 전국·시·자치구 포함 의미
- 페이지 정렬·중복·누락 가능성과 수정·삭제 신호
- 허용 호출량과 개인정보를 포함할 수 있는 원문·판정 자료의 보관 기준

이 항목을 확인한 뒤 첫 구현은 **정책 몇 건 수집 → 원본과 현재 개정 저장 → 공개 목록·상세 → 명확한 조건의 근거 표시** 순서로 제한한다. 아직 모르는 원천 계약을 임의의 성공 응답이나 운영 DB 제약으로 고정하지 않는다.
