# 원본 확인과 정책 개정 적용 경계

- 상태: 내부 적용 규칙을 순수 모델로 구현. 원천 계약·저장 DDL·운영 수집기는 미확정
- 기준: [PRD 6절](../PRD/0001_product-baseline/spec.md#6-정책-수집공개변경-처리), [데이터 구조 초안](policy-data-model.md), [ADR-0001](../ADR/0001_기술스택과_책임_분리.md)
- 구현·검증: [정책 개정 적용 판단 모델](../development/policy-revision-application.md)

## 1. 인증키 없이 구현할 범위

현재 온통청년 성공 응답·정책번호 범위·수정시각·삭제 신호·보관 기준은 확인하지 못했다. 따라서 원천 DTO·파서·Flyway DDL은 만들지 않는다. 먼저 **한 정책의 현재 상태와 수집 결과 하나를 받아 적용 여부와 다음 상태를 계산하는 순수 Java 모델**만 구현한다. 입력은 테스트의 인공 값이며 DB·HTTP·스케줄러에 연결하지 않는다.

이 모델은 정책 식별자·원본 참조·비교 식별값을 발급하거나 검증된 원천 자료로 승격하지 않는다. 미래 수집기는 성공 계약을 확인한 뒤 이 입력을 만들어야 한다. 정책 번호와 제목의 매핑, JSON 정렬·공백 처리와 의미 비교 대상 필드는 이 단계에서 정하지 않는다.

## 2. 서로 다른 식별과 시간

| 값 | 의미 | 대신할 수 없는 값 |
|---|---|---|
| 내부 정책 식별자 | 호출 측이 이미 식별한 한 정책 | 미확인 원천 정책번호 계약 |
| 원본 참조 | 원천명·스냅샷 식별자·원본 SHA-256 | 원문 자체·저장 완료 증명 |
| 비교 내용 식별값 | 비교 방식 버전 + 비교 대상 내용의 SHA-256 | 자격 확정·원천 개정 번호 |
| 내부 수집 순번 | 해당 정책의 요청 시작 전에 발급할 단조 증가 순번 | 응답 도착 시각·원천 수정시각·해시 정렬 |
| 수집 확인 시각 | 해당 응답을 확인한 시각 | 결과 적용 순서 |
| 내부 적용 개정 | 실제 비교 내용 변경에 따라 1씩 증가하는 번호 | 온통청년이 제공한 외부 개정 번호 |

원본 참조는 인증키가 있는 요청 URL이나 접근 토큰이 아니다. 본문·원천 수정시각 원문과 출처는 향후 원본 보관 경계에서 보존한다. 이 모델에는 본문·개인정보·자유로운 오류 메시지를 넣지 않는다.

비교 방식 버전이 같아야 내용 해시를 비교한다. 방식이 다르면 기존 정상 개정을 유지하고 비교 방식 확인 필요로 남긴다. 해시가 우연히 같거나 원본 해시가 같아도 이 확인을 생략하지 않는다. 변경 필드 목록·정규화 데이터·조건 해석 결과는 후속 정규화 계약에서 정하며, 이 모델의 해시만으로 그 내용을 복원할 수는 없다.

## 3. 결과 적용 규칙

현재 상태는 마지막 처리 결과, 현재 적용 개정, 마지막으로 현재 내용과 일치함을 확인한 정상 결과를 구분한다. 실패한 수집이 마지막 정상 확인 시각을 갱신하지 않게 하기 위해서다.

| 새 결과 | 처리 | 적용 개정·마지막 정상 확인 |
|---|---|---|
| 다른 정책의 결과 | 입력 오류 | 기존 상태 유지 |
| 마지막 처리보다 낮은 수집 순번 | 오래된 결과로 무시 | 유지 |
| 같은 순번·동일 결과 재처리 | 재처리로 무시 | 유지 |
| 같은 순번·서로 다른 결과 | 순번 충돌로 분리 | 유지 |
| 높은 순번·취득 실패/표시 불가 | 실패를 마지막 처리로 기록 | 기존 정상 개정·확인 시각 유지 |
| 높은 순번·비교 방식 버전 불일치 | 확인 필요를 마지막 처리로 기록 | 기존 정상 개정·확인 시각 유지 |
| 높은 순번·같은 비교 내용 | 정상 확인만 갱신 | 개정 유지·정상 확인 갱신 |
| 높은 순번·비교 내용 변경 또는 첫 정상 결과 | 새 내부 개정 생성 | 새 원본 근거 연결·정상 확인 갱신 |

같은 내용이거나 실패한 경우에도 마지막 처리 순번을 갱신한다. 예를 들어 30번 결과가 내용 A를 다시 확인한 뒤 도착한 20번의 B를 적용하지 않는다. A→B→A는 현재 내용이 달라지는 세 번의 적용이므로 개정 1→2→3이다. 전체 이력에 내용 해시를 유일키로 두지 않는다.

재시도 중 **같은 결과를 다시 저장**할 때는 같은 순번과 확인 시각·본문 참조를 유지한다. **외부 요청을 다시 수행**하면 새 순번을 발급한다. 같은 순번에 실패 결과를 기록한 후 다른 성공 결과로 바꾸는 방식은 허용하지 않는다. 비교 방식을 바꿔 다시 처리할 때도 새로운 처리 순서를 배정하는 저장 계약이 필요하다.

표시 가능한 원문에 미해석 자격 조건이 있다는 이유만으로 취득 실패·표시 불가로 분류하지 않는다. 자격 미해석은 기존 판정 모델에서 추가 확인으로 남긴다. 페이지 실패·일시 누락을 정책 삭제로 바꾸는 처리는 제공하지 않는다.

## 4. 실제 저장 단계에서 필요한 원자성

이 순수 모델은 동시에 읽은 두 요청의 DB 갱신을 막지 않는다. 저장 구현은 다음 조건을 실제 PostgreSQL에서 검증해야 한다.

1. 외부 요청 전에 내부 순번과 재시도 식별을 기록한다. 원본 취득·객체 저장·AI 대기 동안 DB 잠금을 유지하지 않는다.
2. 짧은 트랜잭션에서 현재 상태를 읽고 적용 여부를 계산한다. 현재 개정만이 아니라 **기대한 마지막 처리 순번**도 일치해야 갱신한다. 충돌하면 최신 상태로 다시 판단한다.
3. 새 개정 기록·현재 개정 참조·마지막 처리 결과·정상 확인 정보를 함께 커밋한다. 같은 결과의 재저장과 내용 미변경은 개정이나 변경 알림을 추가하지 않는다.
4. 수집 실행·페이지·항목 실패와 재처리 위치는 따로 보존한다. 한 정책의 현재 상태가 전체 실패 이력을 대신하지 않는다. [수집 실행 진행 모델](collection-run-progress.md)은 메모리의 시도 이력을 다루며 실제 DB 보존·재시작 복구는 후속 구현이다.
5. AI·판정·일정·알림에는 적용 정책 식별자와 내부 개정을 전달하고 처리 직전에 현재 개정과 맞는지 확인한다. [AI 후보 모델](policy-ai-candidates.md)은 현재 개정·원본·생성 방식·요청 순번의 관계만 검사한다. 실제 AI·판정·일정·알림의 실행·취소·전달은 별도 구현이다.

원문 저장 위치·보관 기간, 성공/부분 수집의 정의, 원천 식별·정규화·변경 필드 계약을 확인한 뒤 첫 DDL과 저장 유스케이스를 작성한다. 테스트용 임시 DB가 아닌 기존 로컬 DB·운영 DB에 가짜 정책을 적재하지 않는다.
