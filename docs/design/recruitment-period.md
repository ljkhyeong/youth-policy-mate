# 모집 기간·마감 상태 모델

- 기준일: 2026-08-31
- 제품 기준: [PRD 5·7절](../PRD/0001_product-baseline/spec.md)
- 책임 경계: [ADR-0001](../ADR/0001_기술스택과_책임_분리.md)
- 범위: 원문에서 의미를 확인한 단일 신청기간을 비교한다. 실제 API 문자열 파서·DB·화면·알림 예약은 별도 작업이다.

## 날짜와 시각을 분리한다

신청기간과 사업기간은 서로 다른 정보다. 신청기간이 없을 때 사업 종료일을 마감일로 사용하지 않는다. 이 모델은 사업기간을 입력받지 않는다.

| 입력 종류 | 필요한 확인 | 비교 방식 |
|---|---|---|
| 날짜 범위 | 시작·끝 날짜가 모두 포함되는 신청기간임을 확인 | 서울의 오늘 날짜가 시작일 전이면 모집 전, 범위 안이면 접수 기간, 끝 날짜 다음 날부터 마감 |
| 시각 범위 | 시간대·시작 시각 포함·접수 종료 경계를 확인 | 시작 시각 이상이며 마감 시각 미만이면 접수 기간, 마감 시각과 같거나 이후이면 마감 |
| 상시 | 원문에서 상시 모집임을 확인 | 상시 상태를 유지하며 날짜를 만들지 않음 |
| 소진 시 종료 | 예산·정원 등의 소진에 따라 종료함을 확인 | 소진 시 종료 상태를 유지하며 현재 접수 가능·소진 완료를 추정하지 않음 |
| 명시적 마감 | 원문에서 마감 상태임을 확인 | 마감 상태만 보존하며 과거의 마감 날짜를 만들지 않음 |
| 기간 미확인 | 누락·충돌·미지원 표현의 이유를 기록 | 기간 미확인으로 남기고 날짜를 만들지 않음 |

날짜 범위의 끝 날짜는 시각형 마감으로 변환하지 않는다. 날짜형 결과의 접수 기간 표시는 달력상 범위에 포함된다는 뜻이며, 정확한 접수 시각을 보장하지 않는 안내를 함께 제공한다. 원문에 시간이 존재하지만 아직 해석하지 못했다면 날짜형으로 정밀도를 낮추지 않고 미확인으로 남긴다.

시각형 입력의 `closesAtExclusive`는 접수가 끝나는 순간이다. 원문의 `18:00까지`가 실제로 어떤 정밀도·포함 경계를 뜻하는지는 원천 해석 단계에서 확인해야 한다. 모든 원문을 이 규칙으로 자동 해석하지 않는다. 시간대 없는 `LocalDateTime`을 받거나 서버 기본 시간대를 적용하지 않는다.

## 상태와 근거의 소유권

모집 상태는 정책 모듈이 계산한다. 자격 결과·회원 정보는 입력받지 않으며, `접수 기간`은 자격 충족이나 공식 접수 가능의 보장이 아니다. 일정·알림 모듈에서 원문을 다시 파싱하거나 모집 상태를 중복 계산하지 않는다.

정책 식별자·적용 개정, 기간 자료, 원문 참조·위치·발췌문을 함께 보존한다. 계산 결과에는 시계에서 한 번 읽은 판정 시각을 남기며, 같은 시각으로 서울 날짜를 계산한다. 요청 도중 날짜가 넘어가도 한 결과 안의 기준이 달라지지 않는다. 시계는 호출 측에서 주입한다.

새 개정이나 바뀐 모집 안내는 새 자료로 평가한다. 이 순수 모델은 개정의 선후 관계·최신성·동시 갱신을 판단하지 않는다. 수집 실패·과거 자료는 호출 측에서 마지막 확인 시각과 함께 표시해야 한다.

## 현재 지원하지 않는 입력

- 시작이나 종료 한쪽만 확인한 기간
- 날짜형 시작과 시각형 종료가 섞인 기간
- 복수 차수·반복 모집·차수 사이 공백
- 주말·휴일 제외, 요일별 운영 시간, 접수 채널별 다른 기간
- 날짜 범위와 상시·마감 코드의 모순, 선착순·예산 소진 여부 미확인

위 입력은 임의의 최소 시작일·최대 종료일로 합치거나 우선순위를 정하지 않는다. 확인이 필요한 이유와 원문을 미확인 자료에 남긴다. 이미 종료되었다는 명확한 최신 안내가 확인되면 마감 자료를 사용할 수 있지만, 충돌 해결 책임은 원천 해석 측에 있다.

## 알림과 실제 연동은 별도다

이번 모델은 알림 날짜·발송 시각·재시도 만료를 정하지 않는다. 확인된 마감의 D-7·D-3·D-1 계산은 [PRD](../PRD/0001_product-baseline/spec.md)의 서울 날짜 기준을 따르되, 날짜형과 시각형 원본을 보존한 별도 작업으로 진행한다. 상시·소진 시 종료·미확인에는 가짜 마감일이나 예약을 만들지 않는다.

인증키 발급 후 실제 성공 응답에서 복수 기간, 날짜·시각 정밀도, 시간대와 코드·본문 충돌을 확인한 뒤 수집 파서를 작성한다. 내부 모델을 온통청년 원천 DTO나 확정 REST 계약으로 사용하지 않는다.

확인된 기간의 순수 Java 모델과 테스트는 구현했다. 실제 코드·실행 명령·검증 범위는 [모집 기간 구현 기록](../development/recruitment-period.md)에 정리한다.
