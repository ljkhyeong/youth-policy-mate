# 명시적 연령 조건 비교

2026-08-30 구현 기준. 제품 요구는 [PRD 5절](../PRD/0001_product-baseline/spec.md#5-자격-안내와-추천-근거), 항목 결과와 최종 상태의 관계는 [판정 결과 집계](eligibility-decision.md)를 따른다.

## 현재 구현 범위

`AgeConditionEvaluator.evaluate(condition, solarBirthDate)`는 확인한 연령 조건과 양력 생년월일을 받아 `ConditionAssessment` 하나를 반환한다. 순수 Java 코드이며 인증키·Spring 실행·DB가 필요하지 않다.

원문 해석을 마친 **정책 기준일 현재 만 N세 이상·M세 이하** 조건만 계산한다. 서비스 대상인 19~34세를 기본 범위로 넣지 않는다. 원천 API 파서, 실제 정책 매핑, HTTP API, DB 저장과 화면 연결은 없다. `/conditions`의 입력값도 이 비교기로 보내지 않는다.

## 입력과 미해석 조건

| 입력 모델 | 의미 |
|---|---|
| `AgeCondition.CompletedYears` | 완전히 경과한 연수로 계산하는 나이 정의, 양쪽 경계를 포함한 최소·최대 연령, 명시적 기준일과 원문 근거를 확인한 조건 |
| `AgeCondition.Unresolved` | 아직 비교할 수 없는 조건 설명, 확인된 경우에만 기준일, 미해석 이유와 원문 근거 |
| `Optional<LocalDate> solarBirthDate` | 양력 생년월일 또는 입력 누락. 본인 인증·날짜의 진위 확인을 뜻하지 않음 |

`CompletedYears` 생성자는 필수값, 음수 연령과 최소·최대 역전을 거절한다. 이것은 내부 모델의 잘못된 구성을 막는 검사다. 향후 원문 해석기에서 잘못된 값이나 미확인 조건을 만나면 생성자 오류를 자격 불충족으로 바꾸지 말고 `Unresolved`로 남겨야 한다.

현재 계산하지 않는 조건은 다음과 같다.

- 출생연도 기준, 한쪽만 있는 연령 제한, 경계를 제외하는 비교, 명시적인 연령 제한 없음.
- 군 복무 기간 연장 등 별도 예외, 다른 윤일 처리 방식, 나이 정의·기준일·범위가 미확인인 조건.

이 조건을 표현하려고 누락된 최소·최대값을 0·34·999 등으로 채우거나 기준일을 오늘로 바꾸지 않는다. 예외를 아직 반영하지 못했다면 항목을 미해석으로 남기거나 `PolicyReview`의 미완료 항목으로 보존한다. AI 추출 후보만으로 확인 완료 조건을 만들지 않는다.

## 비교와 결과

| 상황 | 항목 결과 | 미확인 구분 |
|---|---|---|
| 정책 조건을 해석하지 못함 | `UNKNOWN` | `UNRESOLVED_POLICY` |
| 확인한 조건에 필요한 생년월일이 없음 | `UNKNOWN` | `MISSING_USER_INPUT` |
| 생년월일이 정책 기준일보다 늦음 | `UNKNOWN` | `UNRESOLVED_POLICY` |
| 기준일의 만 나이가 확인한 범위에 포함됨 | `MET` | 없음 |
| 기준일의 만 나이가 확인한 범위를 벗어남 | `NOT_MET` | 없음 |

정책 조건이 미해석이면 생년월일 유무와 관계없이 해당 이유를 먼저 보존한다. 생년월일이 기준일보다 늦은 경우도 음수 나이나 불충족으로 계산하지 않고 두 날짜를 확인하도록 안내한다. 이는 사용자 생년월일이 틀렸다고 확정하는 것이 아니라 주어진 날짜 조합의 비교를 보류하는 처리다.

계산은 `Period.between(birthDate, referenceDate).getYears()`를 사용한다. 날짜와 날짜 사이에 완전히 경과한 연수이며 시간대는 적용하지 않는다. [Java 25의 LocalDate 문서](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/LocalDate.html)에서 사용하는 ISO 날짜 계산을 따른다.

2월 29일생의 예를 들면, 2000-02-29부터 2020-02-28까지는 19년, 2020-02-29까지는 20년이다. 평년인 2021-02-28까지는 20년, 2021-03-01부터 21년으로 계산한다. 모든 정책이 이 윤일 해석을 사용한다고 확인한 것은 아니다. 원문이 다른 방식을 정하면 이 타입에 넣지 않고 해당 해석을 지원할 때까지 보류한다.

현재 날짜를 조회하지 않고 정책 기준일을 직접 받으므로 `Clock`은 필요하지 않다. 이후 신청일·오늘 날짜를 기준으로 정하는 기능을 추가하면 그 날짜를 선택하는 계층에 `Clock`과 필요한 시간대를 명시한다. 생년월일의 미래 날짜 검사, 음력 변환과 소셜 정보 확인은 이 비교기의 책임이 아니다.

## 근거와 집계

결과에는 조건 ID, 적용 범위, 정책 기준일, 계산한 `만 N세`, 이유와 원문 근거를 보존한다. 생년월일 원문을 비교값에 복사하지 않으며 새 로그·저장·외부 전송도 추가하지 않았다. 결과와 원문 근거에는 개인정보가 포함될 수 있으므로 객체 전체를 로그나 분석 이벤트에 넣지 않는다.

비교기는 `PolicyReview.complete()`를 만들지 않는다. 연령을 충족해도 다른 필수 조건·예외를 검토하지 않았다면 기존 집계 규칙에 따라 `NEEDS_REVIEW`다. 원천 개정·규칙 버전·판정 시점은 호출자가 `EvaluationBasis`로 함께 관리하며 연령 비교가 이를 덮어쓰지 않는다.

## 코드와 검증

- `backend/src/main/java/kr/youthpolicymate/eligibility/AgeCondition.java`: 확인한 조건과 미해석 조건.
- `backend/src/main/java/kr/youthpolicymate/eligibility/AgeConditionEvaluator.java`: 항목 비교와 근거 생성.
- `backend/src/test/java/kr/youthpolicymate/eligibility/AgeConditionEvaluatorTest.java`: 경계·미확인·집계 연결 검사.

저장소 루트에서 실행한다.

```sh
npm run test:eligibility
./backend/gradlew -p backend assemble --no-daemon
```

2026-08-30에 연령 비교 18건과 기존 집계 14건, 총 32건이 실패·건너뛰기 없이 통과했다. 서버 `assemble` 빌드도 통과했다. 새 테스트는 최소·최대 연령의 생일 경계, 윤일, 입력 누락, 기준일·나이 정의 미해석, 날짜 충돌, 근거 보존과 다른 예외의 보류를 확인한다.

테스트 자료는 연령·날짜를 직접 지정한 인공 입력이다. 실제 API 성공 응답, 특정 정책 원문의 정확한 해석이나 법적 자격을 검증한 것이 아니다. 웹·DB 코드는 바꾸지 않아 프런트엔드 검사와 PostgreSQL 통합 테스트는 이번 작업에서 다시 실행하지 않았다.

## 후속 연결

실제 정책 응답과 원문을 확보한 뒤 나이 정의·기준일·범위·예외가 이 모델에 맞는지 확인한다. 원천 필드가 숫자로 읽혔다는 이유만으로 확인 완료로 처리하지 않는다. [명시적 거주 비교기](residence-condition.md)도 추가했지만 실제 원천 자료와는 연결하지 않았다. 취업·소득 비교와 최종 API/UI 연결은 별도 작업이다.
