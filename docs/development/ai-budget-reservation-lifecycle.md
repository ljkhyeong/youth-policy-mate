# AI 요청 예산 예약·정산 상태 모델

2026-09-01 구현 기준. [설계](../design/ai-budget-reservation-lifecycle.md)에 따라 요청별 최대 비용을 보유하는 순수 Java 상태와 PostgreSQL 원자적 예약·호출 이후 상태 전이를 구현했다. 실제 외부 AI 호출과 공급자 청구 조회는 아직 없다.

## 코드와 동작

`backend/src/main/java/kr/youthpolicymate/ingestion/AiBudgetReservationState.java`가 한 예산의 잔액과 이번 모델에서 만든 요청별 예약을 함께 관리한다.

- `reserve`: `ReservationRequired`의 예산 스냅샷과 현재 잔액을 다시 비교하고 최대 비용을 예약액에 더한다.
- `dispatch`: 예약 이후의 외부 호출 식별자와 시각을 기록한다. 외부 호출 자체는 수행하지 않는다.
- `markOutcomeUnknown`: 타임아웃·연결 끊김·공급자 상태 미확인을 기록하고 예약액을 유지한다.
- `settle`: 확인한 실제 비용을 확정액에 더하고 최대 비용 예약을 해제한다. 예약액 초과 비용도 별도 결정으로 기록한다.
- `cancelBeforeDispatch`: 외부 호출 전 취소한 예약만 해제한다.
- `releaseAfterNoCharge`: 외부 호출 후에는 별도의 무과금 확인이 있을 때만 예약을 해제한다.

상태는 불변 객체다. 성공한 전이가 새 `AiBudgetReservationState`를 반환하며 이전 객체를 바꾸지 않는다. 동일 예약·요청의 재전달과 다른 내용의 충돌, 오래된 잔액, 허용되지 않은 전이 순서를 구분한다.

순수 모델의 예약은 DB 행이 아니다. 같은 시작 상태를 두 작업자가 각각 사용하면 둘 다 성공 상태를 계산할 수 있다.

## PostgreSQL 저장

V1이 예산·요청 예약 테이블을 만들고 V2가 호출 이후 상태 열과 제약을 추가한다.

| 구성 | 역할 |
|---|---|
| `ai_budgets` | 예산 ID·기간·한도·확정액·예약액 저장. 음수 금액과 잘못된 기간 차단 |
| `ai_request_reservations` | 요청 근거·생성/가격 버전·최대 비용, 호출·미확인·완료 정보와 현재 단계 저장 |
| `AiBudgetReservationStore` | 예산 행 잠금, 최신 잔액 재검사, 중복 분류, 예약 INSERT와 예약액 증가 |
| `AiBudgetReservationLifecycleStore` | 호출 식별자·결과 미확인 저장, 정산·취소·무과금 해제, 미완료 예약 조회 |

`reserve`는 `@Transactional` 메서드다. 예산 행을 `FOR UPDATE`로 잠근 뒤 예약 ID와 정책·작업 종류·요청 순번의 중복을 확인한다. DB 잔액이 사전 판단과 다르거나 한도가 부족하면 저장하지 않는다. INSERT에는 `ON CONFLICT DO NOTHING`을 사용하고 충돌 행을 다시 읽어 재전달·예약 ID 충돌·요청 중복을 구분한다.

호출 이후 상태 전이도 외부 호출을 수행하지 않는다. 호출에 사용할 식별자를 저장하고 트랜잭션을 끝낸 뒤 호출 측이 외부 통신을 수행해야 한다. 타임아웃과 연결 끊김은 `OUTCOME_UNKNOWN`으로 저장하며 예약액을 유지한다. 확인된 실제 비용 정산·호출 전 취소·확인된 무과금 해제만 예산 합계를 바꾸고, 예약 행과 예산 행을 같은 트랜잭션에서 갱신한다.

같은 호출·미확인·종료 정보는 재생으로 처리한다. 다른 종료 결과는 기존 확정을 덮지 않는다. `HELD`·`DISPATCHED`·`OUTCOME_UNKNOWN` 조회는 재시작 후 확인 대상을 제공하지만 작업자 소유권이나 자동 재호출은 제공하지 않는다. 예산 행을 만드는 운영 API·기본 예산도 없으며 테스트만 인공 예산을 직접 넣는다.

V2 제약은 단계별 필수 열, 식별자의 빈 문자열, 미확인 사유, 음수 실제 비용과 예약→호출→미확인→완료의 시간 순서를 검사한다. 기존 V1의 `HELD` 행은 새 열이 모두 `NULL`인 상태로 그대로 유효하다.

## 검사

저장소 루트에서 실행한다.

```sh
npm run test:ai-reservations
npm run test:ai-reservation-db
npm run test:ingestion
npm run check:backend
```

전용 검사는 13건이다. 예약액·잔액 갱신, 동일 예약 재전달, 요청·식별자 충돌, 오래된 잔액, 예산·비용 시각, 외부 호출 식별자, 결과 미확인 금액 보존, 실제 비용 정산과 예약 초과, 호출 전 취소, 무과금 확인, 종료 결과 충돌과 잘못된 전이 순서를 확인한다.

`test:ai-reservation-db` 12건은 Flyway 테이블·원자적 예약, 재전달·충돌, 최신 잔액·한도, 동시 요청, 호출·미확인·정산·취소·무과금 해제와 DB 제약을 실제 PostgreSQL 18.6 Testcontainers에서 확인한다. 동시에 같은 잔액을 사용한 최대 비용 60원의 두 요청은 하나만 예약된다. 같은 예약에 정산과 무과금 확인이 동시에 도착해도 한 종료만 확정되고 예약액은 한 번만 해제된다. 금액은 인공 값이다.

`test:ingestion`은 DB 검사를 제외하고 수집 진행 12·AI 후보 12·사전 판단 14·예약 상태 13건, 총 51건이 통과했다. 전체 서버는 254건(도메인 227·개발 API/계약 13·PostgreSQL 예약·연결/기본 차단 14)이 실패·건너뛰기 없이 통과했고 빌드도 성공했다.

최초 예약 저장 작업의 첫 DB 검사에서는 JDBC 드라이버가 Java `Instant`의 SQL 유형을 추론하지 못해 5건이 실패했다. 저장 파라미터를 UTC `OffsetDateTime`으로 바꾸고 PostgreSQL의 마이크로초 정밀도에 맞춘 뒤 통과했다. 이번 상태 전이 검사 첫 실행에서는 `7.50`과 DB의 `7.5`를 객체 자릿수까지 비교해 12건 중 1건이 실패했다. 테스트 금액을 업무 코드와 같은 수치 기준으로 정규화한 뒤 전용 12건과 전체 검사가 통과했다.

테스트 금액·식별자·시각은 인공 값이며 운영 예산이나 가격 권장값이 아니다. 웹·브라우저·실제 AI·공급자 청구는 검사하지 않았다. 화면·API 계약은 변경하지 않았다.

## 남은 작업

- 월 운영비 3만 원 내 AI 배분액과 공급자별 최대 비용 산정·갱신 기준
- 호출·미확인·종료 이벤트의 여러 번 재확인 시도 이력
- 재시작 후 오래된 작업 소유권과 미확인 예약 운영 조회
- 실제 공급자 호출과 후보 기록, 결과 미확인 조회·운영 표시·재확인 절차
- 최대 예약액과 실제 청구의 대사, 초과 청구 처리와 운영 상한 검증

현재 저장소는 DB에 미리 등록된 예산과 호출 측이 제공한 최대 비용을 신뢰한다. 원자적 예약은 검증했지만 공급자 가격·청구 정확성이나 외부 비용 상한을 보장하지 않는다.
