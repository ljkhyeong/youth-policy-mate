# AI 예약 복구 내부 운영 조회

2026-09-02 구현 기준. [복구 소유권 설계](../design/ai-reservation-recovery.md)에 따라 오래된 미완료 예약, 전체 복구 이력과 재확인 판단을 한 번에 읽는 내부 저장소 조회를 추가했다. 관리자 API·화면·인증·권한과 실제 복구 실행은 포함하지 않는다.

## 조회 입력과 결과

`AiReservationRecoveryOperationsQuery.findOldestUnresolved`는 호출 측이 다음 값을 명시하도록 한다.

- 고정 기본값이 없는 최대 시도 횟수와 시도별 재확인 간격
- 오래된 예약으로 볼 마지막 갱신 시각
- 재확인 판단 시각
- 1개 이상의 최대 조회 수

판단 시각은 오래된 예약 기준보다 빠를 수 없다. `updated_at`이 기준 시각 이하인 `HELD`·`DISPATCHED`·`OUTCOME_UNKNOWN` 예약만 조회하며, 오래된 갱신 시각과 예약 ID 순서로 결과를 고정한 뒤 최대 수를 적용한다.

각 항목은 정책 ID·AI 작업 종류·생성 방식 버전·요청 순번, 예약 스냅샷, 예약별 전체 복구 시도 이력과 [재확인 정책](ai-reservation-recovery-retry-policy.md)의 판단을 반환한다. 수동 검토와 최대 횟수 도달도 결과에서 구분된다.

## 운영과 보안 경계

- 예약과 복구 이력은 한 SQL 문으로 읽어 서로 다른 시점의 상태를 조합하지 않는다.
- 조회 트랜잭션은 읽기 전용이며 예약·예산·시도 상태를 바꾸거나 임대를 얻지 않는다.
- `Ready`는 작업 실행 명령이 아니다. 후속 [작업 배정](ai-reservation-recovery-work-assignment.md)이 예약을 잠그고 현재 상태와 전체 이력으로 정책을 다시 확인한다.
- 정책 원본·AI 프롬프트·사용자 개인정보는 반환하지 않는다.
- `preview` 프로필에는 저장소 조회 빈을 등록하지 않는다.

현재는 내부 Java 조회와 명시적으로 선택한 `Ready` 후보의 배정 경계이며, 후속 [제한 목록 실행](ai-reservation-recovery-work-runner.md)이 한 조회 결과의 보류·중단 항목을 건너뛰고 준비된 후보를 순서대로 배정·실행한다. [작업 실행 기록](ai-reservation-recovery-work-runs.md)은 실행 ID와 이 조회 조건을 함께 저장한다. 운영자에게 노출할 관리자 API·화면·인증·권한, 주기 스케줄러, 수동 검토나 최대 횟수 도달을 해제하는 명령과 감사 기록은 아직 없다.

## 검사

저장소 루트에서 실행한다.

```sh
npm run test:ai-recovery-operations
npm run check:backend
```

전용 PostgreSQL 18.6 Testcontainers 검사 중 조회 5건은 다음을 확인한다.

- 오래된 미완료 예약만 선택하고 종료·최근 예약을 제외하는 컷오프
- 갱신 시각과 예약 ID의 안정적인 순서, 최대 조회 수와 AI 요청 범위
- 활성 임대 보류와 조회 전후 상태 불변
- 확인 실패 뒤 재확인 간격
- 수동 검토와 완료·만료를 포함한 최대 시도 횟수 도달 구분
- 잘못된 조회 시각과 최대 조회 수 거절

같은 명령의 작업 배정 5건을 포함해 전용 10건, 후속 배정 실행 4건과 제한 목록·작업 실행 기록·운영 중단·시도 연결 18건을 포함한 전체 백엔드 328건이 실패·오류·건너뛰기 없이 통과했다. 구성은 DB 없는 도메인 245건, 개발 API·계약 13건, PostgreSQL 예약·실행·복구·연결·운영 조회·작업 배정·제한 목록·작업 실행 기록/운영 중단/실행-시도 연결/기본 차단 70건이다. 화면·API 계약은 변경하지 않았고 Flyway V6까지 적용했다.
