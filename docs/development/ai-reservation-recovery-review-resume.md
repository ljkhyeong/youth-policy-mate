# AI 예약 복구 수동 검토 재개

2026-09-02 구현 기준. 수동 검토가 필요하다고 완료한 복구 시도의 결과를 보존하면서, 운영자가 확인한 예약 상태와 근거를 남기고 자동 재확인을 다시 허용한다. [복구 소유권 설계](../design/ai-reservation-recovery.md)의 감사·펜싱 계약을 따른다. 관리자 API·화면·인증·권한과 실제 공급자 확인은 포함하지 않는다.

## 저장 계약

Flyway V7의 `ai_reservation_recovery_review_resumes`는 다음 값을 저장한다.

- 재전달과 충돌을 구분할 재개 ID
- `MANUAL_REVIEW_REQUIRED`로 끝난 대상 복구 시도 ID
- 재개한 운영자 식별자
- `SUPPLIER_STATE_VERIFIED`·`INTERNAL_STATE_VERIFIED`·`RECOVERY_INCIDENT_RESOLVED` 중 하나의 사유
- 운영자가 확인한 예약 단계와 갱신 시각
- 재개 시각

대상 시도는 외래 키로 연결하고 한 시도에는 재개 기록을 하나만 허용한다. 기존 복구 시도의 결과·완료 시각·작업자를 수정하지 않으며 자유 형식 공급자 응답이나 오류 메시지를 감사 필드에 저장하지 않는다.

## 재개와 펜싱

`AiReservationRecoveryReviewStore.resume`은 다음 순서로 처리한다.

1. 재개 ID를 PostgreSQL 자문 잠금으로 직렬화하고 같은 명령이면 기존 기록을 재전달한다.
2. 예약 행을 잠그고 종료 여부와 운영자가 확인한 단계·갱신 시각을 비교한다.
3. 대상 시도를 잠그고 같은 예약의 가장 최근 완료 시도인지 확인한다.
4. 결과가 `MANUAL_REVIEW_REQUIRED`이고 아직 재개되지 않았을 때만 감사 기록을 저장한다.

같은 재개 ID에 다른 내용이 오면 충돌로 반환한다. 예약이 바뀌거나 종료됐고, 대상 시도가 없거나 최신이 아니며, 다른 결과로 끝났거나 이미 재개됐다면 새 기록을 만들지 않는다. 서로 다른 재개 ID가 동시에 도착해도 예약 잠금과 대상 시도의 유일 제약으로 하나만 저장한다.

호출 측이 전달한 운영자 ID는 현재 내부 감사 값이다. 실제 관리자 기능에서는 인증된 운영자와 권한을 HTTP 경계에서 확인해야 한다.

## 재확인 정책 연결

운영 조회는 복구 시도와 재개 감사 이력을 한 SQL 스냅샷으로 읽는다. 재개되지 않은 최신 수동 검토는 기존처럼 `Stopped.MANUAL_REVIEW_REQUIRED`다. 재개됐다면 예약 갱신 시각·수동 검토 완료 시각·재개 시각 중 늦은 시각에 기존 재확인 간격을 더한다.

재개 기록은 시도 횟수를 지우거나 최대 횟수를 늘리지 않는다. 최대 횟수에 도달했다면 `Stopped.MAXIMUM_ATTEMPTS_REACHED`를 유지한다. 간격이 지난 `Ready` 후보도 작업 배정 시 예약 잠금 안에서 감사 이력을 다시 읽어 같은 정책으로 확인한 뒤에만 다음 시도를 만든다.

## 검사

저장소 루트에서 실행한다.

```sh
npm run test:ai-recovery-policy
npm run test:ai-recovery
npm run test:ai-recovery-operations
npm run check:backend
```

- 재확인 순수 정책 11건: 재개 후 간격과 최대 시도 횟수 유지 포함
- 복구 저장소 16건: 재개 감사와 활성 임대 갱신·동시성·DB 제약 포함
- 운영 조회·배정 11건: 재개 이력 조회, 간격 경계와 다음 시도 배정 포함
- 전체 백엔드 340건: 실패·오류·건너뛰기 없이 통과

전체 구성은 DB 없는 도메인 246건, 개발 API·계약 13건, PostgreSQL 예약·실행·복구·임대 갱신·운영 조회·수동 검토 재개·기본 차단 81건이다. 화면·API 계약은 변경하지 않았고 Flyway V8까지 적용했다.

## 남은 작업

- 인증된 관리자와 재개 권한을 확인하는 API·화면
- 운영자에게 표시할 공급자 확인 근거와 민감 정보 제외 기준
- 실제 공급자 상태 조회와 재개 사유의 운영 절차
- 실제 작업자의 자동 heartbeat와 갱신 실패 처리
