# AI 예약 복구 작업 배정

2026-09-02 구현 기준. [내부 운영 조회](ai-reservation-recovery-operations-query.md)에서 선택한 `Ready` 후보를 현재 PostgreSQL 상태로 다시 확인하고 한 작업자에게 배정한다. 실제 공급자 확인과 자동 반복 실행은 포함하지 않는다.

## 배정 흐름

`AiReservationRecoveryWorkAssigner.assign`은 운영 조회 결과, 그 결과에 포함된 후보와 호출 측이 만든 임대를 받는다.

- 후보가 운영 조회 결과에 실제로 포함돼 있어야 한다.
- 조회 당시 판단이 `Ready`가 아니면 DB 소유권 획득을 시도하지 않는다.
- 임대 시작 시각은 운영 조회 판단 시각보다 빠를 수 없다.
- 최대 시도 횟수·재확인 간격·임대 길이는 호출 측이 제공하며 고정 기본값은 없다.

`AiReservationRecoveryStore.claimIfReady`는 시도 ID를 직렬화한 뒤 예약 행을 잠근다. 같은 트랜잭션에서 현재 예약 스냅샷과 전체 복구 이력을 다시 읽고, 실제 임대 시작 시각으로 재확인 정책을 계산한다. 결과가 여전히 `Ready`일 때만 새 활성 시도를 저장한다.

조회 뒤 활성 임대·재확인 대기·수동 검토·최대 횟수 도달·종료 상태가 생기면 현재 판단을 반환하고 새 시도를 만들지 않는다. 같은 배정 요청은 기존 시도를 재전달하며, 같은 후보에 대한 서로 다른 작업자의 동시 배정은 한 작업자만 통과한다.

## 현재 연결 범위

배정 결과는 활성 `Attempt`까지다. 기존 `PolicyAiRecoveryCoordinator.recoverNext`는 여전히 자체 `claimNext`로 대상을 선택하므로 이번 배정 경계를 사용하지 않는다. 다음 연결에서는 이미 배정된 시도를 조정자가 입력으로 받아 예약 상태를 다시 읽고, 트랜잭션 밖 인공 확인을 수행하도록 분리해야 한다.

관리자 API·화면·인증·권한, 후보 목록 자동 순회, 스케줄러, 공급자 어댑터, 실제 재확인 간격과 최대 횟수는 아직 없다. `claimNext`도 호환을 위해 유지하지만 재확인 정책이 필요한 자동 작업의 진입점으로 사용하면 안 된다.

## 검사

저장소 루트에서 실행한다.

```sh
npm run test:ai-recovery-operations
npm run check:backend
```

기존 운영 조회 5건에 배정 5건을 더한 PostgreSQL 18.6 Testcontainers 검사 10건이 통과했다. 배정 검사는 다음을 확인한다.

- 조회 당시 `Ready` 후보의 첫 소유권 획득
- 조회 당시 활성 임대로 보류된 후보의 미배정
- 조회 뒤 수동 검토가 기록된 후보의 잠금 후 재확인
- 같은 오래된 조회 결과를 사용한 동시 배정 중 한 작업자만 획득
- 동일 배정 요청의 기존 시도 재전달

전체 백엔드 306건이 실패·오류·건너뛰기 없이 통과했다. 구성은 DB 없는 도메인 245건, 개발 API·계약 13건, PostgreSQL 예약·실행·복구·연결·운영 조회·작업 배정/기본 차단 48건이다. 화면·API·Flyway 계약은 변경하지 않았다.

## 남은 작업

- 배정된 시도를 기존 복구 조정자의 트랜잭션 밖 확인 입력으로 연결
- 후보 목록의 중단 항목이 다음 `Ready` 후보를 막지 않는 제한·순회 계약
- 공급자 선정 뒤 실제 간격·최대 시도 횟수·임대 길이 확정
- 인증·권한을 갖춘 관리자 노출과 수동 검토 재개 감사 기록
