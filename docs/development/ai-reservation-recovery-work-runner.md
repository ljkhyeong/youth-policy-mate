# AI 예약 복구 제한 목록 실행

2026-09-02 구현 기준. [내부 운영 조회](ai-reservation-recovery-operations-query.md)가 반환한 제한된 후보 목록을 순서대로 확인하고, 준비된 항목만 [작업 배정](ai-reservation-recovery-work-assignment.md)과 [복구 조정자](policy-ai-recovery-execution.md)에 연결한다. 후속 [작업 실행 기록](ai-reservation-recovery-work-runs.md)은 한 번의 목록 실행을 식별하고 중복 기동과 결과 집계를 PostgreSQL에 남긴다. 실제 공급자·스케줄러·고정 운영값은 포함하지 않는다.

## 실행 흐름

`AiReservationRecoveryWorkRunner.run`은 운영 조회 조건과 준비된 후보마다 사용할 임대 생성 함수를 받는다.

1. 운영 조회의 `limit`만큼 오래된 미완료 예약을 읽는다.
2. `Deferred`·`Stopped` 후보는 임대 정보를 만들거나 DB를 변경하지 않고 건너뛴다.
3. 조회 당시 `Ready`인 후보만 임대를 만들고, 예약 행을 잠근 현재 상태로 다시 배정 가능 여부를 확인한다.
4. 배정된 `ReadyClaimed`는 `recoverAssigned`로 전달해 트랜잭션 밖 인공 확인과 기존 펜싱 적용을 수행한다.
5. 한 후보의 외부 확인에서 예외가 발생하면 실패를 후보 결과에 보존하고 같은 목록의 다음 후보를 계속 처리한다.

조회 결과의 순서와 크기는 그대로 유지하며 후보별 결과를 다음과 같이 구분한다.

| 결과 | 의미 |
|---|---|
| `SkippedByReport` | 조회 단계에서 활성 임대·재확인 대기·수동 검토·최대 횟수 도달 등으로 실행하지 않음 |
| `AssignmentNotClaimed` | 조회 때는 준비됐지만 잠금 후 현재 상태나 소유권 충돌 때문에 배정하지 못함 |
| `RecoveryFinished` | 배정 뒤 복구 조정자 호출이 결과를 반환함. 내부 결과가 실제 적용 완료인지 별도로 확인해야 함 |
| `RecoveryFailed` | 배정 뒤 후보 단위 복구 호출에서 예외가 발생함 |

외부 확인 예외가 난 시도는 성공이나 수동 검토로 임의 완료하지 않는다. 기존 조정자 계약대로 활성 임대와 예약액을 유지하며, 다음 운영 조회는 임대 만료와 재확인 일정에 따라 다시 판단한다. 임대 생성 함수 자체의 오류나 DB 조회·배정 오류는 실행 전체의 구성·인프라 실패이므로 후보 실패로 삼키지 않는다.

## 현재 경계

- 한 번의 호출은 운영 조회 `limit`로 제한되며 결과 목록 밖의 예약은 건드리지 않는다.
- 임대 시도 ID·작업자·획득 시각·만료 시각은 호출 측이 제공한다. 공급자별 기본값을 만들지 않는다.
- 같은 활성 배정의 동시 실행에서 공급자 조회를 정확히 한 번 수행한다고 보장하지 않는다.
- 주기 실행, 다음 실행 시각 예약, 임대 갱신, 수동 검토 재개는 구현하지 않았다.
- 실제 공급자 빈이 없으므로 현재 검사는 인공 확인 포트만 사용한다.

`AiReservationRecoveryWorkRunCoordinator`를 사용하면 실행 ID와 조회 조건을 먼저 `RUNNING`으로 저장하고, 목록 처리 뒤 후보 결과 개수를 `COMPLETED`로 기록한다. 실행이 실제로 소유한 복구 시도는 Flyway V6 연결 테이블에 함께 저장한다. 같은 실행 ID의 실행 중·완료·실패 재전달은 목록 실행기를 다시 호출하지 않는다. 실행 전체 오류는 `FAILED`로 남기지만 후보 하나의 외부 확인 오류는 기존 `RecoveryFailed` 집계에 포함하고 다음 후보를 계속 처리한다.

## 검사

저장소 루트에서 실행한다.

```sh
npm run test:ai-recovery-work
npm run check:backend
```

실제 PostgreSQL 18.6 Testcontainers를 사용하는 제한 목록 4건은 다음 경계를 확인한다.

- 오래된 보류·중단 후보 뒤의 `Ready` 후보 실행
- 조회 뒤 수동 검토로 바뀐 첫 후보의 잠금 후 미배정과 다음 후보 실행
- 운영 조회 `limit` 밖 예약의 미변경
- 한 후보의 외부 확인 예외 기록과 다음 후보 계속 실행

작업 실행 기록·연결 9건과 오래된 실행 조회·운영 중단 5건을 더한 전용 18건, 전체 서버 328건이 실패·오류·건너뛰기 없이 통과했고 빌드도 성공했다. 전체 구성은 DB 없는 도메인 245건, 개발 API·계약 13건, PostgreSQL 예약·실행·복구·연결·운영 조회·작업 배정·제한 목록·작업 실행 기록/운영 중단/실행-시도 연결/기본 차단 70건이다. 화면·API 계약은 변경하지 않았고 Flyway V6까지 적용했다.

## 남은 작업

- 실제 공급자 상태 조회 어댑터와 확인 근거 보존
- 공급자 선정 뒤 실제 재확인 간격·최대 시도 횟수·임대 길이 확정
- 수동 검토로 중단된 예약의 명시적 재개와 감사·펜싱 계약
- 스케줄러의 실행 주기와 실행 ID·작업자 ID 생성
- 같은 활성 배정의 공급자 조회 멱등 계약
- 인증·권한을 갖춘 관리자 조회와 수동 검토 재개 감사 기록
