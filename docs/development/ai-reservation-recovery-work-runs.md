# AI 예약 복구 작업 실행 기록

2026-09-02 구현 기준. [제한 목록 실행](ai-reservation-recovery-work-runner.md)의 한 번의 호출을 식별하고, 같은 실행의 중복 기동을 막으며 후보별 결과 개수와 실행이 만든 예약별 복구 시도를 PostgreSQL에 보존한다. 강제 종료로 남은 오래된 실행 중 기록은 읽기 전용으로 조회하고 운영자가 명시한 경우에만 감사 정보와 함께 중단한다. 실제 공급자·주기 스케줄러·고정 운영값은 포함하지 않는다.

## 실행 식별자와 시작

`AiReservationRecoveryWorkRunStore.start`는 다음 값을 한 실행 요청으로 저장한다.

- 호출 측이 만든 실행 ID와 작업자 ID
- 최대 복구 시도 횟수와 재확인 간격
- 오래된 예약 기준 시각과 판단 시각
- 최대 조회 후보 수

같은 실행 ID와 모든 값이 같으면 현재 상태에 따라 `ALREADY_RUNNING` 또는 `REPLAYED`를 반환한다. 실행 ID를 다른 작업자나 조회 조건에 사용하면 `RUN_ID_CONFLICT`로 거절한다. 동시 INSERT는 실행 ID 기본 키로 직렬화되므로 같은 실행 ID에서는 한 호출만 `STARTED`를 받는다.

이 중복 방지는 같은 실행 ID에 한정한다. 서로 다른 실행 ID는 동시에 시작할 수 있고, 같은 예약에 대한 실제 소유권 경쟁은 기존 예약 행 잠금과 예약별 활성 임대 하나 제약이 처리한다. 실행 ID를 모든 작업의 전역 잠금으로 사용하지 않는다.

## 실행 상태와 트랜잭션

Flyway V4의 `ai_reservation_recovery_work_runs`와 V5의 운영 중단 필드는 다음 상태를 저장한다.

| 상태 | 의미 |
|---|---|
| `RUNNING` | 실행 시작을 저장했고 제한 목록 처리가 끝나지 않음 |
| `COMPLETED` | 제한 목록 처리를 끝내고 후보별 집계를 저장함 |
| `FAILED` | 조회·임대 생성·배정 같은 실행 전체 경계에서 예외가 발생함 |
| `ABORTED` | 운영자가 실행 프로세스 종료·작업자 응답 없음·운영 판단을 확인하고 명시적으로 중단함 |

`AiReservationRecoveryWorkRunCoordinator`는 `RUNNING` 저장을 커밋한 뒤 제한 목록 실행기를 호출하고, 완료 또는 전체 실패를 별도 짧은 트랜잭션으로 기록한다. 외부 AI 상태 확인 동안 실행 기록 행의 잠금을 유지하지 않는다.

후보 하나의 공급자 확인 예외는 제한 목록 실행기의 `RecoveryFailed`이며 실행 전체는 `COMPLETED`로 남는다. 조회나 임대 생성처럼 목록 자체를 계속할 수 없는 예외만 실행 상태를 `FAILED`로 만든다. 예외 메시지는 정책 원문이나 공급자 응답이 섞일 수 있으므로 DB에 저장하지 않는다.

프로세스가 시작 기록 뒤 강제로 종료되면 행은 우선 `RUNNING`으로 남는다. 오래됐다는 이유만으로 자동 만료하거나 다른 실행 ID로 소급 변경하지 않는다. 새 실행 ID의 작업은 시작할 수 있고 예약별 임대가 실제 중복 확인을 다시 막는다.

## 오래된 실행 조회와 운영 중단

`findOldestRunning`은 호출 측이 제공한 시작 시각 기준 이하의 `RUNNING`만 `evaluated_at`, 실행 ID 순으로 제한 조회한다. 조회 조건에는 시작 시각 기준·조회 시각·최대 개수가 함께 있고 조회 자체는 상태를 바꾸거나 실행 소유권을 가져오지 않는다. 고정된 오래됨 기준이나 자동 종료 시간은 코드에 없다.

운영 중단은 같은 조회 결과에 실제로 포함된 실행을 `AbortSelection`으로 다시 선택해야 한다. 중단 시각은 조회 시각보다 빠를 수 없고, 실행 행을 잠근 뒤 현재 상태가 여전히 `RUNNING`인지 확인한다. 완료·실패가 먼저 확정됐으면 `RUN_NOT_ACTIVE`로 반환하며 기존 결과를 덮어쓰지 않는다. 반대로 중단이 먼저 확정됐으면 늦은 완료·실패도 적용하지 않는다.

`ABORTED`는 종료 시각과 다음 감사 정보를 저장한다.

- `PROCESS_TERMINATED`: 실행 프로세스가 종료됐음을 운영자가 확인함
- `WORKER_UNREACHABLE`: 실행 작업자가 응답하지 않음을 운영자가 확인함
- `OPERATOR_DECISION`: 그 밖의 운영 판단으로 실행을 중단함
- 중단을 수행한 운영자 식별자

같은 실행·사유·운영자·중단 시각의 재전달은 `REPLAYED`다. 이미 중단한 실행에 다른 감사 정보를 보내면 `ABORT_CONFLICT`로 거절한다. 자유 형식 오류 메시지는 정책 원문이나 공급자 응답을 섞을 수 있어 저장하지 않는다. 현재 이 메서드는 내부 저장 경계이며 관리자 인증·권한·HTTP API는 아직 연결하지 않았다.

Flyway V5는 V4를 수정하지 않고 중단 사유와 운영자 열을 추가한다. PostgreSQL 제약은 `ABORTED`에 종료 시각·허용된 사유·비어 있지 않은 운영자를 요구하고, 실행 결과 집계가 함께 저장되는 것을 막는다.

## 완료 집계

완료 실행은 조회한 후보 수와 다음 결과 개수를 저장한다.

- 운영 조회에서 보류·중단된 수
- 조회 뒤 잠금 재판정이나 소유권 충돌로 배정하지 못한 수
- 복구 조정자가 실제 결과 적용 경계를 수행한 수
- 배정 뒤 조정자가 시작하지 않은 수
- 후보 단위 외부 확인 예외 수

다섯 결과의 합은 조회 후보 수와 같아야 한다. Java `Summary`와 PostgreSQL CHECK 제약이 같은 조건을 확인하며, 완료 시각은 실행 판단 시각보다 빠를 수 없다.

## 실행과 복구 시도 연결

완료 집계만으로는 실행 중 실제로 소유권을 얻은 예약과 복구 시도를 찾을 수 없다. Flyway V6의 `ai_reservation_recovery_work_run_attempts`는 작업 실행 ID와 복구 시도 ID를 양쪽 외래 키로 연결한다. 시도 ID가 기본 키이므로 한 시도를 여러 실행의 결과로 중복 연결할 수 없다.

`AiReservationRecoveryWorkRunCoordinator`는 실행 ID가 있는 제한 목록 경로를 호출한다. `Ready` 후보를 배정할 때 작업 실행 행을 공유 잠금으로 읽고 다음을 확인한다.

- 작업 실행이 존재하고 아직 `RUNNING`임
- 작업 실행의 작업자와 복구 임대 소유자가 같음
- 잠금 후 재판정에서도 후보가 여전히 `Ready`임

위 조건을 통과한 복구 시도와 연결 행은 같은 짧은 트랜잭션에서 저장한다. 실행 중인 같은 실행의 동일 배정 재전달은 기존 연결을 반환한다. 같은 시도 ID를 다른 실행에 사용하거나 실행 ID 없이 이미 만든 시도에 소급 연결하면 `ATTEMPT_ID_CONFLICT`로 거절한다. 직접 `claim`·`claimNext`·기존 `assign`을 사용한 호환 경로의 시도는 연결 없이 남는다.

`historyForWorkRun`은 실행이 만든 시도를 획득 시각·시도 ID 순으로 반환하고 `findWorkRunId`는 한 시도의 실행 ID를 조회한다. 보류·자동 중단·잠금 후 미배정 후보는 복구 시도를 만들지 않으므로 연결 행도 없고 완료 집계에서 확인한다.

운영자가 작업 실행을 `ABORTED`로 바꾸는 것은 실행 기록을 닫는 조치다. 이미 연결된 활성 시도를 만료시키거나 외부 공급자 확인·예약 정산을 취소하지 않는다. 해당 상태는 기존 복구 시도와 예약 상태에서 따로 확인한다.

## 검사

저장소 루트에서 실행한다.

```sh
npm run test:ai-recovery-work
npm run check:backend
```

실행 기록 PostgreSQL 18.6 Testcontainers 검사 9건은 다음을 확인한다.

- 실행 ID·작업자·조회 조건과 후보별 완료 집계 저장
- 완료한 동일 실행의 집계 재전달과 외부 확인 미반복
- 같은 실행 ID의 동시 기동 한 건
- 다른 작업자·조회 조건의 실행 ID 충돌
- 실행 전체 실패 기록과 동일 실행 미반복
- 완료 집계 누락·합계 불일치의 DB 제약
- 한 실행이 실제로 만든 완료·실패 후보의 복구 시도 연결과 양방향 조회
- 작업자 불일치·종료 실행의 새 시도 차단
- 같은 실행 연결의 재전달, 다른 실행 연결 충돌과 외래 키 제약

운영 조회·중단 PostgreSQL 검사 5건은 다음을 확인한다.

- 실행 중 상태·시작 기준 시각·안정된 정렬·최대 조회 수
- 운영자·중단 사유·중단 시각 저장과 동일 명령 재전달
- 조회 목록 밖 실행과 조회보다 이른 중단 시각 거절
- 완료와 운영 중단 중 먼저 확정된 종료 상태 보존
- 운영 중단 감사 정보의 PostgreSQL 제약

기존 제한 목록 4건과 운영 조회·중단 5건을 포함한 전용 18건, 활성 임대 갱신·heartbeat·수동 검토 재개를 포함한 전체 서버 341건이 실패·오류·건너뛰기 없이 통과했고 빌드도 성공했다. 전체 구성은 DB 없는 도메인 246건, 개발 API·계약 13건, PostgreSQL 예약·실행·복구·임대 갱신·heartbeat·연결·운영 조회·수동 검토 재개·작업 배정·제한 목록·작업 실행 기록/운영 중단/실행-시도 연결/기본 차단 82건이다. 화면·API 계약은 변경하지 않았고 Flyway V8까지 적용했다.

## 남은 작업

- 실제 공급자 상태 조회 어댑터와 확인 근거 보존
- 공급자 선정 뒤 실제 재확인 간격·최대 시도 횟수·임대 길이 확정
- 스케줄러 실행 주기와 실행 ID·작업자 ID 생성 규칙
- 인증·권한을 갖춘 관리자 조회·운영 중단 API와 수동 검토 재개 명령 연결
- 실제 운영 기준을 정한 뒤 오래된 실행 조회 기준과 자동 점검 주기 확정
- 실제 작업자의 자동 heartbeat와 갱신 실패 처리
