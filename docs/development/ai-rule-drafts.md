# AI 추출 결과의 규칙 초안 저장

`915b175` 기준. 수집한 공고 개정에 추출 요청과 결과를 연결하고 유효한 최신 결과를 관리자 규칙 초안으로 저장한다. 명시적인 운영 명령으로 OpenAI 호출·예산 예약·응답 보관·청구 확인을 처리한다. 수집 후 자동 실행과 공급자 청구 자동 대사는 아직 연결하지 않았다.

## 처리 흐름

1. 현재 정책번호·개정·생성 방식·요청 UUID로 요청을 준비한다. 기존 공개 개정과 원본 스냅샷을 참조하며 원문을 중복 보관하지 않는다. 요청 순서는 DB가 발급한다.
2. 준비한 원문과 정책번호·해시·규칙 버전을 사용해 [규칙 형식](policy-rule-data.md#판정표-형식)의 결과를 만든다. 내보내는 범위는 공고 원본·공개 내용·요청 기준이다. 회원 정보를 조회하지 않으며 작업자 이름은 제외한다. 공고에 적힌 지시는 실행하지 않고 자료로 취급한다.
3. 결과를 저장할 때 같은 정책 행을 잠그고 현재 개정·원문·최신 요청을 확인한다. 유효한 결과는 `PolicyRuleStore`로 초안을 만든다. 본문·해시·처리 결과와 초안 ID를 같은 트랜잭션으로 저장한다.
4. [관리자 조건 검토](policy-rule-review.md)의 기존 상세에서 `AI/생성 방식`과 `AI 추출 후보 · 검토 필요` 사유를 확인한다. 원문·질문·판정표·기간을 검토하고 필요하면 수정한 새 초안을 만든 뒤 별도로 적용한다.

생성된 초안만으로 공개 질문이나 최종 자격이 바뀌지 않는다. 이미 저장한 같은 본문을 다시 처리하면 기존 결과를 반환한다. 이후 원문·요청·적용 버전이 달라져도 재적용하지 않는다. 같은 요청 ID에 다른 본문을 덮어쓸 수 없다. 실패한 결과를 고쳐 다시 처리하려면 새 요청 ID로 준비한다.

## 처리 상태

| 상태 | 저장 결과 |
|---|---|
| `DRAFT_CREATED` | 결과 본문과 검토할 규칙 초안을 저장 |
| `SOURCE_CHANGED` | 공고 개정·원문이 달라 본문만 보관 |
| `REQUEST_SUPERSEDED` | 더 최근 요청이 있어 본문만 보관 |
| `INVALID_DEFINITION` | JSON·질문·판정표·기간 형식이 잘못되어 본문만 보관 |
| `INVALID_REFERENCE` | 결과의 정책번호·원문 해시·규칙 버전이 요청과 달라 본문만 보관 |
| `VERSION_CONFLICT` | 같은 규칙 버전이 이미 있어 본문만 보관 |

본문은 UTF-8 128KB까지 받는다. 용량 초과는 저장 전에 거절한다. JSON 외 설명·알 수 없는 필드·여러 JSON 문서를 이어 붙인 결과는 유효한 규칙으로 받지 않는다. 형식이 맞아도 의미가 정확하다고 보증하지 않으며 원문 근거와 추가 확인 항목을 함께 검토한다.

## 운영 명령

저장소 루트에서 Java 25와 로컬 DB를 사용한다. 꺾쇠 안의 값을 검토 대상에 맞춰 바꾼다. 파일은 새 경로에만 작성한다.

```sh
npm run ai:policy-rules -- --args='prepare <정책번호> <현재개정> <생성방식> <요청UUID> /tmp/policy-ai-source.json'
npm run ai:policy-rules -- --args='generate <요청UUID>'
npm run ai:policy-rules -- --args='complete <요청UUID> /tmp/policy-ai-result.json'
npm run ai:policy-rules -- --args='status <요청UUID>'
```

- `prepare`: 현재 원문과 요청 기준을 내보낸다. 규칙 버전은 `ai-요청UUID`이며 결과에 그대로 사용한다. 같은 ID·입력의 재시도는 같은 요청을 사용하지만, 공고가 달라지거나 더 최근 요청이 있으면 거절한다. 출력 파일 쓰기만 실패했으면 같은 ID와 새 경로로 다시 실행할 수 있다.
- `generate`: 설정과 최신 요청을 확인하고 토큰 수 조회 → 예산 예약 → 발송 기록 → OpenAI 호출 → 원 응답 보관 → 초안 저장을 수행한다. 저장된 결과는 재사용하며 원 응답만 있으면 초안 저장만 다시 처리한다. 발송 기록이 있고 응답이 없으면 재호출하지 않는다.
- `complete`: 별도로 확보한 규칙 JSON을 저장한다. 외부 호출을 실행하지 않는다.
- `status`: 후보 상태·초안 ID·예약 상태·최대 예약액·원 응답 보관 여부를 조회한다. 본문과 인증키는 출력하지 않는다.

명령은 정기 수집·알림·이메일 발송을 비활성화한다. `generate`만 외부 API를 호출한다. 새 UUID를 준비하는 것은 새 추출 요청이며, 같은 공고라도 추가 비용이 발생할 수 있다. 명시적 재시도에만 사용한다.

## OpenAI 설정과 비용

루트 `.env`의 예시는 [.env.example](../../.env.example)에 있다. API 키를 채팅·커밋·로그에 남기지 않는다. 설정이 없거나 `AI_ENABLED=false`이면 외부 호출을 차단한다.

| 설정 | 의미 |
|---|---|
| `AI_ENABLED`, `OPENAI_API_KEY` | 실제 호출 활성화와 서버 전용 API 키 |
| `OPENAI_MODEL` | Responses·입력 토큰 조회·JSON mode를 지원하는 모델. 가격을 확인한 고정 모델 ID 권장 |
| `AI_MONTHLY_LIMIT_WON` | 한국 시간 월별 AI 한도. 0원 초과, 최대 3만 원. 전체 운영비에서 AI에 배분한 금액을 사용 |
| `AI_INPUT_WON_PER_MILLION`, `AI_OUTPUT_WON_PER_MILLION` | 백만 토큰당 원화 상한 단가. 모델별 표준 요금·환율·세금 여유분을 반영하고 캐시 할인은 차감하지 않음 |
| `AI_PRICING_VERSION`, `AI_PRICING_VALID_UNTIL` | 가격 근거 식별자와 ISO-8601 UTC 유효 종료 시각 |
| `AI_MAX_OUTPUT_TOKENS` | 출력 상한. 1~16384. 추론 토큰도 이 상한에 포함 |

최대 예약액은 `(입력 토큰 × 입력 단가 + 출력 상한 × 출력 단가) / 1,000,000`을 소수 6자리에서 올림한 금액이다. 토큰 조회 실패·단가 누락·요금 만료·잔액 부족에는 생성 요청을 보내지 않는다. 월 예산이 이미 있으면 설정값으로 덮어쓰지 않는다. 월 경계 또는 요금 만료 후 발송하려는 예약은 취소한다. 예약·발송 직전·결과 저장 단계에서 공고와 요청의 최신성을 확인한다.

`service_tier=default`, `store=false`를 사용하며 도구·검색·이전 대화를 보내지 않는다. 동적 질문 ID 맵을 유지하기 위해 JSON mode와 기존 서버 규칙 검증을 사용한다. 참고: [입력 토큰 조회](https://developers.openai.com/api/docs/guides/token-counting), [JSON mode와 출력 검사](https://developers.openai.com/api/docs/guides/structured-outputs).

응답의 토큰 사용량은 실제 원화 청구액이 아니다. 정상·거절·HTTP 오류 응답도 청구 확인 전에는 `DISPATCHED`로 예약액을 유지한다. 연결 유실은 `OUTCOME_UNKNOWN`으로 기록한다. 발송 기록 직후 프로세스가 중단된 경우도 자동 재호출하지 않는다. 실제 청구 상한 준수는 모델 요금·사용량·세금·환율을 확인해야 한다.

공급자 청구나 무과금을 확인한 뒤 아래 명령으로 기존 예약을 정리한다. 확인 ID는 근거를 추적할 수 있는 식별자를 사용한다. 재실행할 때 ID·시각·금액을 그대로 사용하면 중복 정산하지 않는다. HTTP 오류·토큰 예상액만으로 무과금이나 실제 청구액을 확정하지 않는다.

```sh
npm run ai:policy-rules -- --args='settle <요청UUID> <청구확인ID> <확인시각> <원화청구액>'
npm run ai:policy-rules -- --args='no-charge <요청UUID> <무과금확인ID> <확인시각>'
```

예약액보다 청구액이 크면 기존 정산 저장소가 초과 금액도 기록한다. 이후 잔액 부족은 새 생성을 차단한다. 응답이 없던 요청을 무과금으로 해제해도 같은 UUID를 다시 보내지 않으며 필요한 재시도는 현재 공고로 새 요청을 준비한다.

## 저장 구조

- Flyway V26의 `policy_ai_rule_requests`: 요청 UUID·순번·정책/개정·원문 해시·생성 방식·요청자·준비 시각. 기존 `policy_revisions`를 참조한다.
- `policy_ai_rule_candidates`: 요청별 본문·SHA-256·처리 상태·초안 ID·기록 시각. 요청과 결과는 수정할 수 없으며 같은 요청에 후보 하나만 둔다.
- V27의 `policy_ai_rule_calls`: 예산 예약 참조·실제 전송 내용·입력 토큰 수·단가·HTTP 상태·원 응답을 보관한다. 전송 내용과 단가는 변경할 수 없고 응답은 한 번만 기록한다. 원 응답 한도는 1MB이며 초과 시 결과 미확인으로 남긴다. 128KB를 넘는 추출·미완료·거절·오류는 짧은 실패 사유를 후보로 기록하고 원 응답은 호출 기록에 남긴다.
- 기존 예산 실행 조정자와 예약 수명 주기를 사용한다. 공고 잠금과 발송 기록은 짧은 트랜잭션으로 처리하고 외부 API는 그 밖에서 호출한다. 원 응답 저장 후 초안 저장에 실패하면 `generate`로 보관한 응답만 다시 처리한다.
- 예산 모델에 연결하는 원본 이름 공간은 `ontong-catalog-revision`이다. 내부 관찰 순번에는 카탈로그 개정을 사용하며 실제 외부 수집 요청 순번으로 해석하지 않는다. 원본 참조는 스냅샷 ID와 저장된 원문 JSON의 SHA-256, 내용 비교는 해당 개정의 해시다.
- 규칙 정의와 판정 검사는 기존 `PolicyRuleDefinition`·`PolicyRuleStore`를 사용한다. 형식 검사 로직을 새로 복제하지 않는다.

| 운영 명령·로컬 서버 | 빈 요청 UUID로 `status` 실행·V27 적용·정상 기동·상태 조회 200 확인. `/tmp/youth-openai-rule-command.log`, `/tmp/youth-openai-rule-runtime.log` |

마지막 검증 이후 변경은 문서뿐이다. 로컬 실제 데이터는 정책 40건·적용 규칙 11건·AI 요청/호출 0건을 확인했다. 키·모델·요금·한도가 없어 실제 OpenAI 호출과 생성 품질·청구는 검증하지 않았다. 테스트의 모델·가격·응답은 인공 값이며 운영 권장값이 아니다.

화면·HTTP 계약·생성 타입은 변경하지 않았다. 기존 관리자 API를 통해 AI 초안이 조회되고 공개 질문은 적용 전까지 바뀌지 않음을 통합 테스트로 확인했다. 웹 검증은 이전 `e05fa3d` 결과를 유지한다. 실제 관리자 로그인·원격 CI·배포는 이번 작업에서 실행하지 않았다.
