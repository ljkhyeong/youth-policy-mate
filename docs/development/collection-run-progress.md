# 수집 실행 진행·실패·재처리 모델

2026-08-31 구현 기준. [수집 진행 설계](../design/collection-run-progress.md)에 따라 페이지·항목별 시도와 재처리 위치를 계산하는 순수 Java 모델을 추가했다. 인증키·외부 API·DB 없이 확인한 내부 동작이며 운영 수집기나 서버 재시작 복구 기능이 아니다.

## 코드와 사용 범위

코드는 `backend/src/main/java/kr/youthpolicymate/ingestion/`에 있다.

| 코드 | 역할 |
|---|---|
| `CollectionPosition` | 페이지 내부 참조와 페이지 안의 항목 위치 |
| `CollectionAttempt` | 실행·위치·시도 번호, 시작·종료 시각, 페이지/항목 결과·실패·중단 이력 |
| `CollectionRun` | 등록 작업, 명시적 범위 종료, 시작·결과 기록·중단·재개와 다음 불변 상태 |

`CollectionRun.start(runId, firstPage, startedAt)`로 시작한다. 호출 측은 다른 실행에 같은 ID를 재사용하지 않아야 한다. 이 모델에는 실행 ID 발급·전역 중복 검사가 없다.

- `begin(position, at)`는 새 시도 식별값과 다음 상태를 반환한다. 이미 진행 중이거나 완료·검토 필요인 작업은 다시 시작하지 않는다.
- `record(attemptId, result)`는 기록 여부와 다음 상태를 반환한다. 페이지 성공은 원본 참조·항목 목록·다음 페이지 또는 명시적 종료를 함께 받는다. 외부 응답을 직접 해석하지 않는다.
- `pause(at)`는 진행 중 시도를 중단 기록으로 닫는다. `resume()`는 새 시도를 허용할 뿐 실제 요청을 보내지 않는다. 호출자는 매번 반환 상태를 사용해야 한다.
- `resumeTargets()`는 시작 전·실패·중단 위치, `reviewTargets()`는 검토 필요 위치를 등록 순서로 반환한다. 대기 중인 위치와 이미 진행 중인 위치를 구분한다.
- `attempts(position)`는 실패·중단을 포함한 해당 위치의 전체 시도 목록이다. 페이지 성공 원본은 페이지 시도에, 실패 시 확보한 원본 참조는 실패 결과에 남는다.
- `finishedAt()`는 범위 종료와 등록 작업 완료를 모두 확인했을 때 마지막 종료 시각을 제공한다. 원천의 마지막 수정 시각이나 전체 정책의 최신성은 아니다.

결과 기록 결정은 `RECORDED`, `REPLAYED`, `STALE`, `CONFLICT`다. 이전 시도·중단한 시도의 결과는 `STALE`로 유지 상태를 반환한다. 같은 종료 결과(시각 포함)는 재전달, 같은 시도의 다른 결과는 충돌이다. 다른 실행·미등록 위치·미발급 시도 번호는 입력 오류다.

실행 상태는 `PAUSED`, `RETRY_REQUIRED`, `RUNNING`, `COMPLETED_WITH_REVIEW`, `COMPLETED`로 구분한다. 실패가 있어도 등록된 다른 작업을 시작할 수 있다. 마지막 페이지를 읽었어도 실패·미처리 항목이 남으면 완료가 아니다. 검토 필요는 자동 재시도 대상에서 제외한다.

`PageFetched`·`ItemProcessed`는 호출 측이 알려주는 처리 결과다. `PolicyRevisionState`를 호출하거나 정책·개정·AI 결과를 저장하는 기능은 없다. `SnapshotReference`도 기존 정책 모듈의 참조 값만 재사용하며 본문을 저장하지 않는다. 항목 참조는 정책 ID가 아니고, 시도 번호는 정책별 수집 순번이 아니다.

## 검사

저장소 루트에서 실행한다.

```sh
npm run test:ingestion
npm run check:backend
```

첫 명령은 인증키·DB·Docker 없이 새 테스트 12건을 실행한다. 전체 서버 빌드는 기존 PostgreSQL 통합 테스트 때문에 Docker가 필요하다. 새 테스트는 다음을 확인한다.

- 등록한 작업만 시작하고 진행 중 작업은 중복 시작하지 않음
- 빈 페이지와 명시적 범위 종료의 구분
- 일부 항목 실패 후 나머지 항목·페이지 처리, 실패 위치만 재시도
- 페이지 실패 시 항목·종료를 만들지 않고 재시도 이력 보존
- 중단한 시도만 닫고 성공 기록 유지, 재개 전후의 늦은 응답 무시
- 페이지 결과 재전달·충돌에 항목 목록과 원본 유지
- 검토 필요와 정상 완료의 구분, 페이지별 항목 위치 분리
- 다른 실행·미발급 시도, 페이지 순환·중복 참조, 잘못된 결과·시각 거절
- 외부 목록 변경과 이력 조회를 통한 상태 변경 방지

전용 12건과 전체 서버 203건(도메인 188·개발 API/계약 13·실제 DB/기본 차단 2), 서버 빌드가 통과했다. 실패·건너뛰기는 최종 실행 기준 0건이다.

첫 전체 실행에서는 임시 PostgreSQL의 JDBC 연결 중 `EOFException`이 발생해 기존 통합 테스트 2건이 실패했다. 코드·설정·테스트를 바꾸거나 건너뛰지 않고 같은 전체 명령을 새 임시 DB로 재실행해 통과했다. 연결이 끊긴 근본 원인은 확정하지 않았다. Gradle 캐시·Docker 접근에 권한 확장을 사용했다.

화면·API 계약·DB 스키마는 변경하지 않았고 웹 테스트·브라우저·타입 재생성은 다시 실행하지 않았다. 기존 웹 53건은 앞선 검증 기록이다. 실제 온통청년 호출·GitHub 푸시·배포는 하지 않았다.

## 아직 구현하지 않은 기능

- 실제 원천 목록·상세 호출과 페이지 커서·종료 신호 해석
- 실행 필터·원본 본문 보관, 저장소 재조회·프로세스 재시작 복구
- Spring Batch 실행, 동시 작업자 소유권·임대 만료·원자적 DB 갱신
- 항목 처리와 정책 개정 반영의 연결·멱등 저장, AI·일정·알림 후속 처리
- 재시도 한도·대기 시간·운영 알림, 검토 사유 상세·수동 검토 완료 절차

실행 하나의 전체 이력을 복사하는 현재 모델을 대량 수집 저장소로 사용하지 않는다. 실제 실행에는 제한된 작업 단위와 DB 조회·저장이 필요하다. 실패나 목록 부재를 정책 삭제·비공개로 처리하는 동작은 없다.

실제 DB 복구·중복 정책·개정·알림 방지까지 확인한 것이 아니므로 PRD AC-05 완료로 보고하지 않는다. [원천 성공 계약 확인](../research/ontong-api-contract.md#8-유효-인증키-확보-후-필요한-최소-확인) 전에는 운영 수집기·확정 DTO·Flyway DDL을 만들지 않는 기준을 유지했다.
