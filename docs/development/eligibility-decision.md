# 자격 판정 결과 집계

2026-08-30 구현 기준. 제품 규칙은 [PRD 5절](../PRD/0001_product-baseline/spec.md#5-자격-안내와-추천-근거), 서버 책임은 [ADR-0001](../ADR/0001_기술스택과_책임_분리.md)을 따른다.

## 현재 구현 범위

`backend/src/main/java/kr/youthpolicymate/eligibility/`에 순수 Java 모델을 추가했다. 개별 조건을 이미 비교한 결과와 정책 검토 상태를 받아 최종 자격 안내 상태를 계산한다. API 인증키, Spring 실행, DB, 외부 호출은 필요하지 않다.

이 집계 모델 자체는 원문을 해석하거나 사용자 값과 조건을 직접 비교하지 않는다. 같은 패키지에 [연령](age-condition.md)·[거주](residence-condition.md)·[단일 취업 조건](employment-condition.md)·[소득 구간](income-condition.md) 비교기를 추가했다. HTTP API, JSON 직렬화 계약, DB 저장, 화면 연결은 추가하지 않았다. `/conditions`의 입력값을 서버로 보내거나 이 모델로 판정하지 않는다.

별도로 [자격 결과·근거 표시 컴포넌트](eligibility-result-preview.md)를 구현했다. 개발 전용 인공 결과를 표시하며 서버 모델·API와 연결하지 않았다. 화면은 전체 상태를 다시 집계하지 않고, 모집 상태와 정책 검토 이슈를 구분해 보여준다.

## 결과와 근거 구조

| 모델 | 보존하는 내용 |
|---|---|
| `EvaluationBasis` | 정책 식별자, 서비스가 적용한 정책 개정, 규칙 버전, 명시적으로 전달한 판정 시점 |
| `SourceEvidence` | 원문 자료 참조, 확인한 필드·본문 위치, 존재하는 경우 원문 발췌 |
| `ConditionAssessment` | 조건 식별자, 적용 조건 설명, 비교값, 해당 조건의 기준일, 항목 결과, 미확인 원인, 이유와 근거 |
| `PolicyReview` | 필수 조건·예외의 검토 범위가 모두 반영됐는지 여부와 아직 반영하지 못한 항목의 설명·근거 |
| `EligibilityDecision` | 위 자료와 항목 목록, 이를 이용해 계산하는 최종 상태와 안내 문구 |

식별자와 개정은 아직 영속성 계약이 없는 내부 문자열이다. 원천 API가 제공하는 개정 번호나 스냅샷 저장 경로를 확정한 것이 아니다. 비교값도 화면에 근거를 설명하기 위한 문자열이지 숫자·날짜 비교에 재사용할 규칙 입력이 아니다. 연령은 나이 정의·범위·기준일, 거주는 주민등록상 거주 범위·기준일, 취업은 단일 사실의 정의·요구 방향·기준일을 보존한다. 소득은 확인한 원화 구간, 소득 정의·대상·기간·적용 기준으로 비교하며 산정·원천 해석은 하지 않는다.

원문 발췌·사용자 비교값·조건 기준일은 값의 부재를 명시한다. 빠진 원문이나 날짜를 임의의 문구·오늘 날짜로 채우지 않는다. `UNKNOWN` 항목은 사용자 정보 누락(`MISSING_USER_INPUT`)과 정책 자체의 해석 불가(`UNRESOLVED_POLICY`)를 구분한다. 구체적인 미확인 내용은 `explanation`과 원문 근거에 남긴다.

각 조건은 정책에 적용되는 필수 요건 하나의 비교 결과다. OR 조건·예외를 아직 풀지 못한 하위 항목을 독립적인 필수 요건 불충족으로 넣지 않는다. 복합 조건을 해석할 수 없으면 정책 미확인으로 남긴다.

## 최종 상태를 계산하는 순서

| 순서 | 조건 | 결과 |
|---|---|---|
| 1 | 정책 검토 범위가 미완료이거나, 항목이 없거나, 정책 조건 자체가 미해석 상태 | `NEEDS_REVIEW` — 추가 확인 필요 |
| 2 | 위 문제가 없고 명확한 필수 조건 불충족이 하나 이상 있음 | `INELIGIBLE` — 조건 불충족 |
| 3 | 불충족은 없지만 필요한 사용자 정보가 빠진 항목이 있음 | `NEEDS_REVIEW` — 추가 확인 필요 |
| 4 | 검토 범위가 완료되고 비어 있지 않은 모든 항목이 충족 | `ELIGIBLE` — 입력 조건 기준 신청 가능 |

다른 사용자 정보가 없다는 이유로 명확한 필수 조건 불충족을 숨기지 않는다. 반면 미해석 정책 조건·예외는 불충족 판단을 바꿀 가능성이 있으므로 먼저 추가 확인으로 분류한다. 원문 해석이 없는 현재 단계에서는 정책 미해석의 영향을 임의로 좁히지 않는다.

검토 완료 표시는 일부 코드가 파싱됐다는 뜻이 아니다. 향후 원문 해석기가 추가사항·참여제한·신청 주체 등 검토 범위를 모두 확인한 뒤 각 항목 또는 검토 이슈로 빠짐없이 반영해야 한다. 개별 항목에 정책 미해석이 남아 있다면 검토 완료 표시가 있어도 신청 가능이나 불충족으로 확정하지 않는다.

최종 상태를 생성자에서 직접 받지 않아 개별 근거와 따로 덮어쓸 수 없다. 조건과 검토 이슈 목록은 복사해 보존하며, 같은 조건 ID의 중복은 거절한다. 정책 검토 미완료에는 확인할 항목을 요구하고, `UNKNOWN`에는 원인 구분을 요구한다.

## 시간·개인정보·모집 상태

- 코드 안에서 `now()`를 호출하지 않는다. 집계 모델은 전달받은 판정 시점을 보존하고, 연령 비교기는 명시적으로 전달받은 생년월일·정책 기준일로 계산한다. 현재 시각에 의존하지 않아 `Clock`이 필요하지 않다. 향후 오늘 날짜 등을 선택하는 계층에는 `Clock`과 필요한 시간대를 명시한다.
- 조건별 기준일과 판정 시점은 다를 수 있다. 하나의 오늘 날짜로 모든 조건을 덮어쓰지 않는다.
- 거주 비교기도 명시적인 날짜만 사용한다. 입력된 거주 정보의 기준일이 정책 기준일과 다르면 과거·현재 거주를 추정하지 않고 `MISSING_USER_INPUT`으로 보류한다.
- 취업 답변도 정책·개정·조건 ID·정의·기준일이 모두 일치해야 사용한다. 다르면 현재 조건에 대한 답변 부족으로 보류하며 이전 답변을 현재 비교값에 복사하지 않는다.
- 소득 답변도 같은 정책·개정·정의·대상·기간·가구·적용 기준에서만 비교한다. 소득 기간과 기준표 연도는 실제 기준일과 별도로 보존하며 일부만 겹치는 구간은 `MISSING_USER_INPUT`으로 남긴다.
- 비교값과 판정 이유에는 개인정보가 포함될 수 있다. 결과 객체 전체를 로그·분석 이벤트에 넣지 않는다. 현재 로깅·외부 전송·저장은 없다.
- 모집 상태는 이 서버 결과 모델에 넣지 않았다. 화면 컴포넌트는 별도 모집 안내를 받으며 인공 예시의 모집 종료·모집 중을 구분해 표시한다. 실제 API의 접수 전·마감·상시·기간 미확인 표현과 계산은 아직 없다. `ELIGIBLE`만으로 현재 신청 접수가 가능하다고 안내하지 않는다.
- 내부 enum과 record는 확정 REST 계약이 아니다. API를 만들 때 전체 상태·항목·근거의 직렬화를 명시하고 생성 TypeScript 계약으로 연결한다.

## 검증과 한계

저장소 루트에서 실행한다. 최초 Gradle 의존성 준비 후에는 인증키·DB·Docker 없이 해당 단위 테스트를 실행할 수 있다.

```sh
npm run test:eligibility
./backend/gradlew -p backend assemble --no-daemon
```

2026-08-30에 단위 테스트 14건(매개변수별 실행 포함)이 실패·건너뛰기 없이 통과했고 백엔드 `assemble` 빌드도 통과했다. 테스트는 빈 조건, 전체 충족, 명확한 불충족, 사용자 정보 누락, 정책 해석 불가, 예외 우선 처리, 근거·개정·시점 보존, 중복·모순 상태 방지를 확인한다. DB·웹 코드는 바꾸지 않아 기존 PostgreSQL 통합 테스트와 프런트엔드 검사는 이번 작업에서 다시 실행하지 않았다.

이후 CI 구성 작업에서 전체 서버 `build`를 실행했고 단위 14건과 기존 PostgreSQL 통합 2건이 모두 통과했다. 웹 검사도 다시 통과했다. [CI 검증 기록](ci.md)에 로컬 확인과 아직 실행하지 않은 GitHub 검사를 구분했다.

이후 연령 비교기를 추가한 작업에서는 연령 18건과 기존 집계 14건, 총 32건 및 서버 `assemble`이 통과했다. 웹·PostgreSQL 통합 검사는 이 작업에서 다시 실행하지 않았다. 연령 계산 방식과 미지원 조건은 [연령 비교 검증 기록](age-condition.md#코드와-검증)을 따른다.

이후 거주 비교기를 추가한 작업에서는 거주 17건·연령 18건·집계 14건, 총 49건과 서버 `assemble`이 통과했다. 웹·PostgreSQL 통합 검사는 다시 실행하지 않았다. 전국·서울·자치구 범위와 기준일 처리의 한계는 [거주 비교 검증 기록](residence-condition.md#코드와-검증)을 따른다.

이후 단일 취업 비교기를 추가한 작업에서는 취업 21건·거주 17건·연령 18건·집계 14건, 총 70건과 서버 `assemble`이 통과했다. 웹·PostgreSQL 통합 검사는 다시 실행하지 않았다. 명시적 답변, 정책 개정·정의·기준일 확인과 미해석 처리 범위는 [취업 비교 검증 기록](employment-condition.md#코드와-검증)을 따른다.

이후 소득 구간 비교기를 추가한 작업에서는 소득 47건을 더해 총 117건과 서버 `assemble`이 통과했다. 웹·PostgreSQL 통합 검사는 다시 실행하지 않았다. 구간 경계·입력 기준 일치·미해석 처리의 범위는 [소득 비교 검증 기록](income-condition.md#코드와-검증)을 따른다.

[조사 문서](../research/ontong-api-contract.md)의 학력 제한없음과 대학생 참여 불가가 함께 나온 사례, 전국 분류와 동아리 신청 요건이 함께 나온 사례의 위험도 재현한다. 테스트 자료는 수동으로 구성한 집계 입력이며 실제 API 성공 응답이나 원문 파서 검증이 아니다. 테스트 통과를 실제 정책 판정 정확도·자동 판정 가능 비율로 보고하지 않는다.

## 다음 연결 지점

- 인증키 없는 [CI 구성](ci.md)과 [공통 상태 화면](page-states.md)은 구현했다. 첫 GitHub 실행과 실제 정책 조회 연결은 남아 있다.
- 명시적 연령·거주·단일 취업·소득 구간 비교는 구현했다. 실제 정책 자료를 확보하면 원천 코드, 각 조건 정의·기준일·예외를 확인한 뒤 연결한다. AI 후보를 곧바로 `MET`·`NOT_MET`으로 넣지 않는다. 소득 산정·복합 취업 조건 비교는 아직 없다.
- 취업 입력과 후속 질문은 [취업 조건 설계](../design/employment-condition.md)를 따른다. 현재의 주된 상태 문자열을 확정된 취업 사실이나 다른 상태의 부정 답변으로 변환하지 않는다.
- 소득 입력과 구간 경계는 [소득 조건 설계](../design/income-condition.md)를 따른다. 의미가 맞는 구간 일부만 정책 범위에 겹치면 사용자 정보 부족이며, 정의·기준표·방식이 미확인이면 정책 미해석으로 보류한다. 소득 비교기와 [개발 전용 질문 미리보기](income-question-preview.md)는 각각 구현했지만 실제 정책·판정 연결, 원천 매핑·단위 변환·기준표 산정은 아직 없다.
- 실제 결과 API를 구현할 때 조건 입력·정책 개정·규칙 버전의 소유 경계를 정하고 근거와 모집 상태를 화면에서 함께 안내한다.
- 결과 표시 컴포넌트와 개발 미리보기는 구현했다. 화면의 표시용 타입은 확정 API 계약이 아니며, 실제 결과 변환·입력 변경 후 재판정 연결은 후속 작업이다. [결과 화면 검증 기록](eligibility-result-preview.md#검증-결과와-한계)에 웹 24건과 브라우저 확인 범위를 정리했다.
