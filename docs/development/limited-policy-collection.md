# 한 페이지 정책 수집과 저장 원본 재처리

2026-09-05 구현. [PRD의 수집·실패 처리](../PRD/0001_product-baseline/spec.md#6-정책-수집공개변경-처리)와 [ADR-0001](../ADR/0001_기술스택과_책임_분리.md)에 따라 Spring Batch 6.0.5와 PostgreSQL 실행 이력을 연결했다. 지정한 서울 필터 페이지를 한 번 요청하고 최대 10건을 기존 정책 목록에 반영한다. 정기 실행·전체 페이지 순회·전체 서울 정책 확보는 아직 제공하지 않는다.

## 실행

저장소 루트 `.env`의 `ONTONG_API_KEY`와 로컬 PostgreSQL을 사용한다. 인증키를 명령 인자에 넣지 않는다.

```sh
npm run db:up
npm run collect:policy -- --args='fetch 2'
npm run collect:policy -- --args='status'
```

`fetch`는 페이지 번호 1~1000 중 하나를 받아 새 실행 ID를 발급한다. 실제 원천 페이지 수는 이 입력 상한과 다르다. `zipCd=11000`, `pageSize=10`, `pageType=1`, `rtnType=json`은 고정이다. 다음 페이지를 자동 호출하지 않으며, 애플리케이션의 자동 재시도는 없다.

실행 결과에 표시된 UUID로 항목별 결과를 확인하거나 보관 원본을 재처리한다.

```sh
npm run collect:policy -- --args='status <실행 UUID>'
npm run collect:policy -- --args='replay <실행 UUID>'
```

- `status`는 최근 실행 10개, UUID를 지정하면 해당 실행과 최대 10개 항목의 현재 결과를 출력한다. 외부 API를 호출하지 않는다.
- `replay`는 보관한 응답으로 미처리·표시 오류·저장 실패 항목만 다시 처리한다. 성공 항목의 개정을 다시 만들지 않으며 외부 API를 호출하지 않는다. 코드 수정 후 표시 오류를 재검사할 때도 사용한다.
- HTTP 오류나 프로세스 종료로 원본이 남지 않은 실행은 재처리할 수 없다. 새로 가져오려면 별도 `fetch` 실행이 필요하다. 기존 실행 ID로 요청을 다시 보내지 않는다.
- 표시 오류·저장 실패가 남거나 페이지 수집이 실패하면 종료 코드 1이다. 다른 정상 항목은 이미 커밋한 결과를 유지한다.
- 일반 웹 서버 기동이나 `preview` 실행으로 수집이 시작되지 않는다. 배치 자동 시작은 기본 설정에서 껐고, 수집 작업과 HTTP 클라이언트는 `collection` 프로필에서만 만든다.

## 저장과 실패 경계

| 저장소 | 보존하는 내용 |
|---|---|
| Flyway V11, Spring Batch `BATCH_*` | 작업 실행·단계의 시작, 완료·실패와 실행 인자. 인증키와 원문은 인자에 넣지 않음 |
| V12 `ontong_collection_pages` | 요청 전 발급한 순번, UUID, 페이지·고정 필터·주소, 요청·수신 시각, 응답 본문, 목록 형식 오류·HTTP 실패 코드, 원천 전체 건수 |
| `ontong_collection_items` | 원본 안의 항목 위치, 원본 정책, 마지막 처리 결과와 시도 횟수 |
| `ontong_collection_item_attempts` | 항목별 이전 실패와 재처리 결과. 정상 처리로 바뀌어도 실패 이력 유지 |
| 기존 정책 테이블 | 원본 스냅샷·현재 내용·적용 개정과 마지막 적용 요청 순번 |

Spring Batch는 실행 이력을 맡고, 수집 테이블은 원본과 다시 처리할 위치를 맡는다. 기존 메모리 `CollectionRun`을 DB 전체 이력 저장소로 복사하지 않았다. 한 단계에서 최대 10개만 순회하며 외부 호출과 순회에는 DB 트랜잭션을 걸지 않는다. 원본 저장·항목 등록은 각각 짧게 커밋한다. 정책 반영·항목 완료·항목 시도 기록은 같은 트랜잭션으로 커밋한다.

페이지 상태 `READY`는 원본과 처리 항목이 등록됐다는 뜻이다. 항목 실패가 남아 있으면 배치 실행은 `FAILED`이고 완료가 아니다. `FETCHING`이 오래 남아 있으면 요청 결과가 저장되지 않은 상태이며, 실제 미호출인지 응답 저장 전에 종료됐는지는 구분할 수 없다. 비정상 종료한 Spring Batch 실행의 자동 회수·주기 재시작은 아직 없지만, 응답 저장을 마쳤으면 별도 `replay` 프로세스로 남은 항목을 처리할 수 있다.

요청 순번은 외부 요청 직전에 DB에서 발급·커밋한다. 원천 개정 번호나 원천 시각을 뜻하지 않는다. 같은 내용의 후속 요청도 마지막 적용 순번을 갱신해 낮은 순번의 늦은 응답을 차단한다. 직접 수집이 적용된 정책은 순번이 없는 과거 로컬 캡처로 덮어쓰지 않는다. 보관 원본은 남는다. 정상 항목 하나의 현재 행과 해당 항목 행을 잠그므로 동시 재처리도 중복 개정·완료 기록을 만들지 않는다.

응답의 페이지 번호·페이지 크기가 요청과 다르면 정책에 반영하지 않는다. 같은 페이지에 정책번호가 중복되면 해당 번호의 항목들을 표시 오류로 남긴다. 빈 목록·부분 실패·원천 목록 부재로 기존 정책을 삭제하거나 비공개로 바꾸지 않는다. 전체 건수는 응답에 담긴 참고 값이며 모든 정책을 확보했다는 표시가 아니다.

HTTP 주소는 온통청년으로 고정하고 리다이렉트를 따르지 않는다. 연결은 10초, 응답 전체 대기는 20초, 본문은 1MiB로 제한한다. HTTP 오류 본문·깨진 JSON·인증키를 되돌려주는 본문은 보관하지 않는다. 정상 HTTP·JSON이어도 업무 오류나 목록 형식 오류가 있으면 원본은 보관하고 정책 반영은 중단한다. 외부 예외의 URL·응답 일부를 로그나 배치 오류 설명으로 전파하지 않는다.

## 확인 범위와 남은 작업

공식 공공데이터포털은 호출 가능한 트래픽이 기관 정책에 따라 다르다고 안내한다. 현재 계정의 일일·분당 수치, 페이지 정렬 안정성, 전체 서울·전국 공통 정책 포함 범위는 아직 확정하지 않았다. 숫자를 임의로 운영 한도로 채택하지 않고 수동 한 페이지 호출만 제공한다. [공식 API 정보](https://www.data.go.kr/data/15143273/openapi.do), [원천 계약 조사](../research/ontong-api-contract.md)를 참고한다.

```sh
npm run test:policy-collection
npm run check:backend
```

전용 검사는 실제 PostgreSQL에서 배치 실행·부분 실패·정책과 완료 기록의 동시 롤백·보관 원본 재처리·동시 재처리·오래된 요청 차단을 확인한다. HTTP 검사는 로컬 응답 서버로 요청 범위·리다이렉트·호출 제한·본문 크기·인증키 반사 응답 차단을 확인한다. 운영 API에 실패나 과다 호출을 일으키는 검사는 하지 않는다.

최종 전용 검사 21건(HTTP 4·수집 6·기존 캡처 4·정책 조회 7), 서버 전체 373건과 빌드가 실패·오류·건너뛰기 없이 통과했다. 첫 전용 검사에서는 테스트 자료에 같은 정책번호를 두 번 생성해 3건이 실패했다. 자료의 번호를 고친 뒤 전용 검사와 전체 검사가 통과했다. 중복 정책번호를 표시 오류로 처리하는 제품 규칙은 유지했다.

실제 호출은 2026-09-05 11:01 서울 시각에 두 번째 페이지를 한 번 요청했다. 실행 `67ecf455-1948-4440-b035-8d2d3d86b5a8`에서 10건 모두 새 개정으로 반영했고 실패는 0건이다. 응답의 전체 건수는 481이었다. 기존 10건과 합쳐 API 목록은 20건이며 새 정책 `20260716005400113260`의 상세 200과 웹 목록 노출을 확인했다. 별도 프로세스로 같은 실행을 `replay`해 정상 완료와 항목별 처리 시도 1회 유지를 확인했다. 원본과 실행 이력은 로컬 DB에 보관하며 저장소에 커밋하지 않는다.

다음 범위는 호출량 확인 후 정기 실행·페이지 순회, 실제 조건 해석·판정 연결, 로그인·관심 정책 저장이다. 원본 보관 기간·객체 저장소, 수집 실패를 공개 화면에 연결하는 안내, 비정상 종료 배치 회수와 운영 알림은 남아 있다. 이 구현만으로 PRD의 전체 수집·운영 완료를 보고하지 않는다.

기술 근거: [Spring Boot 배치 설정](https://docs.spring.io/spring-boot/reference/io/spring-batch.html), [Spring Batch Tasklet](https://docs.spring.io/spring-batch/reference/step/tasklet.html). 공식 PostgreSQL 스키마는 Spring Batch 6.0.5 배포본을 V11로 고정했다.
