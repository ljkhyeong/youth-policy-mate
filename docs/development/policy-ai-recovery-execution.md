# AI 예약 인공 복구 조정자와 상태 변경 펜싱

2026-09-01 구현 기준. [복구 소유권 설계](../design/ai-reservation-recovery.md)에 따라 미완료 AI 예약을 선택하고, 인공 확인 결과를 활성 임대 안에서만 적용한다. 실제 공급자 조회 어댑터와 자동 작업자는 없다.

## 구성과 흐름

| 구성 | 역할 |
|---|---|
| `PolicyAiRecoveryPort` | 기존 호출·청구 상태를 AI 응답 발견, 확인된 청구, 확인된 무과금, 호출 전 중단, 확인 실패, 수동 검토로 분류 |
| `PolicyAiRecoveryCoordinator` | 호환용 다음 예약 획득 또는 배정된 시도 확인, 현재 예약 조회, 트랜잭션 밖 확인, 결과 적용 순서 조율 |
| `PolicyAiRecoveryApplier` | 예약 상태 변경과 복구 시도 완료를 한 트랜잭션으로 처리 |
| `AiBudgetReservationLifecycleStore.*UnderRecovery` | 활성 시도와 관찰한 예약 상태를 다시 확인한 뒤 정산·해제·취소 |

호환 경로인 `recoverNext`는 `claimNext`로 소유권을 얻는다. 재확인 정책을 적용하는 경로는 작업 배정이 반환한 `ReadyClaimed`를 `recoverAssigned`에 전달한다. 조정자는 DB에서 같은 시도를 다시 읽고 저장된 값이 그대로 `ACTIVE`인지 확인한다. 이미 완료·교체된 시도라면 외부 확인을 호출하지 않는다.

활성 시도는 현재 예약 단계와 갱신 시각을 읽은 뒤 `PolicyAiRecoveryPort.inspect`로 전달한다. 이 호출 동안 Spring 트랜잭션은 열려 있지 않다. 확인이 끝나면 주입한 `Clock`에서 실제 적용 시각을 읽고 다음 항목을 잠가 확인한다.

- 시도 ID·예약 ID·예약별 시도 순번·작업자 일치
- 시도가 `ACTIVE`인지와 적용 시각이 임대 만료 전인지
- 외부 확인 전에 읽은 예약 단계·갱신 시각이 그대로인지

확인된 청구는 `SETTLED`, 확인된 무과금은 `RELEASED_NO_CHARGE`, 호출 전 중단은 `CANCELLED`로 바꾼다. 확인 실패와 수동 검토는 예약 상태와 예약액을 유지하고 복구 시도 결과만 기록한다.

`ResponseFound`는 AI 결과와 그 응답의 청구 상태를 함께 반환한다. 청구가 대기 중이면 예약은 `DISPATCHED`와 예약액을 유지하고 복구 시도만 `CHECK_COMPLETED`로 끝낸다. 청구·무과금이 확정되면 기존 펜싱 안에서 정산·해제를 함께 적용한다. 복구한 응답 시각이 최초 호출보다 빠르면 적용하지 않는다.

## 보수적인 실패 처리

- 외부 확인 중 새 임대가 시작되면 오래된 작업자의 결과를 적용하지 않는다.
- 외부 확인 중 예약 상태가 바뀌면 결과를 적용하지 않고 `MANUAL_REVIEW_REQUIRED`로 남긴다.
- 예상하지 못한 포트 예외는 예약 상태와 활성 시도를 그대로 둔다. 임의의 무과금·정상 완료로 바꾸지 않는다.
- 완료한 같은 시도의 재전달은 포트를 다시 호출하지 않는다.
- 배정 뒤 시도가 완료·교체됐으면 포트를 호출하지 않는다.
- 배정 뒤 예약이 종료됐으면 포트를 호출하지 않고 수동 검토로 시도를 완료한다.
- 상태 변경이 성공했는데 시도 완료가 실패하면 전체 트랜잭션을 되돌린다.

복구 조정자가 기록하는 `CHECK_COMPLETED`는 확인 결과를 예약 상태에 적용했거나 청구 대기 응답의 존재를 확인했다는 내부 기록이다. AI 후보가 최신 정책에 맞고 사용자에게 제공 가능하다는 뜻이 아니다. 후속 [결과 연결](policy-ai-candidate-projection.md)이 `ResponseFound`와 완료 상태를 확인한 뒤 현재 정책·최신 요청을 다시 검사한다.

후속 [재확인 정책](ai-reservation-recovery-retry-policy.md)은 예약이 여전히 미완료일 때 활성 임대·시도 간격·최대 횟수·수동 검토를 구분한다. [내부 운영 조회](ai-reservation-recovery-operations-query.md)는 오래된 대상과 전체 이력에 이 판단을 적용하고 [작업 배정](ai-reservation-recovery-work-assignment.md)은 현재 상태를 잠근 뒤 다시 확인해 활성 시도를 만든다. `recoverAssigned`는 이 시도를 인공 확인·펜싱 적용 경로에 연결한다. [제한 목록 실행](ai-reservation-recovery-work-runner.md)은 한 조회 결과의 보류·중단 후보를 건너뛰고 준비된 후보를 순서대로 이 경로에 전달하며 [작업 실행 기록](ai-reservation-recovery-work-runs.md)은 실행 ID와 결과 집계를 저장한다. 주기 스케줄러는 아직 없으므로 자동 반복 실행을 구현한 것은 아니다.

## 검사

저장소 루트에서 실행한다.

```sh
npm run test:ai-recovery-execution
npm run check:backend
```

복구 조정자 전용 14건은 실제 PostgreSQL 18.6 Testcontainers에서 다음 경계를 확인한다.

- 결과 미확인 예약의 AI 응답·확인된 비용 정산과 트랜잭션 밖 조회
- AI 응답을 찾았지만 청구가 대기 중일 때 예약액 유지와 확인 완료
- 확인된 무과금 해제와 호출 전 예약 취소
- 확인 실패·수동 검토의 예약액 유지
- 외부 확인 중 교체된 임대의 오래된 작업자 차단
- 임대 만료 시각과 같은 결과 적용 차단
- 외부 확인 중 변경된 예약 버전의 결과 적용 보류
- 완료 시도 재전달의 외부 조회 차단
- 복구 대상 없음의 외부 조회 차단
- 예상하지 못한 조회 오류의 활성 임대·예약액 유지
- 배정된 시도의 중복 소유권 획득 없는 트랜잭션 밖 확인
- 배정 뒤 완료·교체된 시도의 외부 확인 차단
- 배정 뒤 종료된 예약의 공급자 확인 생략과 수동 검토 완료

전용 14건과 재확인 정책 11건, 내부 운영 조회·작업 배정·수동 검토 재개 연결 11건, 제한 목록·작업 실행 기록·운영 중단·시도 연결 18건과 전체 서버 334건이 실패·오류·건너뛰기 없이 통과했고 빌드도 성공했다. 화면·API 계약은 변경하지 않았고 Flyway V7까지 적용했다.

## 남은 작업

- 실제 공급자 상태 조회 결과와 내부 결과의 검증 가능한 매핑
- 스케줄러와 실제 운영 간격·최대 횟수
- 인증·권한을 갖춘 관리자 수동 검토 재개 명령 연결
- 같은 활성 배정의 중복 실행에 대한 공급자 조회 멱등 계약
- 공급자 확인 근거와 인증·권한이 있는 운영 노출
- 후보 상태의 PostgreSQL 저장과 저장 직전 현재 정책 개정 재검사
