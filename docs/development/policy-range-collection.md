# 정책 범위 수집과 정기 실행

2026-09-05 구현. 기존 [한 페이지 수집](limited-policy-collection.md)의 Spring Batch 작업·원본 보관·항목 재처리를 여러 페이지에 연결했다. [PRD 6절](../PRD/0001_product-baseline/spec.md#6-정책-수집공개변경-처리), [ADR-0001](../ADR/0001_기술스택과_책임_분리.md)을 기준으로 한다.

## 설정과 실행

루트 `.env`의 온통청년 키와 로컬 DB를 사용한다. 범위 수집 전 다음 두 값을 함께 설정해야 한다. 기본값 0은 미설정이며 범위·정기 수집을 실행할 수 없다. 모든 수집 프로세스는 같은 한도와 간격을 사용해야 한다.

| 설정 | 단위·의미 |
|---|---|
| `ONTONG_COLLECTION_DAILY_LIMIT` | 서울 날짜별 DB 요청 예약 수 상한. 양수 |
| `ONTONG_COLLECTION_INTERVAL_SECONDS` | 새 요청 예약과 실제 발송 시작의 최소 간격, 초. 양수 |

숫자는 공식 계정의 호출 한도를 확인하고 정한다. 이 애플리케이션의 DB에 기록되지 않은 점검 도구·다른 서비스의 호출은 집계하지 않으므로 공급자 계정 전체 사용량으로 해석하지 않는다. 실패·결과 미확인·발송 전 중단도 이미 예약한 요청 수에 포함한다. `replay`와 저장 원본 재처리는 새 호출을 쓰지 않는다.

```sh
npm run collect:policy -- --args='range 3 4'
npm run collect:policy -- --args='range-status'
npm run collect:policy -- --args='range-status <범위 UUID>'
npm run collect:policy -- --args='range-resume <범위 UUID>'
```

- `range <처음> <마지막>`: 양끝을 포함한 1~1000 페이지 범위다. 서울 필터·페이지당 최대 10건은 기존과 같다. 실행 UUID를 출력하고 페이지마다 진행 위치를 커밋한다. 호출 간격을 기다리며 순서대로 실행한다.
- 같은 DB에서 활성·보류 중인 범위는 하나만 둔다. 다른 범위를 중복 시작하면 거절한다.
- 일일 한도에 도달하면 위치를 유지하고 명령이 종료 코드 1로 끝난다. 다음 서울 날짜에 `range-resume`으로 이어 간다. 정기 실행 중인 범위는 다음 날짜에 자동으로 이어 간다.
- 응답이 저장돼 있으면 `range-resume`은 원본을 다시 처리한다. 완료한 항목에는 새 처리 시도나 개정을 만들지 않는다. 원문 자체가 깨진 항목은 재처리해도 확인 필요로 남을 수 있다.
- 부분 실패한 범위도 완료 페이지를 보존한다. `range-resume`은 첫 미완료 페이지부터 저장 원본을 확인하고 기존 완료 페이지를 건너뛴다.
- 상태 조회는 최근 10개 범위와 완료 페이지·확인 필요·마지막 정상 처리 시각을 보여준다. UUID를 지정하면 페이지별 원본 실행 ID·실패 사유를 볼 수 있다. 해당 실행 ID는 기존 `status`·`replay`에도 사용할 수 있다.
- 기존 `fetch <페이지>`는 한도 미설정 상태에서도 수동 한 페이지 용도로 유지한다. 한도를 설정한 프로세스에서는 이 명령에도 같은 일일 수와 최소 간격 검사가 적용된다.

## 요청 결과 미확인과 중단

페이지 배정과 요청 순번·호출 간격 예약은 하나의 짧은 트랜잭션이다. 외부 호출 직전에는 발송 시작 시각을 별도로 한 번 기록하고 다음 허용 시각을 늦춘다. 후속 요청이 먼저 예약되었다면 뒤늦은 이전 요청의 발송은 거절한다. 같은 실행의 배치 재시작이 `receive`를 반복해도 이미 발송한 요청은 다시 보내지 않는다. 이 내부 모드는 CLI의 개별 페이지 실행 선택지로 노출하지 않는다.

외부 응답이 저장되기 전에 프로세스가 종료되면 `WAITING_RESPONSE`로 남을 수 있다. 아직 실행 중인지, 발송 직전에 끝났는지, 응답 저장 전에 끝났는지를 상태만 보고 확정하지 않는다. 같은 요청을 자동으로 다시 보내지 않는다. 인증·429·HTTP 실패도 범위를 `PAUSED`로 남기고 자동 재시도하지 않는다.

저장 원본이 없는 실행은 재개할 수 없다. 기존 프로세스가 종료됐고 원천 결과·호출량을 확인한 뒤 범위를 종료하고 필요한 위치만 새 범위로 시작한다.

```sh
npm run collect:policy -- --args='range-abandon <범위 UUID>'
```

`range-abandon`은 기존 이력을 삭제하지 않고 `ABANDONED`로 남긴다. 이미 발송한 HTTP 요청의 취소 명령은 아니다. 진행 중인 한 페이지 처리가 끝날 수 있으며, 종료된 범위는 다음 페이지로 진행하지 않는다. API 실패·빈 응답·미수집 정책을 삭제나 비공개 사유로 사용하지 않는다.

## 정기 실행

일반 서버에서 다음 설정을 모두 준비한 경우에만 활성화한다. 기본 상태는 비활성화다.

| 설정 | 의미 |
|---|---|
| `ONTONG_COLLECTION_SCHEDULE_ENABLED=true` | 정기 작업 활성화 |
| `ONTONG_COLLECTION_FIRST_PAGE`, `ONTONG_COLLECTION_LAST_PAGE` | 수집할 범위 |
| `ONTONG_COLLECTION_CYCLE_SECONDS` | 이전 정기 범위 종료 후 다음 범위까지의 초 단위 간격 |
| `ONTONG_API_KEY` | 기존 인증키 |

한도·호출 간격·범위·주기·키 중 필요한 값이 빠지면 수집기를 활성화하지 못하게 서버 시작 단계에서 오류를 낸다. 기동 직후에는 새 범위를 시작할 수 있으므로, `true`를 넣는 시점을 실제 외부 작업 시작으로 취급한다. CLI는 이 설정이 있더라도 정기 작업과 회원 알림 작업을 명시적으로 끄고 요청한 명령만 실행한다. `preview`에서는 수집 코드를 만들지 않는다.

정기 작업은 DB의 기존 정기 범위를 이어서 처리한다. 처리할 범위가 없으면 이전 종료 시각과 설정한 주기를 비교해 한 범위만 만든다. 보류된 범위는 운영 확인 전까지 유지하고 새 주기로 건너뛰지 않는다. 수동 범위가 열려 있으면 정기 작업은 해당 범위를 대신 실행하지 않는다. DB 접근·진행 확인은 기본 5초 간격이며 실제 원천 요청은 별도 최소 간격·일일 한도를 통과해야 한다.

## 저장과 완료 의미

Flyway V15는 다음을 추가하고 V16은 현재 요청 예약 ID를 덧붙인다. 이미 로컬에 적용한 V15를 수정하지 않고 발송 지연 보완을 V16에 기록했다.

- `ontong_collection_request_gate`: 요청 간격과 동시 배정에 사용하는 한 행. 외부 대기 중에는 잠금을 잡지 않는다.
- `ontong_collection_sweeps`: 시작·마지막·다음 페이지, 상태, 마지막 정상 처리와 종료 시각.
- `ontong_collection_sweep_pages`: 범위의 페이지와 기존 원본 실행 ID, 처리 결과·오류.
- 기존 `ontong_collection_pages.dispatch_started_at`: 원천 요청의 한 번뿐인 발송 시작 기록. 마이그레이션 이전 행은 이미 시도한 것으로 보존한다.

페이지별 결과와 다음 위치는 함께 커밋한다. 결과 저장 전에 종료돼도 항목별 기존 멱등 처리가 중복 개정을 막는다. 항목 오류는 해당 페이지를 `PARTIAL`로 남기고 다음 페이지를 진행한다. 원본 형식·HTTP·배치 전체 오류는 범위를 `PAUSED`로 남긴다. 예상 항목 수와 응답 수가 다르면 `UNEXPECTED_ITEM_COUNT`로 남기며, 빈 목록을 보고 전체 종료를 추정하지 않는다.

`COMPLETED`는 지정 범위의 페이지 처리가 끝났다는 뜻이다. 전체 서울 정책 확보나 원천 목록의 일관된 스냅샷을 보장하지 않는다. 원천 전체 건수는 각 응답의 참고 값이다. 페이지 정렬 안정성·전국 공통 정책 포함 범위·삭제 의미·정책 원문 보관 기간은 여전히 확인할 사항이다.

## 검증

```sh
./backend/gradlew -p backend test --tests 'kr.youthpolicymate.ingestion.Ontong*Test' --no-daemon
npm run check:backend
```

실제 PostgreSQL과 가짜 원천 응답으로 범위·간격·일일 한도, 서울 날짜 변경, 동시 배정, 요청/배정 롤백, 저장 원본 재개, 부분 실패 후 다음 페이지, 429 중단, 빈 페이지, 반복 주기와 설정 누락을 확인한다. 같은 입력 행렬을 HTTP·규칙·DB 테스트에 반복하지 않는다. 실제 공급자에 오류·429나 과다 호출을 유발하는 테스트는 하지 않는다.

실제 확인에서는 프로세스에만 일일 예약 상한 3회·최소 간격 30초를 적용해 3~4페이지를 한 번 수집했다. 그날 DB의 기존 예약은 1회였으며 추가 2회를 사용했다. 이 값은 이번 두 번의 확인을 제한한 값이고 공식 계정 한도나 운영 권장값이 아니다. `.env`에는 저장하지 않았고 정기 실행도 켜지 않았다.

2026-09-05 서울 14:55:40~14:56:12 실행 `29c4b44d-c860-4562-ba53-497967446585`에서 2페이지·20건을 모두 반영했다. 페이지별 실행은 `69f58799-c677-49aa-a92d-861b5d5d97fc`, `ca87c05f-51b5-462b-ab3d-9454ab78977b`다. 로컬 정책은 20건에서 40건으로 늘었으며 전체 서울 목록 확보를 뜻하지 않는다.

최종 서버 전체 403건(신규 범위·설정 10건 포함)이 실패·오류·건너뛰기 없이 통과했고 빌드도 통과했다. 별도 프로세스의 완료 이력 조회와 V16 적용, 웹 40건 및 두 번째 페이지를 확인했다. 화면 소스와 API 계약은 바뀌지 않아 웹 검사·빌드는 다시 실행하지 않았다. 전체 테스트 종료 중 Spring Session 만료 정리 작업의 DB 연결 중단 로그가 있었으며 JUnit 수집 검사 실패는 없었다.
