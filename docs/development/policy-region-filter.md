# 공개 목록 지역 필터와 단어 검색

2026-10-17 구현. [지역 필터 조사](../research/public-region-filter.md)의 제안 설계를 따라 공개 정책 목록에서 서울 자치구 하나를 골라 공고 지역에 포함된 정책만 보고, 검색어를 띄어쓰기와 무관하게 단어 단위로 비교한다. 기준은 [PRD 3.2](../PRD/0001_product-baseline/spec.md#32-최소-화면-범위)와 [웹앱 기준](../design/webapp-interface.md#정책-목록상세)에 반영했다. 분야별 수와 내 조건 결과에는 지역 필터를 적용하지 않는다.

## 지역 필터

- `GET /api/v1/policies?district=강남구`. 값은 `BasicConditions.district`와 같은 `SeoulDistrict` 표시 이름이고 검색어·분야·질문·접수 상태 필터와 AND로 묶여 전체 건수에 먼저 적용된다. 빈 값은 전체다. Spring 바인더의 enum 변환은 변환기가 실패해도 상수 이름(`GANGNAM`)으로 되돌아가므로, 컨트롤러가 문자열을 받아 `SeoulDistrict.fromLabel`로 찾고 상수 이름·목록 밖 값은 400 `INVALID_REQUEST`로 거절한다. OpenAPI에는 `@Schema(implementation = SeoulDistrict.class)`로 표시 이름 enum을 남긴다.
- 비교 대상은 저장 내용의 `regionCodes`(온통청년 `zipCd`, 법정동코드 앞 5자리)다. 자치구와 코드의 대응은 `policy/catalog/SeoulRegionCodes`에 두고 자격 판정의 `SeoulDistrict`와 분리한다. 코드는 공고 지역이지 거주 자격이 아니다.
- 포함 규칙: 선택한 자치구 코드가 있으면 포함, 서울 전체 코드 `11000`이 있거나 코드가 비어 있으면 지역 미확인으로 보고 포함, 서울 코드가 있는데 그 자치구가 없거나 서울 코드가 전혀 없으면 제외한다. SQL은 `content->'regionCodes' @> jsonb_build_array(:code)`다(`?` 연산자는 JDBC 자리표시자와 충돌). 전체 수집 뒤 건수가 늘면 GIN(`jsonb_path_ops`) 인덱스를 검토한다.
- 화면은 목록 검색 폼의 검색어 옆에 ‘전체 지역’과 25개 자치구 선택을 두고 검색 버튼으로 함께 적용한다. 페이지 이동·분야·질문 필터 링크와 결과 제목에 선택을 유지하며, 지역을 고르면 “선택한 자치구가 공고 지역에 포함된 정책을 보여줘요. 신청 자격은 공고에서 확인해주세요.”를 안내한다. 지역만 골라 결과가 없으면 지역 때문임을 안내한다. 지역을 고른 결과는 검색에 노출하지 않는다(`robots index:false`). 저장한 거주 자치구를 주소에 자동으로 넣지 않는다. 자치구 목록은 `features/policies/seoul-district.ts`에 두고 조건 입력 화면과 공유한다.
- 좁은 화면(639px 이하)은 검색어 한 줄, 지역·접수 상태 한 줄, 검색 버튼 한 줄로 놓는다.

### 남은 위험

- 자치구 하나만 코딩된 정책이 다른 구 거주자의 필터에서 빠질 수 있다. 조사에서 본문에 거주 제한 문구가 없는 자치구 전용 정책 2건을 확인했다. 전체 수집 뒤 자치구 전용 10~20건의 원문을 확인하고 필요하면 정책별 보정 범위를 정한다.
- 현재 로컬 90건은 `zipCd=11000` 요청 결과라 모두 서울 코드를 포함해 효용이 작다. 서울 코드가 없는 정책은 전체 수집 뒤 생긴다.

## 단어 검색

- `q`는 공백(일반·탭·줄바꿈·NBSP·전각)으로 나눈 단어가 모두 들어 있는 정책을 찾는다. 비교 대상은 제목·설명·운영 기관을 이어 붙여 같은 공백을 모두 뺀 문자열이라 ‘취업 지원’은 ‘국민취업지원제도’를, ‘청년미래이음’은 ‘청년 미래이음 대출’을 찾는다. 공백만 있는 검색어는 전체다. `%`와 `_`는 와일드카드가 아니다. 공백을 뺀 뒤 비교하므로 ‘자금 지원’처럼 단어 경계를 넘는 짧은 단어가 드물게 걸릴 수 있다.
- 목록과 내 조건 결과(`POST /api/v1/policies/checks`)가 같은 `where()`를 쓰므로 둘 다 바뀐다. 결과 순서는 바꾸지 않는다(검색 관련도 정렬 없음).

- 변경 검토(`youth-policy-review`)가 전역 `Converter` 방식에서 `district=GANGNAM`이 200으로 통과하는 문제를 찾았다. 첫 서버 테스트가 그 단언에서 실패했고(`.local/verification/1792166656482-718ac202.log`), 컨트롤러가 표시 이름만 받도록 고친 뒤 통과했다. 첫 웹 타입 검사는 목록 페이지의 `district`가 `string`으로 넓혀져 실패했고 타입 주석으로 고친 뒤 통과했다.
- 실제 데이터: 로컬 DB(V1~V6) 90건 중 87건이 서울 25개 자치구 코드를 모두 담고, 3건만 일부다(중랑구 전용 1건, 은평구 전용 1건, 농식품 바우처는 서울 23개로 강서·송파 제외). 빈 코드·`11000`·서울 코드 없음은 0건이다. 자치구별 건수는 87~89건(강서·송파 87, 은평·중랑 89, 나머지 88)이고 빈 값은 전체 90건, `GANGNAM`·`부산`은 400이다.
- 검색: ‘취업 지원’ 11건(국민취업지원제도·청년 국가기술자격 응시료 지원 등), ‘장학 금’ 3건(장학금 3개 정책), ‘자금 지원’ 4건. ‘청년미래이음’은 로컬에 없는 정책이라 0건이다.
- 브라우저: 로컬 DB·검증용 서버(8180)·운영 모드 웹(3103)으로 Playwright CLI 헤드리스 확인. 1280px에서 검색어·지역·접수 상태·검색 버튼이 한 줄이고 선택지는 전체 지역 포함 26개다. 강남구를 골라 검색하면 주소 `district=강남구`, 결과 제목 ‘강남구 88건’, 공고 지역 안내, 다음 페이지·분야 링크의 지역 유지, 초기화 링크를 확인했다. ‘취업 지원’ 검색은 지역을 유지한 채 11건이었고, 은평구와 없는 검색어는 ‘선택한 지역이 포함된 정책이 없어요’를, `district=GANGNAM`은 전체 지역 90건을 보여줬다. Tab 순서는 검색어 → 지역 → 접수 상태 → 검색이다. 390px에서는 검색어 한 줄, 지역·접수 상태가 각 173px로 한 줄, 검색 버튼 한 줄이며 문서 너비 390px로 가로 넘침이 없었다. 콘솔 오류는 없었고 회원 응답은 사용하지 않았다.
- 실제 화면 낭독기와 Safari·Firefox는 확인하지 않았다. 확인 후 브라우저·검증용 웹·서버를 종료하고 DB 컨테이너를 중지했다(볼륨 유지). 8080의 다른 프로젝트 서버는 그대로 두었다.
