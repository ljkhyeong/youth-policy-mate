# 정책 개정 적용 판단 모델

2026-08-31 구현 기준. [원본 확인과 개정 적용 설계](../design/policy-revision-application.md)에 따라 한 정책의 수집 결과 적용 여부를 계산하는 순수 Java 모델을 추가했다. 외부 요청·원본 저장·DB·실제 정책·화면에 연결하지 않았다. 제품 정책과 기존 자격·모집 규칙은 변경하지 않았다.

## 코드와 책임

코드는 `backend/src/main/java/kr/youthpolicymate/policy/`에 있다. 현재 적용 내용과 내부 개정을 정책 모듈이 소유한다는 ADR-0001의 경계를 따른다. 스케줄러·수집 실행기·저장소를 미리 만들지 않는다.

| 코드 | 역할 |
|---|---|
| `PolicyObservation` | 이미 식별한 한 정책의 수집 순번·확인 시각·정상/실패 결과 |
| `SnapshotReference` | 원천명·스냅샷 식별자·원본 해시 참조. 실제 본문이나 저장 기능은 없음 |
| `ContentFingerprint` | 비교 방식 버전·비교 대상 내용의 해시. 정규화·해시 계산은 호출 측의 후속 책임 |
| `PolicyRevisionState` | 현재 상태에서 적용 결과와 다음 불변 상태를 계산 |
| `AppliedRevision` | 내부 개정 번호와 해당 개정을 만든 수집 결과의 원본·내용·순번·시각 |

호출은 `PolicyRevisionState.empty(policyId)`로 시작해 `consider(observation)`을 사용한다. 반환한 `Transition`에는 결정 코드와 다음 상태가 있다. 원래 상태는 변경하지 않는다. `REVISION_CREATED`일 때만 새 개정이 있으며, 같은 내용·실패·낮은 순번·같은 결과 재처리에는 개정을 늘리지 않는다.

현재 상태에서 조회할 수 있는 기록은 다음 세 가지다.

- `lastProcessedObservation`: 처리 순번 기준 마지막 정상·실패 결과. 비교 방식 불일치도 여기에 남는다.
- `currentRevision`: 현재 적용 개정과 그 개정을 만든 원본 근거. 최근 같은 내용의 원본으로 덮지 않는다.
- `lastConfirmedObservation`: 현재 내용과 같거나 새 개정으로 적용할 수 있음을 확인한 마지막 정상 결과. 실패·비교 방식 불일치로 갱신하지 않는다.

결정 코드는 `REVISION_CREATED`, `UNCHANGED`, `OBSERVATION_FAILED`, `COMPARISON_REQUIRED`, `STALE`, `REPLAYED`, `SEQUENCE_CONFLICT`다. 동작은 설계 문서의 적용 규칙 표를 따른다. 마지막 처리 순번과 다른 결과를 가진 동률 순번은 충돌이며, 같은 결과의 재저장과 새로운 외부 요청을 구분해야 한다.

`Readable`은 표시 가능한 내용이라는 입력 분류다. 모든 자격 조건이 해석되었거나 신청 가능하다는 뜻이 아니다. 해시는 소문자 16진수 64자리 형식만 검사하며 실제 원문·정규화 내용과 맞는지 확인하는 구현은 아직 없다. 필드 순서·조회수 제외·HTML·코드·날짜의 의미 비교 규칙을 임의로 추가하지 않았다.

## 검사 명령

저장소 루트에서 실행한다.

```sh
npm run test:policy-revisions
```

개정 적용 11건을 인증키·DB·Docker 없이 검사한다. 서버의 `test` 태스크를 사용하며 CI의 전체 서버 검사에도 포함된다.

```sh
npm run test:recruitment
npm run check:backend
```

`test:recruitment`는 `Recruitment*` 테스트로 범위를 좁혀 기존 모집 31건을 유지한다. 전체 정책 패키지 패턴은 이제 개정 적용 테스트도 포함하므로, 모집만 확인할 때는 전용 명령을 사용한다. 전체 서버 빌드는 실제 PostgreSQL 통합 테스트 때문에 Docker가 필요하다.

## 검증 범위

- 첫 정상 개정과 원본·수집 순번·확인 시각 보존
- 원본 해시·확인 시각 변경과 정책 내용 변경의 분리
- 같은 결과 재처리와 같은 순번의 다른 결과 충돌
- 응답 확인 시각과 관계없는 낮은 순번 거절
- 같은 내용 재수집 뒤 중간 순번 결과의 적용 방지
- A→B→A의 연속 개정 생성
- 실패 후 마지막 정상 개정·확인 시각 유지, 지연 결과 거절과 새 요청 복구
- 첫 실패에 정상 개정·시각을 만들지 않음
- 같은 해시라도 비교 방식 버전이 다르면 확인 필요로 유지
- 다른 정책·유효하지 않은 순번·식별값 거절

개정 11건과 모집 31건, 총 42건 및 서버 `assemble`이 통과했다. 전용 npm 명령 두 개도 각각 실행했다. 이후 전체 `check:backend`에서 기존 180건과 새 개정 11건, 총 191건 및 빌드가 실패·건너뛰기 없이 통과했다. 실제 PostgreSQL·기본 차단 2건과 개발 API·생성 계약 13건도 포함한다.

첫 컴파일에서 Java 기본 `Readable`과 중첩 타입의 이름 충돌이 있었고 명시적 import로 수정한 뒤 통과했다. Gradle·Docker 실행에 권한 확장을 사용했고 JVM 클래스 공유 경고는 유지했다. 웹 코드·API 계약·스키마는 바꾸지 않아 웹 검사·브라우저·타입 재생성은 다시 실행하지 않았다. 원격 GitHub 실행·푸시·배포도 하지 않았다.

## 아직 구현하지 않은 경계

- 원천 정책 식별, 실제 성공 DTO·파서·정규화, 비교 대상 필드와 해시 생성
- 원본 취득·보관·보관 기간·삭제, 수집 순번 발급과 실행·항목 실패 이력
- 상태 복원·DB 저장·재시작 복구, 중복 키와 원자적 갱신, 실제 동시 요청의 경합
- 비교 방식 버전 전환·수동 확인 완료 후 재적용 절차
- 실제 정책 공개와 변경 필드 목록, AI·판정·일정·알림의 개정 전파

특히 두 작업이 같은 현재 상태를 읽으면 이 모델은 각각 다음 개정을 계산할 수 있다. DB 저장 시 기대한 마지막 처리 순번을 확인하고 전체 상태·개정 기록을 한 트랜잭션으로 갱신해야 한다. 따라서 PRD AC-05의 **실제 PostgreSQL에서 중복 정책·개정·알림을 막는 완료 기준**을 충족했다고 보고하지 않는다.

[온통청년 성공 응답 점검](ontong-api-probe.md)과 [원천 계약 최소 확인](../research/ontong-api-contract.md#8-유효-인증키-확보-후-필요한-최소-확인)이 완료되기 전에는 운영 수집기·확정 DTO·Flyway DDL을 만들지 않는다. 이번 작업은 그 전에도 검증할 수 있는 적용 규칙만 다룬다.
