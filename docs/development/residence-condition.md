# 명시적 거주 조건 비교

2026-08-30 구현 기준. 제품 요구는 [PRD의 대상·조건 입력·자격 안내](../PRD/0001_product-baseline/spec.md), 전체 결과는 [판정 결과 집계](eligibility-decision.md)를 따른다.

## 현재 구현 범위

`ResidenceConditionEvaluator.evaluate(condition, residence)`는 확인한 거주 조건과 서울 거주 입력을 받아 `ConditionAssessment` 하나를 반환한다. 인증키·Spring 실행·DB 없이 실행하는 순수 Java 코드다.

비교 대상은 **명시적인 기준일에 주민등록상 거주지가 전국·서울 전체·특정 서울 자치구에 포함되는지**다. 서울 외 거주자 입력, 원천 지역 코드 매핑, 정책 수집·검색 필터와 API/UI 연결은 구현하지 않았다. 전국 범위 지원은 서울 거주자에게 적용할 수 있는 전국 공통 조건을 빠뜨리지 않기 위한 것이며 제품 대상 지역을 확대한 것이 아니다.

## 조건과 입력 모델

| 모델 | 의미 |
|---|---|
| `ResidenceCondition.RegisteredIn` | 원문에서 확인한 주민등록상 거주 허용 범위, 기준일과 근거 |
| `ResidenceCondition.Unresolved` | 아직 해석하지 못한 조건 설명, 확인된 경우에만 기준일, 미해석 이유와 근거 |
| `SeoulResidence` | 사용자가 입력한 서울 자치구와 그 거주 정보가 가리키는 날짜 `asOfDate` |
| `SeoulDistrict` | 서버 내부 서울 자치구 25개. 온통청년 코드나 확정 REST 계약이 아님 |

`RegisteredIn`의 범위는 다음과 같다.

| 범위 | 허용 자치구 집합 | 같은 기준일의 서울 거주 입력 |
|---|---|---|
| `NATIONWIDE` | 비어 있어야 함 | 전국 거주 조건에 포함 |
| `SEOUL` | 비어 있어야 함 | 서울 전체 거주 조건에 포함 |
| `SEOUL_DISTRICTS` | 하나 이상 필요 | 집합 중 하나와 정확히 일치해야 포함 |

전국·서울 전체에는 자치구 제한을 섞지 못하도록 생성자가 거절한다. 자치구 집합은 복사해 보존하고 표시 순서는 enum 선언 순서로 고정한다. 원본 집합의 변경이나 전달 순서 때문에 조건·설명이 달라지지 않는다.

정책의 전국 분류, 중앙부처 기관 분류나 빈 `zipCd`만으로 `NATIONWIDE`를 만들지 않는다. 이 타입은 원문에서 전국의 주민등록상 거주지를 허용한다고 확인한 조건이다. 거주 정보를 아예 요구하지 않는 ‘거주 제한 없음’과도 같지 않다. 현재 타입은 세 범위 모두 거주 입력과 기준일을 요구한다.

현재 UI의 자치구 이름 25개와 서버 enum의 표시 이름이 같은지는 확인했다. UI 문자열을 서버 enum이나 원천 코드로 바꾸는 매핑은 추가하지 않았다. 향후 원천 파서에서 알 수 없는 코드·빈 목록을 만나면 전국 허용이나 서울 전체로 대체하지 말고 `Unresolved`로 보존한다.

## 기준일과 미확인 처리

`SeoulResidence.asOfDate`는 입력한 시각·본인확인 시각·전입일이 아니다. **그 날짜에 해당 자치구에 주민등록상 거주한다는 사용자 입력**이다. 현재 주소에 과거 정책 기준일을 붙여 과거 거주를 확인한 것처럼 만들면 안 된다.

| 상황 | 항목 결과 | 미확인 원인 |
|---|---|---|
| 허용 지역·거주 정의·정책 기준일이 미해석 | `UNKNOWN` | `UNRESOLVED_POLICY` |
| 거주 정보가 없음 | `UNKNOWN` | `MISSING_USER_INPUT` |
| 입력 거주지의 날짜와 정책 기준일이 다름 | `UNKNOWN` | `MISSING_USER_INPUT` |
| 같은 기준일이고 허용 지역에 포함됨 | `MET` | 없음 |
| 같은 기준일이고 허용 자치구에 포함되지 않음 | `NOT_MET` | 없음 |

기준일이 다르면 입력한 자치구가 같아도 비교를 보류한다. 하루 전후의 입력으로도 거주 연속성을 추정하지 않는다. 정책 기준일은 이미 확인했으므로 이 경우의 미확인 원인은 정책 해석이 아니라 **해당 날짜의 사용자 정보 부족**이다. 설명에는 두 날짜를 남긴다.

정책이 미해석이면 사용자 입력 유무에 앞서 그 이유를 보존한다. 거주 기간, 직장·학교 소재지와의 선택 요건, 전입 예정, 동 단위 제한, 외국인 체류지 등 다른 거주 정의는 현재 비교하지 않는다. 해당 항목을 `Unresolved`로 남기거나 아직 반영하지 못한 예외를 `PolicyReview`의 미완료 항목으로 보존한다. AI 추출 후보만으로 확인 완료 조건을 만들지 않는다.

현재 날짜를 조회하거나 시간대로 날짜를 바꾸지 않으므로 `Clock`은 필요하지 않다. 나중에 오늘·신청일을 기준일로 선택하는 계층을 만들 때 명시적인 시계와 시간대를 적용한다.

## 근거·전체 판정·화면 연결

결과는 조건 ID, 허용 지역 설명, 정책 기준일, 입력 자치구와 그 기준일, 이유와 원문 근거를 보존한다. 새 로깅·저장·외부 전송은 없다. 자치구와 기준일도 개인 조건이므로 결과 객체 전체를 로그·분석 이벤트에 넣지 않는다.

비교기는 정책 전체의 검토를 완료하지 않는다. 연령과 거주가 맞아도 신청 주체·추가 조건·예외가 미해석이면 전체 결과는 `NEEDS_REVIEW`다. [조사 사례 B](../research/ontong-api-contract.md#사례-b-전국-분류와-개인-신청-가능-여부는-다름)의 전국 분류와 동아리 신청 요건을 서로 다른 조건으로 다뤄야 하는 이유가 여기에 있다.

`/conditions`에는 현재 자치구 입력만 있고 특정 과거 날짜의 거주 확인 흐름은 없다. 이번 작업에서 입력 항목을 늘리거나 자동 전송·저장을 추가하지 않았다. 연결할 때는 현재 정보로 확인할 수 없는 날짜를 사용자에게 안내하고, 주소 이력 전체를 먼저 수집하지 않는다. 사용자 입력을 공적 거주 증명으로 표시하지 않는다.

## 코드와 검증

코드는 `backend/src/main/java/kr/youthpolicymate/eligibility/`의 `ResidenceCondition.java`, `ResidenceConditionEvaluator.java`, `SeoulDistrict.java`, `SeoulResidence.java`에 있다. 검증은 `backend/src/test/java/kr/youthpolicymate/eligibility/ResidenceConditionEvaluatorTest.java`에서 수행한다.

저장소 루트에서 실행한다.

```sh
npm run test:eligibility
./backend/gradlew -p backend assemble --no-daemon
```

2026-08-30에 거주 비교 17건·연령 비교 18건·기존 집계 14건, 총 49건이 실패·건너뛰기 없이 통과했고 서버 `assemble` 빌드도 통과했다. 전국·서울 포함, 복수 자치구 일치·불일치, 입력 누락, 기준일 하루 전후, 미해석 예외, 순서와 근거 보존, 연령 결과와의 집계를 확인했다.

테스트는 허용 지역·날짜를 직접 지정한 인공 입력이다. 조사 사례의 위험을 재현하지만 실제 API 응답이나 원문 파서를 검증한 것은 아니다. 실제 정책 판정 정확도·자동화 가능 비율·원천 지역 코드 검증으로 보고하지 않는다. 웹·DB 코드와 의존성은 바꾸지 않았으며 프런트엔드 검사와 PostgreSQL 통합 테스트는 이번 작업에서 다시 실행하지 않았다.
