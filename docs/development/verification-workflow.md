# 개발 검증 절차

## 작업 순서

1. 변경 파일과 확인할 동작을 정한다. 이전 실행이 있으면 `npm run verify -- status`로 명령·결과·그 뒤 바뀐 파일을 확인한다.
2. 관련 테스트로 수정 중인 동작을 확인한다. 알려진 코드 검토와 필요한 테스트 보완을 마친 뒤, 전체 검사가 필요한 경우 한 번 실행한다.
3. 실패하면 로그에서 코드·환경·명령 오류를 구분하고 원인을 수정한 뒤 실패한 범위부터 재실행한다. 원인이나 실행 조건이 그대로인 명령을 반복하지 않는다.
4. 필요한 검증이 통과하면 결과를 기록하고 커밋한다. 문서 갱신·커밋·코드가 같은 병합만으로 앱 검사를 다시 실행하지 않는다.

## 변경별 검증 범위

| 변경 | 기본 확인 | 확대하는 경우 |
|---|---|---|
| 문서·스킬 | 변경한 링크·경로·실행 명령, 수정한 스킬 형식 | 실제 앱 동작도 변경했을 때 해당 검사 |
| 화면 문구·스타일 | 바뀐 화면의 표시·줄바꿈 | 입력·상태·이동 동작도 바뀌면 관련 테스트 |
| 웹 동작·타입 | 관련 Vitest 테스트와 `check:web`, 대표 사용자 흐름 | 라우팅·서버 렌더링·의존성 변경 시 `build:web` |
| 자격·기간 등 서버 규칙 | 해당 클래스·기능 테스트 | 공통 계산·모듈 전반에 영향이 있으면 전체 서버 검사 |
| SQL·트랜잭션·인증 | 관련 PostgreSQL·권한 통합 테스트 | 공통 보안 설정·마이그레이션 영향이 넓으면 전체 서버 검사 |
| API 계약 | DTO 수정 후 생성, 대표 응답·`check:api-types`·소비 코드 검사 | 계약 소비 범위에 맞춰 웹·서버 검사 추가 |
| 빌드 설정·의존성·광범위한 변경 | 영향받는 앱의 전체 검사 | CI 필수 검사는 그대로 수행 |

컴파일 성공·실행 파일 생성·부분 테스트를 전체 테스트 통과로 보고하지 않는다. 후속 수정이 있으면 그 수정의 영향만 확인하고, 통과한 다른 범위를 자동으로 다시 실행하지 않는다.

## 실행과 결과 기록

저장소 루트에서 실행한다. `verify`는 기존 npm 검증 명령을 실행하고 명령·인자·종료 코드·시간·Node 버전·Git 기준·파일 해시를 `.local/verification/`에 기록한다. 성공 시 요약, 실패 시 로그 끝 20줄을 출력한다. 전체 로그는 기록된 경로에서 필요한 부분만 읽는다.

```sh
npm run verify -- test:policy-questions
npm run verify -- test:web -- src/features/eligibility/policy-questionnaire.test.tsx
npm run verify -- compile:backend
npm run verify -- package:backend
npm run verify -- status test:policy-questions
```

- `compile:backend`: 앱·테스트 컴파일만 수행한다. DB 테스트를 실행하지 않는다.
- `package:backend`: `bootJar`로 실행 파일만 만든다. 통과한 테스트를 다시 실행하지 않는다.
- `test:policy-questions`: 정책별 `*RulesTest`만 실행한다. API·DB 검증은 별도로 선택한다.
- `check:backend`: 전체 테스트를 포함한 빌드다. 컴파일이나 로컬 서버 반영만 필요한 상황에 사용하지 않는다.
- `verify status [스크립트]`: 최근 5개 기록과 현재 파일 차이를 보여준다. 검사를 자동 생략하거나 실패를 재시도하지 않는다. 실행 중 파일이 바뀌면 종료 코드 2로 재확인을 알리고, 중단되어 결과가 없는 기록은 미완료로 남긴다.
- 파일 비교는 Git 추적 파일과 무시하지 않은 새 파일을 대상으로 한다. `.env`·설치된 의존성·JDK·Docker·DB 상태는 비교하지 않으므로 환경이 바뀌었으면 필요한 검증을 다시 선택한다. 생성 명령인 `generate:api`는 직접 실행하고, 생성 diff를 확인한 뒤 검증을 기록한다.

결과 기록은 로컬에만 보관한다. HANDOFF에는 실제 명령·확인 범위·결과·남은 제약을 짧게 남긴다. 테스트 총개수를 여러 문서에 복사해 맞추지 않는다. Gradle의 부분 테스트는 기존 XML 보고서를 교체할 수 있으므로 최신 XML만으로 이전 전체 검사 결과를 집계하지 않는다.

## 기존 작업에서 확인한 낭비와 조치

2026-09-05에 이 프로젝트의 **개발 계속 진행**(`01a06eec-85ea-7653-a3f7-4573c18d5667`)과 **프로젝트 기술스택 추천**(`01a05188-bf8c-7e62-b34a-d4b2bebc1c06`) 작업 기록을 검토했다. 최근 페이지에서 검증 명령을 추렸고, 반복 실행이 있던 4개 작업의 수정 순서를 자세히 비교했다.

| 확인한 사례 | 적용한 조치 |
|---|---|
| AI 복구 작업에서 전체 빌드 후 검토·테스트 보완이 이어져 다시 검사함 | 알려진 검토를 전체 검사 전에 마치고 후속 수정은 관련 검사로 확인 |
| 문구 작업에서 정책 테스트·`bootJar` 명령을 반복하고, 기능 작업마다 부분 검사 뒤 전체 빌드를 추가함 | 컴파일·관련 테스트·패키징·전체 검사 명령을 구분 |
| 테스트 XML 집계용 awk를 다시 작성하고 여러 문서의 개수를 반복 대조함 | 실행별 로그·결과 기록을 사용하고 총개수 갱신을 완료 조건에서 제외 |
| 긴 문서·작업 기록을 한 번에 출력해 잘림·재조회가 발생함 | 검색으로 위치를 좁히고 원본 응답을 저장한 뒤 필요한 필드·범위만 출력 |

반복 실행 중에는 코드 보강·실패 수정·키보드 초점 수정에 따른 정당한 재검증도 있었다. 실행 횟수 전체를 낭비로 계산하지 않는다. 이번 개선은 명령 분리와 기록을 검증한 것이며 이후 작업의 시간 절감률은 아직 측정하지 않았다.
